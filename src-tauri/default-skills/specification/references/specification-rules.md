# Specification Rules

## Define intent

State one primary outcome in Target. Describe what the user or system must be able to achieve. Split unrelated outcomes into separate specifications.

## Preserve required constraints

List business, legal, platform, security, compatibility, or technical constraints only when the user, project, or authoritative source already requires them. Keep every constraint concrete and verifiable. Do not convert a preferred implementation into a hard requirement without evidence.

## State non-goals

List work that a reasonable reader might otherwise assume is included. Keep each non-goal explicit. Do not use non-goals as a vague future roadmap.

## Make completion observable

Write each Done-when item as a visible outcome or state. Do not write commands, internal implementation steps, feelings, or broad claims such as “works well,” “is fast,” or “is user-friendly.”

## Mark uncertainty honestly

Use `TBD: <precise question>` when a required decision is missing. Keep assumptions in Context and label them clearly. Do not resolve uncertainty with a plausible guess.

## Keep planning out

Exclude proposed files, components, hooks, routes, libraries, patterns, commands, task order, estimates, and code unless one is an explicit hard constraint. Leave those decisions for planning.
