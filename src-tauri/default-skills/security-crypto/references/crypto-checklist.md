# Crypto Checklist — modèle complet de revue

Reference for `security-crypto`. Each item lists: what to search, what weak
looks like, what conform looks like. No verdict without `file:line` evidence.

## 1. Encryption

- [ ] Algorithm and mode
  - Weak: ECB anywhere; CBC without authentication; custom/XOR "encryption";
    DES/3DES, RC4
  - Conform: AES-GCM, ChaCha20-Poly1305, or an established AEAD wrapper
- [ ] Nonce/IV handling
  - Weak: fixed IV, IV derived from a counter reused across keys, random IV
    from a non-CSPRNG source
  - Conform: unique nonce per message under one key, generated by CSPRNG or
    the library itself
- [ ] Key separation: one key per purpose (encryption vs signing vs
  transport), derived via a real KDF when several keys come from one secret

## 2. Hashing

- [ ] Passwords: memory-hard password hashing only (argon2id, bcrypt, scrypt)
  — full review in `security-auth`
- [ ] Integrity/file hashing: SHA-256 class or better
  - Weak: MD5 or SHA-1 relied on for security (checksums against tampering,
    signatures, dedup with adversarial input)
- [ ] HMAC used for message authentication — never bare `hash(key + message)`

## 3. Randomness

- [ ] Every token, key, nonce, IV, session id, reset link, salt comes from a
  CSPRNG (`crypto.getRandomValues`, `crypto.randomBytes`, `OsRng`,
  `secrets`, `SecureRandom` — per language)
  - Weak: `Math.random`, `rand()`, time-seeded generators, UUIDv4 used as a
    *secret* without checking the source
- [ ] Identifiers that must be unguessable are long enough (128 bits of
  entropy minimum)

## 4. Transport (TLS)

- [ ] TLS enforced on every external connection — no plaintext fallback, no
  `http://` for sensitive endpoints
- [ ] Certificate validation never disabled: search for the platform's
  dangerous flags (`rejectUnauthorized: false`, `danger_accept_invalid_certs`,
  `allowInvalidCertificates`, trust-all managers)
  - A disable behind a debug/dev flag: check whether that flag or build can
    reach production. If it can, it is a finding.
- [ ] Minimum protocol version modern (TLS 1.2+)
- [ ] Certificate pinning (mobile/desktop apps with fixed backends):
  present → review the pin update mechanism; absent → note as a deliberate
  trade-off the project should state, not an automatic finding

## 5. Keys and secrets at rest

- [ ] Keys generated with CSPRNG, never hardcoded, never in source or config
  files committed to the repo
- [ ] Storage in the OS keystore/keychain or an equivalent vault; plaintext
  key files are a finding
- [ ] Keys derived from passwords use a real KDF with salt and work factor —
  never a plain hash
- [ ] Secret buffers zeroized after use when the runtime permits (mutable
  buffers in Rust/C; note as N/A in GC'd languages)
- [ ] Key rotation path exists or is consciously absent (documented)

## 6. Custom constructions

- [ ] Any hand-built protocol (rolling own session tokens, signature
  schemes, "obfuscation" as protection) is a priority finding — recommend
  the established library that replaces it
- [ ] Crypto agility: algorithms named in config/constants, not scattered
  magic strings, so a future migration is possible

## After the review

- [ ] Each call site has a verdict: CONFIRMED WEAKNESS / CONFORM /
  UNVERIFIED / N/A — with evidence or reason
- [ ] Weaknesses ranked: key exposure and broken transport first, weak
  primitives second, hygiene last
- [ ] The correction list names the established replacement for each finding
