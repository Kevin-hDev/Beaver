Git, sans quitter Beaver

Beaver sait changer de branche, valider, publier et fusionner sans que tu ouvres un terminal. Il ne prétend pas remplacer Git pour autant : plusieurs opérations courantes n'existent pas dans l'application, et cette page commence par les nommer. Mieux vaut savoir tout de suite ce qui reste au terminal que le découvrir au premier message d'erreur.

Attention Beaver ne récupère jamais rien du dépôt distant. Ni fetch, ni pull : aucune des deux opérations n'existe dans l'application. Le retard affiché par rapport au distant — « Des changements distants sont disponibles » — est calculé sur ce que ton dépôt local sait déjà, et il n'est actualisé que par une récupération lancée ailleurs, ou par un Push réussi depuis Beaver. Pour rester à jour, garde un terminal à côté.

Ce que Beaver fait, et ce qu'il ne fait pas

Chaque « non » de ce tableau est une absence réelle, pas un oubli de la documentation.

Deux mots méritent une précision. « Cloner » dans Beaver ne parle pas de Git : il désigne le clone d'une conversation, décrit dans Cloner une conversation. Et « résoudre un conflit » n'existe pas : quand une fusion en produit un, Beaver l'annule proprement au lieu de te laisser dans un état intermédiaire — la résolution se fait au terminal ou dans un éditeur.

Où ça se passe dans l'application

Git apparaît à deux endroits, avec des rôles différents.

Le sélecteur de branches, dans la barre de contrôle d'une conversation. Il porte le nom de la branche courante et ouvre un menu contenant un champ « Rechercher dans les branches », la liste des « Branches », celle des « Worktrees », le compteur « Non validés : {{count}} fichier(s) » et l'entrée « Créer et extraire une nouvelle branche… ».

La section Git du résumé de conversation, qui porte les actions et l'historique : les boutons « Commit », « Push » et « Merge dans {{branch}} », puis la liste des « Commits ».

Quand le dossier n'est pas un dépôt Git, le sélecteur de branches disparaît entièrement et le résumé affiche « Aucun dépôt Git ». Rien n'est montré en panne : ce qui n'est pas utilisable est invisible.

La condition d'entrée : un projet enregistré

Toutes les opérations Git passent par un même contrôle : le dossier doit exister et se trouver à l'intérieur d'un projet enregistré dans Beaver. Un dépôt ouvert autrement est refusé.

Un sous-dossier d'un dépôt fonctionne : la détection remonte l'arborescence jusqu'au dépôt parent. En revanche, un dépôt sans dossier de travail — un dépôt dit « bare » — est refusé.

Changer de branche, en créer une

Seules les branches locales sont listées : les branches distantes n'apparaissent pas, ce qui découle directement de l'absence de récupération. La branche courante est en tête, les autres par ordre alphabétique, et la liste s'arrête à 500 branches.

Créer une branche part de la position courante et s'y place aussitôt, sans rien valider : tes modifications en cours restent en place et suivent sur la nouvelle branche.

Le nom est vérifié à la saisie et au moment de créer, avec les mêmes règles des deux côtés.

Les règles de nommage d'une branche

Trois refus supplémentaires existent : la branche existe déjà — « Cette branche existe déjà » ; le dépôt n'a aucun commit — « Le dépôt n'a aucun commit, crée un commit d'abord » ; le connecteur GitHub n'est pas connecté — « Connecte GitHub avant de créer une branche ».

Attention GitHub est exigé même pour une branche purement locale. Si l'un des distants de ton dépôt pointe vers GitHub — sous la forme https://github.com/, ssh://git@github.com/ ou git@github.com: —, Beaver demande que le connecteur GitHub soit connecté avant de créer une branche, y compris quand cette branche ne sera jamais publiée. Un dialogue le propose sur place : « Connectez GitHub pour créer une branche », avec le bouton « Connecter GitHub ». À défaut, la branche se crée au terminal. Le connecteur est décrit dans Connecteurs MCP.

Changer de branche est refusé s'il reste des fichiers non validés, et le refus arrive avant que Beaver touche au disque : il n'essaie pas d'extraire puis d'annuler. Le dialogue s'intitule « Effectuez un commit pour changer de branche » et explique : « Les modifications apportées aux fichiers suivants seraient remplacées par l'extraction : ». Il propose « Effectuer le commit et changer de branche… », qui crée un commit de sauvegarde puis extrait. Si rien n'est modifié, l'extraction se fait directement, sans commit.

Les modifications non validées

Les fichiers en attente sont classés « Créé », « Modifié », « Supprimé », « Renommé » et « Copié », chacun avec son nombre de lignes ajoutées et supprimées.

La liste s'arrête à 200 fichiers, mais le compte réel est conservé et la coupure est annoncée : « {{count}} fichiers modifiés. Les chiffres affichés sont partiels. »

Pour un fichier neuf, les lignes ne sont comptées que sous 1 Mo. Au-delà, Beaver annonce zéro plutôt que de lire un gros fichier — un ajout volumineux peut donc apparaître avec un compte de lignes à zéro.

Valider : « Commit »

Le dialogue s'intitule « Commit des modifications », avec le champ « Message du commit (facultatif) » et le bouton « Commit ».

Note Le commit prend tout. Il n'existe pas de sélection de fichiers : le bouton valide l'ensemble du dossier de travail. Pour découper un travail en plusieurs commits, passe par le terminal intégré.

Le message est facultatif. Laissé vide, le commit porte un sujet de sauvegarde automatique. Il n'y a aucune longueur minimale, un maximum de 2 000 caractères, les fins de ligne sont normalisées, et les caractères de contrôle autres que le saut de ligne et la tabulation sont refusés — le message d'erreur est alors « La description du commit est invalide ou trop longue. »

S'il n'y a rien à valider, l'opération réussit sans rien faire. Aucun commit vide n'est créé.

L'auteur du commit est ton identité Git, cherchée d'abord dans la configuration du dépôt, puis dans celle que git déclare. Si aucune identité n'est configurée, le commit échoue avec « Configure ton nom et ton adresse e-mail Git avant de créer un commit. » — Beaver ne fabrique jamais d'auteur de substitution.

Une protection discrète mérite d'être connue : avant chaque commit, le fichier d'index du dépôt est copié ; si le commit échoue, l'index d'origine est remis en place. Un commit raté ne laisse pas le dépôt dans un état intermédiaire.

Publier : « Push »

L'indicateur au-dessus du bouton annonce « {{count}} commit(s) à Push vers {{destination}} · {{branch}} », la destination étant « GitHub » ou « le dépôt distant ».

Beaver pousse la branche courante vers son distant, sans forçage. Le distant est choisi dans cet ordre : celui configuré pour la branche, puis origin, puis le premier de la liste. Après un push réussi, Beaver met à jour la référence distante locale et pose la branche amont — c'est le seul moment où l'état du distant est rafraîchi.

L'authentification est tentée dans un ordre précis, chaque étape une seule fois : l'assistant d'identifiants Git du système, puis le jeton GitHub du connecteur — uniquement pour une adresse en https://github.com/ —, puis la clé SSH de l'agent, puis le nom d'utilisateur, puis la valeur par défaut. S'il n'y a aucun identifiant utilisable, l'appel échoue : rien ne passe en silence. Un dépôt GitHub en SSH n'utilise pas le jeton du connecteur.

Les cinq refus de Push et leur message
SituationMessage affiché
Aucun identifiant utilisable« Connexion Git requise pour effectuer le Push. »
Le distant refuse« Le dépôt distant a refusé le Push. Vérifie tes droits ou la protection de la branche. »
La branche distante a avancé« La branche distante contient des changements plus récents. Synchronise le dépôt avant de refaire le Push. »
Réseau injoignable« Connexion au dépôt distant impossible. »

Le troisième cas est celui qui reviendra le plus souvent, et il découle de l'encadré du haut : Beaver ne sait pas rattraper un retard, puisqu'il ne récupère rien. La résolution passe par un git pull au terminal, puis un nouveau Push.

Deux délais réseau sont fixés à 30 secondes chacun, pour la connexion et pour l'inactivité. Aucune liste d'adresses autorisées n'existe : n'importe quel distant configuré dans le dépôt est utilisable.

Fusionner : « Merge »

Le dialogue s'intitule « Merge dans {{branch}} » et explique « Choisis la branche à intégrer dans {{branch}}. », avec le champ « Branche source ». La fusion est locale : une branche locale dans la branche courante, jamais une branche distante.

L'aperçu annonce l'ampleur avant d'agir : « {{count}} commit(s) seront ajoutés à {{branch}}. », et le cas échéant « {{count}} modification(s) feront l'objet d'un Commit avant le Merge. ». Quand il n'y a rien à faire : « Cette branche est déjà mergée dans {{branch}}. »

Quatre situations font refuser la fusion : la source est la cible ou il n'y a rien à fusionner ; la branche courante n'est pas celle attendue ; le dépôt est déjà au milieu d'une autre opération Git ; il reste des modifications non validées — sauf si tu choisis de les valider d'abord, via « Commit puis Merge dans {{branch}} ».

Note Un conflit ne casse rien. Beaver annule la fusion, puis vérifie que la position est revenue à sa valeur d'origine, que le dépôt est propre et qu'aucun fichier n'est modifié — ce n'est qu'après ce contrôle qu'il t'annonce le conflit, avec « Le Merge crée un conflit. Il a été annulé sans modifier la branche. ». Il ne propose pas de le résoudre : ça se fait au terminal ou dans un éditeur.

Les crochets du dépôt sont neutralisés pendant la fusion. Le chemin des crochets pointe vers un dossier temporaire vide, la signature cryptographique est désactivée, et aucune invite du terminal ne peut bloquer l'opération. C'est un choix de sécurité assumé : un crochet de dépôt est du code exécutable, et une fusion lancée depuis une interface graphique ne doit pas l'exécuter à ton insu. Voir Modèle de sécurité.

Supprimer une branche ou un worktree

Un aperçu précède toujours la suppression. Il annonce, s'il y a lieu : que c'est la branche courante et sur quelle branche Beaver se repliera, les fichiers non validés, et le nombre de commits non fusionnés — « {{count}} commit(s) ne sont pas fusionné(s) ».

La branche de repli est la branche courante si elle diffère de la cible, sinon main, master, develop, dev dans cet ordre, sinon la première autre branche. Le message est « Cette branche est utilisée. Beaver passera sur {{branch}} avant de la supprimer. » ; sans aucune branche de repli, « Crée d'abord une autre branche pour pouvoir supprimer celle-ci. »

Le comptage des commits non fusionnés s'arrête à 10 000. Un worktree suit la même logique, avec les mêmes trois modes et un délai de dix secondes sur l'opération ; le worktree courant, lui, ne peut pas être supprimé.

Lire l'historique et les différences

L'historique porte sur la branche courante uniquement. Il se charge par pages de 24 commits, la suivante arrivant à l'approche du bas de la liste, jusqu'à 1 000 commits affichés. Chaque commit montre sa première ligne de message seulement, bornée à 160 caractères ; sans message, « Commit sans message ». Le parcours s'arrête à 10 000 commits ; au-delà, la liste répond « Historique des commits indisponible. ». Une branche sans commit affiche « Aucun commit sur cette branche ».

Ouvrir un commit montre les fichiers qu'il touche — 200 au maximum — puis, fichier par fichier, ses différences. Celles-ci se lisent dans deux modes : un commit contre son parent, ou le dossier de travail contre le dernier commit, avec trois lignes de contexte autour de chaque modification.

Un aperçu de différence est tronqué plutôt qu'abandonné quand il dépasse ses bornes, et la troncature est annoncée : « Aperçu limité : le fichier contient davantage de modifications. ». Un fichier binaire n'affiche aucune différence, seulement l'indication qu'il l'est ; un fichier illisible affiche « Les différences de ce fichier ne peuvent pas être affichées. »

Les aperçus de fichiers versionnés ont leurs propres bornes, et toute erreur d'aperçu remonte un message générique : aucun chemin, aucun détail interne n'est jamais affiché.

Les worktrees

Un worktree est un second dossier de travail relié au même dépôt : il permet d'avoir deux branches ouvertes en même temps sur le disque, sans jongler avec les extractions.

Beaver les liste mais n'en crée pas. La création se fait au terminal, avec git worktree add.

La liste s'arrête à 100 worktrees et exclut deux catégories : les dépôts sans dossier de travail, et tous les worktrees internes que Beaver crée pour ses propres sous-agents. C'est voulu — ce sont des dossiers de travail temporaires, pas les tiens. Voir Sous-agents.

Changer de worktree change de dossier de travail, ce qui ne peut pas se faire dans la même conversation. Le dialogue « Changement de dossier » l'explique — « Ce worktree utilise un autre dossier de travail. Crée une nouvelle session pour garder la conversation actuelle intacte. » — et propose « Nouvelle session ».

La détection automatique des changements

Beaver surveille le dépôt et rafraîchit son affichage tout seul. À l'intérieur du dossier .git, il surveille le fichier de position courante, le dossier des branches et le fichier des références compactées, en regroupant les changements sur 200 millisecondes.

Le dossier de travail, lui, est relu toutes les trois secondes, et l'interface n'est prévenue que si quelque chose a réellement changé : nom de branche, position, nombre de fichiers modifiés, ou une empreinte des premières entrées du dossier.

Note Ce que tu fais au terminal apparaît tout seul. Un commit, une extraction ou une simple édition faite hors de Beaver se voit dans l'application en trois secondes au plus, sans rien rafraîchir à la main — y compris quand le nombre de fichiers modifiés ne change pas.

Un seul dépôt est surveillé à la fois pour toute l'application : ouvrir un autre projet arrête la surveillance du précédent. Et si aucun dossier .git n'est trouvé, la surveillance ne démarre pas et ne signale rien.
