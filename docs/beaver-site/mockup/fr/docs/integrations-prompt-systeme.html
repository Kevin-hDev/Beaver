Prompt système et extensions

La réponse courte tient en une phrase : une extension ne touche pas au prompt système, ni pour le lire, ni pour l'écrire, ni pour s'y insérer. Modifier, remplacer ou désactiver le prompt système est une fonctionnalité native de Beaver, sans rapport avec les extensions. Cette page dit où se règle la personnalisation, ce que les extensions font réellement autour du prompt, et par quel chemin leur texte atteint quand même le modèle.

La personnalisation du prompt système est native

Beaver permet de consulter, modifier, remplacer et désactiver le prompt système. Ce réglage vit dans l'application. Le prompt effectivement envoyé se calcule à partir de tes réglages enregistrés, du nom du modèle, du mode, du niveau de détail, du prompt natif du modèle Ollama le cas échéant, et du prompt par défaut de Beaver. Quatre états sont possibles : par défaut, prompt Beaver, personnalisé, désactivé.

Aucune extension ne figure parmi ces entrées. Le mécanisme complet — modes, portées, prompts natifs Ollama, comment modifier et restaurer — est décrit dans Prompts système. C'est la page à lire si tu cherches à changer les instructions données au modèle.

Ce qu'une extension peut faire, et ce qu'elle ne peut pas

Une extension communique avec Beaver par un canal fermé : une liste de méthodes déclarée dans un contrat, et rien d'autre. Cette liste est écrite une seule fois — la version utilisée par Beaver est produite à la compilation à partir du même fichier de contrat que celui lu par l'extension. Il n'existe donc pas de seconde liste, plus permissive, ailleurs.

Les douze méthodes qu'une extension peut appeler sont app.info, sessions.list, sessions.get, projects.list, mcp.connectors.list, mcp.tool.call, channels.config.get, secrets.provider.get, secrets.mcp.oauth.get, secrets.mcp.env.get, secrets.channel.get et host.load.stage. Aucune ne concerne les prompts ni les réglages de l'agent ; tout autre nom renvoie une erreur.

Ce qu'une extension peut déclarer : des outils, des skills, des ressources, des éléments d'interface, et l'écoute d'événements. En mode avancé, elle peut en plus recouvrir un outil natif — ce qui ne concerne que les outils, et fait l'objet de sa propre page. Côté événements, un seul existe, session.turn.started : il signale qu'un tour de conversation a commencé, il ne permet pas d'intervenir dans la construction du prompt.

Note La porte « avancée » est fermée, pas entrouverte. Une extension déclarée en mode avancé dispose d'un appel générique, beaver.unstable.call(...). On pourrait croire qu'il donne accès à des fonctions cachées du cœur de Beaver : ce n'est pas le cas. Cet appel n'accepte que les méthodes marquées « avancées » dans le contrat, et aucune méthode du contrat actuel ne porte ce marquage — les douze méthodes déclarées sont toutes stables. L'ensemble des méthodes que unstable.call peut atteindre est donc vide aujourd'hui.
Attention Ne confonds pas deux mécanismes qui portent le même nom. « Remplacement » désigne dans Beaver le fait pour une extension de recouvrir un outil natif — la recherche web, par exemple. Cela ne concerne à aucun moment le prompt système. Voir Remplacer un outil.

Le seul texte que Beaver ajoute à cause des extensions

Il existe bien un paragraphe ajouté au prompt système à cause des extensions — mais il est écrit par Beaver, pas par une extension, et son texte est fixe. Il est ajouté à la fin du message système, en mode Agent uniquement ; en mode Chatbot, il n'est pas ajouté. Il n'apparaît que si les deux outils de découverte sont actifs, list_extensions et inspect_extensions ; si un seul manque, rien n'est ajouté.

Son contenu explique au modèle comment consulter le catalogue d'extensions : inspecter directement 1 à 4 identifiants exacts, n'utiliser la liste complète que pour la vue d'ensemble, et ne jamais chercher une extension par mot-clé. Ce texte est en anglais dans le code, comme le reste du prompt système.

Comment un texte d'extension atteint quand même le modèle

C'est le point important pour la sécurité, et il ne passe pas par le prompt système.

Les skills d'extension n'entrent pas dans le prompt système. Le prompt contient une liste des skills disponibles, construite depuis le catalogue global — et ce catalogue exclut explicitement les skills d'extension : toute entrée dont l'identifiant commence par extension: en est retirée. Le commentaire qui accompagne le filtre dit pourquoi : cet espace de noms est autorisé session par session et ne doit jamais entrer dans le catalogue global.

En revanche, le contenu d'un skill d'extension entre dans la conversation quand le modèle le charge. Le modèle demande un skill par son identifiant ; si celui-ci commence par extension:, Beaver charge le fichier Markdown fourni par l'extension. Deux garde-fous encadrent ce chargement : le texte est préfixé par sa provenance, sous la forme Skill source: <identifiant de l'extension>, si bien que le modèle voit d'où vient l'instruction ; et le chargement est refusé si la session écarte les extensions.

Les descriptions déclarées par l'extension sont également du texte tiers vu par le modèle : la description d'un outil est obligatoire, non vide et bornée. C'est par ces descriptions qu'un outil d'extension se présente au modèle.

Sécurité C'est là toute la différence. Le contenu d'une extension atteint le modèle à l'intérieur de la conversation, après le prompt système, et signé par sa provenance. Il reste un texte que le prompt système encadre, au lieu de devenir le cadre lui-même. Le prompt système est le seul texte que le modèle reçoit avant tout contenu extérieur : c'est lui qui fixe les règles auxquelles le reste est censé obéir, y compris celles qui encadrent l'usage des outils.
