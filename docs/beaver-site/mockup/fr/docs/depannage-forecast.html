Forecast, quand le calcul échoue

Un modèle de prévision qui ne s'installe pas, des données refusées, un calcul qui s'arrête net. Cette page part du message affiché et remonte à la cause réelle — ce qui, sur Forecast, demande un détour, parce que le panneau n'a que trois messages pour une trentaine de pannes différentes.

Note Le message affiché ne nomme presque jamais la cause. Le moteur de prévision produit des phrases précises — « Modèle non installé », « Ressources insuffisantes pour ce modèle », « Clé API Nixtla non configurée » — mais le panneau Forecast les remplace toutes par une seule. Quand « Le calcul a échoué » ne suffit pas, redemande la même prévision à l'agent dans une conversation : lui reçoit la phrase exacte du moteur et te la montre. C'est le conseil le plus utile de cette page.

Avant de chercher : les deux endroits où le message est différent

Le même échec produit deux textes très différents selon la façon dont la prévision a été lancée. C'est le premier tri à faire, et il évite la moitié des recherches inutiles.

Depuis le panneau Forecast — import d'un fichier, puis bouton Lancer le forecast — il n'existe que trois messages possibles.

Les trois seuls messages du panneau Forecast
Ce qui s'afficheQuand
« Import impossible. Vérifie le format du fichier. »Le fichier n'a pas pu être lu
« Le calcul a échoué. Vérifie les colonnes, le modèle et la clé API. »Toute panne pendant le calcul
« Le stockage Forecast est plein. Supprime d'anciennes analyses puis réessaie. »Le seul cas particulier reconnu

La deuxième phrase couvre une trentaine de causes distinctes. Elle nomme trois pistes — les colonnes, le modèle, la clé API — mais elle ne dit pas laquelle est en cause, et il arrive que la cause ne soit aucune des trois.

Depuis une conversation avec l'agent (« fais-moi une prévision sur ce fichier »), le message exact du moteur est renvoyé tel quel dans le résultat de l'outil, accompagné de l'étape suivante suggérée. C'est le seul endroit où la vraie phrase apparaît.

Les écrans de l'espace Forecast — Données, Scénarios, Comparaisons, Notes, Évaluation — suivent la même règle : ils affichent un message traduit et générique, jamais celui du moteur.

Le modèle de prévision ne s'installe pas

Ce que tu vois, à côté du bouton d'installation, est unique : « Le téléchargement a échoué ». Le moteur ne transmet qu'un seul code d'échec, quelle que soit la cause réelle.

Un second message existe, et il ne veut pas dire la même chose : « Impossible d'ajouter ce modèle à la file d'attente. » Celui-là signifie que l'installation n'a pas démarré — la file est pleine, seize téléchargements en attente au maximum.

Attention Les modèles de prévision locaux demandent Python 3.12. Exactement 3.12 : ni 3.11, ni 3.13. Beaver cherche successivement python3.12, python3 puis python dans le chemin du système, et n'accepte que cette version. C'est la seule dépendance externe des modèles locaux, l'application ne l'installe pas et n'a aucun repli. Sans elle, l'installation échoue avec le message générique « Le téléchargement a échoué », qui ne dit pas que Python est en cause. 
$ python3.12 --version

Le cas du réseau d'entreprise. Les poids viennent uniquement de huggingface.co et des domaines liés, et les bibliothèques Python uniquement de pypi.org, avec vérification obligatoire des empreintes et refus de tout paquet à compiler. Un miroir interne, un proxy qui réécrit les réponses ou un blocage de ces deux domaines fait échouer l'installation, et aucun réglage ne permet de la détourner.

Attention Une installation interrompue repart de zéro. Il n'y a pas de reprise : le dossier de travail temporaire est supprimé à la première erreur, et chaque fichier en cours d'écriture est effacé avec lui. Rien de ce qui a déjà été téléchargé n'est conservé. Sur un modèle de plusieurs gigaoctets et une connexion instable, mieux vaut lancer l'installation à un moment où la machine ne sera pas coupée.

L'installation semble bloquée

C'est le symptôme le plus courant, et ce n'est pas une panne. La barre de progression ne mesure pas une seule opération mais quatre, et la troisième est longue et silencieuse.

Ce que la barre montre, et ce qui se passe réellement
Ce que montre la barreCe qui se passe réellement
0 à 70 %Téléchargement des poids du modèle
72 %Création de l'environnement Python
76 %Préparation de l'installateur de bibliothèques
80 %Installation des bibliothèques Python — l'étape la plus longue
98 %Vérification du moteur
99 %Mise en place définitive du modèle

La phase affichée à côté du pourcentage porte les libellés Téléchargement, Préparation du moteur, Installation, Terminé.

Note La barre bloquée à 80 % n'est pas une panne. C'est l'installation des bibliothèques Python. Elle peut durer plusieurs minutes sans que le pourcentage bouge, puis repart à 98 % et 99 % : ce n'est pas une progression continue, ce sont quatre paliers.

À la toute fin, un test réel du modèle est exécuté, avec un délai maximal de quinze minutes — un échec à ce moment-là annule l'installation entière.

Annuler est possible à tout instant, par le bouton Annuler ou par la touche Échap quand l'écran des modèles est au premier plan. L'annulation supprime ce qui a été téléchargé.

Le modèle est installé, mais Beaver affiche « Préparation requise »

Beaver distingue quatre états pour un modèle local.

Les quatre états d'un modèle de prévision
Ce que tu lisCe que ça signifie
« Non installé »Les poids ne sont pas là
« Préparation requise »Les fichiers sont là mais n'ont pas la taille attendue
« Mise à jour requise »Le reçu, le moteur ou le test de validité n'est plus à jour
« Installé »Les cinq conditions sont réunies

Le passage à « Installé » exige cinq choses simultanément : le dossier du modèle et son marqueur .complete, des fichiers à la taille attendue, un reçu .artifacts-v1.json conforme au catalogue de la version installée, un moteur Python prêt pour la famille du modèle, et une preuve de test à jour.

Ce qu'il faut en retenir : après une mise à jour de Beaver qui change la liste des bibliothèques Python, un modèle déjà installé bascule en Mise à jour requise, et le bouton affiche Préparer au lieu d'Installer. Les poids ne sont pas retéléchargés : Beaver reconnaît qu'ils sont valides et ne refait que le moteur et la validation.

Un écart d'affichage à connaître : des fichiers présents mais de mauvaise taille — typiquement après une copie interrompue — n'ont pas de libellé propre et retombent eux aussi sur « Préparation requise ». Le bouton Préparer relance alors bien un téléchargement complet. L'affichage est trompeur, l'action est la bonne.

« Ressources insuffisantes » : la mémoire

Beaver mesure la mémoire disponible avant de lancer un modèle local et refuse plutôt que de laisser la machine s'effondrer. Il y a deux refus distincts :

  • « Ressources insuffisantes pour ce modèle » — la mémoire a été mesurée, et elle ne couvre pas le besoin du modèle majoré de 20 %.
  • « Ressources indisponibles pour ce modèle » — la mémoire n'a pas pu être mesurée et le modèle demande plus de 2 048 Mo. En dessous de ce seuil, Beaver laisse passer.

Le détail du calcul — mémoire vidéo contre mémoire vive, les cinq verdicts — est dans Sélection du modèle.

Attention Rien ne vérifie la mémoire avant de télécharger. Ce contrôle n'a lieu qu'au lancement d'un calcul, jamais à l'installation. Tu peux donc installer plusieurs gigaoctets de modèle, puis découvrir au premier calcul que la machine ne peut pas le faire tourner. Vérifie la mémoire demandée sur la fiche du modèle avant d'installer — voir Matériel et VRAM.

Un point qui rattrape parfois la situation : la mémoire mesurée est celle disponible au moment du calcul. Fermer un navigateur peut suffire à faire passer un modèle refusé cinq minutes plus tôt.

À l'audit, juste avant le calcul — le contrôle de qualité examine chaque ligne et produit une liste d'anomalies. Une seule anomalie de gravité Erreur suffit à bloquer le calcul. S'y ajoutent des limites de volume.

La liste complète des vingt-deux anomalies et leur remède colonne par colonne est dans Données et audit.

Ce qui ne se voit qu'à l'écran, et qui bloque beaucoup de monde : la section Données de l'espace Forecast affiche le nombre d'anomalies et leur gravité — « Erreur bloquante · 3 », « Avertissement · 12 » — sans jamais nommer l'anomalie. Tu sais donc qu'il y a trois problèmes bloquants, et rien de plus.

Le détour qui marche : demander l'audit à l'agent. Le message précis — « Dates dupliquées », « Colonne cible non numérique », « Fréquence incohérente » — remonte alors dans le résultat de l'outil.

Le tri le plus efficace, dans cet ordre :

  • Le modèle choisi est-il marqué « Installé » ? Sinon, c'est là que ça s'arrête.
  • La section Données signale-t-elle une erreur bloquante ? Si oui, c'est là.
  • Le modèle est-il distant ? Alors vérifie la clé.
  • Sinon, relance la même demande via l'agent pour lire la phrase exacte.

TimeGPT-2 : clé, quota, panne

Sans clé enregistrée, l'écran des modèles affiche « Clé API non configurée » à la place de la mention « Cloud (clé requise) », et le calcul refuse.

Avec une clé, l'appel part vers le service de prévision de Nixtla avec un délai de 60 secondes par tentative, trois tentatives au maximum, et des pauses de 2 puis 4 secondes. Les reprises sont réservées à quatre situations : 429 (trop de requêtes), 502, 503 et 504. Une clé refusée ou un quota épuisé ne sont pas retentés : l'échec est immédiat.

Toutes les issues produisent la même phrase : « Erreur du service de prédiction ». Clé invalide, quota dépassé, service en panne, réponse malformée : rien ne les distingue à l'écran. Le seul endroit qui porte l'information est le journal technique de Beaver, qui écrit le code HTTP renvoyé, sans le corps de la réponse.

Ce que tu peux faire, faute de mieux : vérifier la validité de la clé depuis l'écran des clés API — un bouton de test existe et interroge le fournisseur, voir Le coffre et les clés API — puis vérifier l'état du service chez Nixtla. Si le test de clé passe et que le calcul échoue quand même, c'est le quota ou le service.

Le détail des variantes du modèle, de leurs réglages et de ce qui sort de la machine est dans TimeGPT (cloud).

Le moteur local ne démarre pas

Entre le clic sur Lancer le forecast et le calcul, Beaver démarre un petit service Python local. Toutes ses pannes deviennent « Le calcul a échoué » à l'écran.

Les cinq pannes du service de prévision local
CausePhrase produite par le moteur
Le service précédent refuse de s'arrêter« Sidecar Forecast indisponible »
Le fichier du service est absent« Sidecar Python non installé »
Le moteur Python de cette famille n'est pas prêt« Moteur Forecast non préparé »
Le processus ne se lance pas« Impossible de lancer le sidecar Forecast »
Le service ne répond pas à temps« Sidecar Forecast: timeout au démarrage »

Le délai de démarrage est de trente secondes. Sur une machine lente ou pour un gros modèle, un premier lancement peut donc échouer alors que rien n'est cassé — réessayer est une action utile ici, contrairement à la plupart des autres échecs de cette page.

Note Un modèle installé calcule sans Internet. Le service de prévision est démarré en mode hors ligne, n'écoute que ta machine sur un port libre choisi au lancement, et il est protégé par un jeton tiré au hasard à chaque démarrage. Il ne peut rien télécharger pendant un calcul — ce qui explique aussi qu'une installation incomplète échoue au lieu de se réparer toute seule. Seule l'installation a besoin du réseau.

« Le stockage Forecast est plein »

C'est le seul message précis que le panneau sait afficher : « Le stockage Forecast est plein. Supprime d'anciennes analyses puis réessaie. » Le mécanisme réel est plus subtil que la phrase :

  • la limite est de 500 analyses au total ;
  • une fois cette limite atteinte, Beaver supprime automatiquement la plus ancienne analyse du même espace de travail et enregistre la nouvelle ;
  • le message n'apparaît que si l'espace de travail courant ne contient aucune analyse à supprimer — c'est-à-dire quand les 500 analyses appartiennent toutes à d'autres projets ou conversations.
Attention Le conseil du message ne s'applique pas là où il s'affiche. Supprimer d'anciennes analyses est bien la bonne action, mais il faut les supprimer dans les autres espaces de travail — pas dans celui où le message apparaît, puisque celui-ci est justement vide de toute analyse.

Une seconde limite existe, séparée : une analyse individuelle ne peut pas dépasser 64 Mo une fois enregistrée, sans quoi elle est refusée avec « Analyse Forecast trop volumineuse ». Elle se rencontre sur des prévisions à très nombreuses séries.

Ce qui n'a pas de solution

Sans l'adoucir : dans ces cas, aucune issue n'est prévue.

  • Distinguer une clé TimeGPT refusée d'un quota dépassé. Le message est le même et rien dans l'interface ne les sépare.
  • Savoir quelle anomalie de données bloque, depuis l'écran. Le compteur donne le nombre, jamais le nom. Le détour par l'agent est le seul chemin.
  • Savoir pourquoi une installation a échoué. Un seul code d'échec pour une quinzaine de causes.
  • Reprendre une installation interrompue. Tout est supprimé et retéléchargé.
  • Faire tourner un modèle local sans Python 3.12. Aucun repli, aucun réglage, aucun moteur intégré de secours.
  • Utiliser un miroir de paquets interne. Les adresses de huggingface.co et de pypi.org ne sont pas paramétrables.
  • Installer un modèle sur une machine sans Internet. Les poids et les bibliothèques sont téléchargés à l'installation ; seule l'exécution, ensuite, fonctionne hors ligne.
