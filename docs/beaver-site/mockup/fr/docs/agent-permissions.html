Modes de permission

Ce que l'agent peut faire sans te demander, ce qui déclenche une confirmation, et comment tu changes ça. C'est la page à lire en entier si tu tiens à savoir exactement où passe la frontière.

Attention À l'installation, Beaver est en Accès complet : l'agent exécute ses outils sans jamais demander. Passe en Demander l'autorisation si tu préfères valider chaque action sensible.

Les trois modes

Les modes proposés dans une conversation
ModeComportement
Accès completL'agent exécute ses outils sans jamais demander
Demander l'autorisationLes actions sensibles déclenchent une confirmation
ChatbotDeux outils seulement : recherche web et lecture d'une page

Accès complet est aussi la valeur de repli. Fichier de réglages absent, illisible ou portant une valeur inconnue : le mode retenu est Accès complet.

Ce que le mode Chatbot fait exactement

Le mode Chatbot n'est pas « aucun outil ». L'agent y garde web_search et web_fetch : chercher sur le web, et lire une page. Autrement dit, il ne peut ni lire ni écrire sur ta machine, mais il reste capable d'aller chercher une information en ligne.

La restriction tient sur deux barrières simultanées. Le catalogue envoyé au modèle est réduit à ces deux outils avant l'envoi, pour les fournisseurs distants comme pour les modèles locaux : le modèle ignore que les autres existent. Et si un modèle invente malgré tout un nom d'outil, l'appel est refusé à l'exécution.

Chatbot n'est pas « sans outil » En mode Chatbot, l'agent garde la recherche web et la lecture d'une page. Il ne reçoit pas non plus tes instructions permanentes : AGENTS.md et les fichiers de personnalité ne sont pas injectés. Une consigne qui semble ignorée dans ce mode l'est réellement.

Ce qui déclenche une demande

En mode Demander l'autorisation, douze outils déclenchent systématiquement une confirmation : write_file, edit_file, web_fetch, write_spreadsheet, write_document, create_branch, checkout_branch, apply_subagent_changes, manage_automation, forecast_data_audit, forecast_run, forecast_backtest.

Quatre outils déclenchent une confirmation sous condition.

Les outils conditionnels
OutilCondition
bashLa commande n'est pas reconnue comme sûre
bash_controlDes caractères sont envoyés au processus
transform_imageAu moins une opération est demandée
search_mcp_toolsLe mode est l'appel d'un outil — la simple recherche d'outils ne demande rien

Tous les autres outils natifs passent sans confirmation, y compris en mode Demander l'autorisation : lire un fichier, lister un dossier, chercher par nom ou par contenu, chercher sur le web. C'est un choix de conception : demander confirmation pour chaque lecture de fichier rendrait le mode inutilisable, et tu finirais par tout approuver sans lire.

Les outils fournis par une extension

Ils échappent aux deux listes ci-dessus. Leur besoin de confirmation dépend de l'effet déclaré par l'extension pour cet outil.

Confirmation selon l'effet déclaré
Effet déclaréConfirmationMémorisable pour la session

Seule la lecture seule passe sans rien demander ; tout le reste est confirmé.

Les commandes shell : la règle particulière

Une commande bash passe sans confirmation si elle satisfait les trois conditions à la fois : elle ne touche à aucune donnée sensible, elle ne contient aucun opérateur de contrôle, et elle correspond à l'un des motifs reconnus comme sûrs.

Les opérateurs qui disqualifient une commande — leur seule présence suffit, quinze contrôles : ; && || | ` $( <( >( << > < & $', le retour à la ligne et le retour chariot.

Autrement dit : ls passe, ls | grep foo ne passe pas. La raison est solide — un opérateur permet d'enchaîner n'importe quelle commande derrière une commande anodine.

Les motifs reconnus comme sûrs couvrent une vingtaine de familles de commandes, toutes en lecture ou en vérification.

Les familles de commandes qui passent sans confirmation
CatégorieCommandes
Lecture de fichiersls, cat, head, tail, wc, file, stat
Recherchegrep, find, tree
Systèmepwd, echo, which, du, df
Git en lecturegit status, git log, git diff, git show, git remote, git tag, git branch seul
Vérification de projetcargo check, cargo test, cargo clippy, cargo build, npx tsc, npm run, npm test

Toute autre commande déclenche une confirmation. Un cas mérite d'être signalé : git branch seul est sûr, git branch -d ne l'est pas. C'est le seul motif de la liste qui refuse toute option ; les autres acceptent des arguments après le nom de la commande.

Note En mode Demander l'autorisation, une commande de lecture reconnue comme sûre — ls, cat, git status — s'exécute sans confirmation. Dès qu'une commande contient un enchaînement, une redirection ou un chemin sensible, la confirmation est demandée.

Les données sensibles

Une commande qui mentionne un chemin sensible est toujours soumise à confirmation, même si elle correspond à un motif sûr. Un cat ~/.ssh/id_rsa ne passe pas.

Seize marqueurs sont surveillés : .env, .ssh/, /.ssh, id_rsa, id_ed25519, id_ecdsa, id_dsa, .npmrc, .pypirc, .netrc, .aws/credentials, .config/gcloud, .kube/config, credentials, login.keychain, keychain-db.

Quatre fichiers de l'application sont également protégés : config.json, secrets.enc, agent-settings.json, configured-providers.json.

Un raffinement évite les fausses alertes : le contenu des blocs de texte multiligne est retiré avant l'analyse. Écrire un .gitignore qui mentionne .env ne déclenche rien ; seul un vrai chemin passé en argument compte.

Les trois réponses possibles

Répondre à une demande de confirmation
RéponseEffet
AutoriserL'action s'exécute, une fois
Autoriser pour la sessionL'action s'exécute, et l'outil ne redemande plus — sous conditions
RefuserL'action n'est pas exécutée

« Autoriser pour la session » et ses exceptions

Trois outils ne sont jamais mémorisés, quoi que tu répondes : bash, bash_control et search_mcp_tools. Chaque appel redemande. La raison est bonne : ces trois outils peuvent faire n'importe quoi selon leurs arguments, et autoriser bash une fois pour la session reviendrait à passer en Accès complet sans le savoir.

Pour les autres outils, l'autorisation est mémorisée avec des bornes.

Bornes de la mémorisation
BorneValeur
Durée de validité1 heure
Sessions mémorisées64 au maximum
Outils mémorisés par session16 au maximum

Les autorisations expirées sont purgées automatiquement.

Attention L'option « autoriser pour la session » ne s'applique ni aux commandes shell, ni aux appels d'outils externes. Ces actions redemandent à chaque fois, parce qu'une même commande peut faire n'importe quoi selon ses arguments.

Ce qui se passe en cas de doute

Le principe est le refus par défaut. Trois situations :

  • la conversation est annulée pendant qu'une demande est en attente : refus ;
  • plus de 64 demandes attendent en même temps : refus automatique ;
  • une réponse arrive pour une demande inconnue ou périmée : elle est ignorée et journalisée.

Chaque décision est écrite dans logs/permission-diagnostics.jsonl, avec rotation à 2 Mo.

Les sous-agents ne demandent pas

Sécurité Les sessions déléguées à des sous-agents s'exécutent sans confirmation, même si ta conversation est en Demander l'autorisation. Le contrôle se fait en amont, au moment de décider quoi déléguer, et en aval, en inspectant leurs changements avant de les appliquer. Voir Sous-agents.

Changer de mode

  • Le mode se change depuis la conversation, à tout moment, via un sélecteur dédié.
  • Les touches 1, 2 et 3 sélectionnent directement un mode quand le sélecteur est ouvert.
  • Un mode par défaut se définit dans les réglages.
  • Le mode est propre à chaque conversation.
