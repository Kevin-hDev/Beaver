External connectors

A connector gives the agent access to an outside service: reading an internal documentation page, creating a ticket, browsing a repository, searching a knowledge base. It rests on a standard protocol, which saves Beaver from writing service-specific code. On the agent side, everything goes through a single two-step tool — search, then call.

The catalog is closed

This is the most important decision on this page. Beaver does not allow adding an arbitrary connector. Only connectors from an established list can be configured, and for those that run locally, the exact command is frozen in the application — argument by argument, version by version. Not one character can be changed.

Security The catalog is closed, and that is deliberate. A local connector is third-party code that runs with your rights and receives your access tokens. Allowing any of them to be installed would amount to allowing anything to be run. Most comparable tools leave that door open; Beaver closes it. What it costs: if the connector you need is not in the list, you cannot add it — you have to go through the terminal, or wait for it to be integrated.

The available connectors

Thirteen services are reached remotely, over a secure address: Gmail for mail, Google Drive for files, Google Calendar for the calendar, Notion as a knowledge base, Slack for team messaging, Linear for issue tracking, GitHub for code repositories, Figma for interface design, Canva for graphic creation, Lucid for diagrams, Sentry for error tracking, Vercel for hosting and deployment, and Apify for web data extraction.

Five services run on your machine: Context7 for up-to-date library documentation, Hugging Face for models and datasets, Product Hunt for product watch, Reddit for searching discussions, and iMessage for messages, on macOS only.

This list matches Beaver 1.2.2; your application's connector screen is authoritative.

Adding a connector

The path is Settings › Integrations › Connectors, and the flow depends on the type. For a remote service, Beaver already knows the address: all that remains is to authenticate, usually by account — see Connector authentication. For a local service, the command is already known: all that remains is to supply the service's access key when it asks for one.

A malformed connector is refused when saved: invalid identifier, unrecognized address, non-compliant command, or neither of the two supplied. The limit is 32 configured connectors.

Enabling per conversation

Each connector carries an activation switch for conversations, independent of its configuration. The distinction is worth understanding: a connector can be configured and authenticated, but switched off — the agent then does not see it at all.

That is useful: you keep several connectors ready and only expose the ones relevant to the work at hand. Every active connector adds tools the agent has to consider, and that is not free.

What is locked down

Hardening is this module's strong point.

For remote services, the address must match exactly the one expected for that connector — same host, same path. Encryption is mandatory: an insecure address is refused. No custom port, no parameters in the address. And one connector cannot borrow another's address: the match is checked pair by pair.

For local services, only three programs are allowed — the Node, Python and Deno package launchers. No other, and above all no command interpreter. The command must match the catalog's exactly, including the package version number: a different version is refused. Every argument is validated against a pattern — no semicolon, no vertical bar, no backtick, no command substitution, no space — so that attempts to chain a second command are rejected. The "allow everything" permission is refused for all of them, and the iMessage connector is subject to a reinforced check: its execution permissions are frozen to the expected list, and adding write permission is refused.

At runtime, the program is launched without going through a command interpreter, with its arguments in a list. Tokens are passed through environment variables, whose names are validated, and handled in protected memory.

Security Versions are pinned, and no command interpreter is ever used. A local connector always installs at the version Beaver expects, which prevents a compromised update from installing silently. And because programs are launched directly with their arguments in a list, no string is ever interpreted as a command.

Process management

Local connectors run as separate programs, in a pool Beaver manages. Eight processes at most: beyond that, the connector unused for the longest is stopped. A process idle for 10 minutes is stopped, then restarted as needed — that is why a first request after a pause is slower. All of them are stopped along with their process tree when Beaver closes. Responses are bounded: 128 tools per connector, description capped at 250 characters, tool name at 64.
