Les connecteurs externes

Un connecteur donne à l'agent accès à un service extérieur : lire une page de documentation interne, créer un ticket, consulter un dépôt, chercher dans une base de connaissances. Il repose sur un protocole standard, ce qui évite à Beaver d'écrire du code spécifique par service. Côté agent, tout passe par un seul outil à deux temps — chercher, puis appeler.

Le catalogue est fermé

C'est la décision la plus importante de cette page. Beaver ne permet pas d'ajouter un connecteur arbitraire. Seuls les connecteurs d'une liste établie peuvent être configurés, et pour ceux qui s'exécutent localement, la commande exacte est figée dans l'application — argument par argument, version par version. Impossible d'en changer un caractère.

Sécurité Le catalogue est fermé, et c'est délibéré. Un connecteur local est du code tiers qui tourne avec tes droits et reçoit tes jetons d'accès. Permettre d'en installer n'importe lequel reviendrait à permettre l'exécution de n'importe quoi. La plupart des outils comparables laissent cette porte ouverte ; Beaver la ferme. Ce que ça coûte : si le connecteur dont tu as besoin n'est pas dans la liste, tu ne peux pas l'ajouter — il faut passer par le terminal, ou attendre qu'il soit intégré.

Les connecteurs disponibles

Treize services sont joints à distance, par une adresse sécurisée : Gmail pour le courrier, Google Drive pour les fichiers, Google Agenda pour le calendrier, Notion comme base de connaissances, Slack pour la messagerie d'équipe, Linear pour le suivi de tickets, GitHub pour les dépôts de code, Figma pour la conception d'interfaces, Canva pour la création graphique, Lucid pour les diagrammes, Sentry pour le suivi d'erreurs, Vercel pour l'hébergement et le déploiement, et Apify pour l'extraction de données web.

Cinq services s'exécutent sur ta machine : Context7 pour la documentation de bibliothèques à jour, Hugging Face pour les modèles et jeux de données, Product Hunt pour la veille produit, Reddit pour la recherche de discussions, et iMessage pour les messages, sur macOS uniquement.

Cette liste correspond à Beaver 1.2.2 ; l'écran des connecteurs de ton application fait foi.

Ajouter un connecteur

Le chemin est Réglages › Intégrations › Connecteurs, et le parcours dépend du type. Pour un service distant, l'adresse est déjà connue de Beaver : il reste à s'authentifier, le plus souvent par compte — voir Authentification des connecteurs. Pour un service local, la commande est déjà connue : il reste à fournir la clé d'accès du service quand il en demande une.

Un connecteur mal formé est refusé à l'enregistrement : identifiant invalide, adresse non reconnue, commande non conforme, ou aucune des deux fournies. La limite est de 32 connecteurs configurés.

Activer par conversation

Chaque connecteur porte un interrupteur d'activation dans les conversations, indépendant de sa configuration. La distinction vaut d'être comprise : un connecteur peut être configuré et authentifié, mais éteint — l'agent ne le voit alors pas du tout.

C'est utile : tu gardes plusieurs connecteurs prêts et tu n'exposes que ceux qui servent au travail en cours. Chaque connecteur actif ajoute des outils que l'agent doit considérer, et cela n'est pas gratuit.

Ce qui est verrouillé

Le durcissement est le point fort de ce module.

Pour les services distants, l'adresse doit correspondre exactement à celle attendue pour ce connecteur — même hôte, même chemin. Le chiffrement est obligatoire : une adresse non sécurisée est refusée. Ni port personnalisé, ni paramètres dans l'adresse. Et un connecteur ne peut pas emprunter l'adresse d'un autre : la correspondance est vérifiée par paire.

Pour les services locaux, seuls trois programmes sont autorisés — les lanceurs de paquets Node, Python et Deno. Aucun autre, et surtout aucun interpréteur de commandes. La commande doit correspondre exactement à celle du catalogue, y compris le numéro de version du paquet : une version différente est refusée. Chaque argument est validé par motif — ni point-virgule, ni barre verticale, ni accent grave, ni substitution de commande, ni espace — si bien que les tentatives d'enchaîner une seconde commande sont rejetées. La permission « tout autoriser » est refusée pour tous, et le connecteur iMessage fait l'objet d'un contrôle renforcé : ses permissions d'exécution sont figées à la liste attendue, et ajouter la permission d'écriture est refusé.

À l'exécution, le programme est lancé sans passer par un interpréteur de commandes, avec ses arguments dans une liste. Les jetons sont transmis par variables d'environnement, dont les noms sont validés, et manipulés en mémoire protégée.

Sécurité Les versions sont épinglées, et aucun interpréteur de commandes n'est jamais utilisé. Un connecteur local s'installe toujours à la version prévue par Beaver, ce qui empêche une mise à jour compromise de s'installer silencieusement. Et parce que les programmes sont lancés directement avec leurs arguments en liste, aucune chaîne de caractères n'est interprétée comme une commande.

La gestion des processus

Les connecteurs locaux tournent comme des programmes séparés, dans une réserve gérée par Beaver. Huit processus au maximum : au-delà, le connecteur inutilisé depuis le plus longtemps est arrêté. Un processus inactif depuis 10 minutes est arrêté, puis redémarré au besoin — c'est ce qui explique qu'une première requête après une pause soit plus lente. Tous sont arrêtés avec leur arbre de processus à la fermeture de Beaver. Les réponses sont bornées : 128 outils par connecteur, description limitée à 250 caractères, nom d'outil à 64.
