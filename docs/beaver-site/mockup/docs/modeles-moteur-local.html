The engine that runs your models

Local models need a runtime engine: Beaver ships its own, and knows how to recognize the one you may already have. This page explains what it installs, what it reuses, what it configures, and what it refuses to do when something is off.

What Beaver installs

Beaver installs its own Ollama engine in its data folder, under ~/.local/share/cl-go-dash/ollama-bundle/ — the same path on all three systems. The download never happens on its own: it is offered at first launch, or triggered whenever you want from Settings › Ollama. As long as you do not ask for it, nothing is installed and Beaver sticks to remote models.

  • No system installation is needed. You do not have to install Ollama separately, nor even know it exists.
  • Beaver's engine does not overwrite an existing installation. The engine program lives in Beaver's folder, with settings of its own. Its models, on the other hand, are indeed Ollama's.

The download can only come from a single address: Ollama's official releases on github.com, over https only. Any other origin — another domain, another port, an address carrying credentials or parameters — is refused before the connection is even opened. The archive is then verified by its SHA-256 fingerprint; if it does not match, it is rejected and nothing is installed.

Once installed, the engine leaves a receipt in its folder: the installed version and the fingerprint of its executable. At every start, Beaver recomputes that fingerprint and compares it with the receipt. If the two do not match, it refuses to launch the engine and switches to recovery rather than running a binary it knows nothing about.

Note You never have to install Ollama yourself: Beaver fetches and manages its own engine, with no manual step and no terminal. But it only does so if you ask — at first launch, or later from Settings › Ollama.

If you already have Ollama

Before launching anything, Beaver checks whether an Ollama engine already answers on the usual port — 127.0.0.1:11434. If so, it adopts it and does not start a second engine.

The check happens in two stages. At detection time, Beaver merely opens a connection on that port, with a 250 millisecond timeout: whatever answers is treated as an existing engine. Then the monitoring really verifies: every 2 seconds, Beaver queries the engine's version endpoint. If it does not answer, the engine is marked unavailable and the feature disappears from the application rather than failing later.

In practice:

  • Models already downloaded by the official Ollama application are immediately available in Beaver. Nothing to download again.
  • There are never two engines in memory — so no model loaded twice, and no video memory taken up twice.
  • Beaver's settings do not apply to an engine it did not start: the existing engine keeps its own configuration. If you set hardware acceleration or multi-model in Beaver, you will see no effect.
  • Some operations are reserved for an owned engine: creating a custom model, for instance, is refused when Beaver did not start the engine itself.
Warning If you already have Ollama, Beaver reuses it. Your models are immediately available and there are never two engines in memory — but in exchange, Beaver's engine settings have no effect on that installation.

The port chosen

Beaver never forces itself onto Ollama's usual port.

  • The port of the engine Beaver starts is assigned by the operating system. Beaver asks for "a free port, any of them", keeps the one it is given, and retries at most 3 times if the port obtained does not fit. There is no fixed port range.
  • Port 11434 is only used for detecting an engine that is already running. The engine Beaver starts does not use it.

The engine listens only on 127.0.0.1. It cannot be reached from any other device on the network.

The settings applied to the engine

When Beaver starts its own engine, it imposes a configuration on it. It comes down to five values, and nothing else.

Three of those lines deserve an explanation. Ollama's remote models are disabled: Ollama offers to run certain models on its own servers, and Beaver cuts that possibility off — when a conversation uses a local model, it really is local. A single model is loaded in memory at a time, unless you enable multi-model in the advanced settings; on an ordinary machine, two loaded models saturate video memory. And CPU-only mode is forced explicitly: by default Beaver lets the engine detect the hardware on its own.

How long a model stays in memory after use is also configurable, but differently: it is not an instruction given to the engine at launch, it is a value sent with every request. It defaults to 5 minutes. Two values are special:

  • Indefinitely — the model never leaves memory. It answers the next question instantly, at the cost of memory taken up permanently.
  • No persistence — the model is unloaded, and Beaver additionally asks the engine explicitly to free the memory at the end of the conversation turn.

Because that value travels with each request rather than with the engine, it is the only engine setting that also works when Beaver reuses a system engine.

Security A local model is truly local. Beaver disables the remote models Ollama offers, and the engine listens only on 127.0.0.1, on a port the system assigns to it. Nothing leaves your machine, and no other device can connect to it.

Where the models live

The models folder is Ollama's, not a folder of Beaver's own:

  • if the OLLAMA_MODELS environment variable is set on your machine, Beaver honors it;
  • otherwise, it uses Ollama's usual location, ~/.ollama/models.

In other words, models are shared with the official Ollama application, whether Beaver starts its own engine or reuses the system one. Nothing is duplicated — and a deletion counts on both sides.

Beaver refuses to start if that folder overlaps one of its own working folders: without that guardrail, an engine update could erase models.

Context size adapts to the hardware

Beaver measures the available memory and derives the context size of local models from it.

The context granted to local models according to the memory detected
Memory detectedContext granted
24 GB or more32,768 tokens
12 GB to 24 GB24,576 tokens
Less than 12 GB, or undetectable8,192 tokens

When memory cannot be measured, Beaver takes the lowest value: a modest context that works beats an ambitious one that makes loading fail.

On Apple silicon Macs, the memory measured is the unified memory — the memory the processor and the graphics part share. A 16 GB Mac therefore falls into the middle tier. On an Intel Mac, memory is not measured at all: the context drops to the 8,192 token tier. The measurement is refreshed every 10 seconds in the background, which also feeds the application's memory indicator.

Startup and recovery after a crash

The order of operations explains why Beaver sometimes refuses to start the engine instead of doing it badly:

  • A recovery pass first. If an engine installation or update was interrupted, it is resumed or rolled back before anything else. Until it completes, the engine stays blocked and Beaver says so rather than launching a half-installed engine.
  • The process receipt is read back. If an engine started by a previous session is still running, it is stopped and reclaimed; if it is gone, the receipt is deleted.
  • Detection of an existing engine.
  • The launch, if no engine was found.
  • The verification. Beaver grants the engine 10 seconds to start listening and return the expected version. If either fails, the process is stopped and startup is declared failed — it is never published as available "just in case".

The process receipt is the mechanism that stops orphaned engines from piling up. It is written before the engine is allowed to actually start: the process is created then held, blocked, until Beaver has recorded its receipt on disk. So there is no moment at which an engine runs without Beaver being able to recognize it.

The receipt holds enough to identify it unambiguously: process identifier, exact start time, system scope, and the fingerprint of the installed engine. All four must match for Beaver to stop a process. A process identifier gets reused by the system: without that check, Beaver would risk killing an unrelated program that had inherited the same number.

Shutdown, cleanup and logs

  • When Beaver closes, the engine it started is stopped along with its whole process tree — process group on macOS and Linux, system job object on Windows.
  • A reused engine is never stopped: Beaver does not kill a process it did not start.
  • Shutdown reserves 3 seconds for that operation within its global budget. An engine that does not hand back control in time does not prevent the application from closing.
  • On Linux, the started engine additionally receives a kernel instruction: if Beaver disappears abruptly, the system kills the engine with it.

The engine writes no log file. Its output is redirected nowhere. What remains available to understand a failure is Beaver's own logs: every engine step is recorded there with a named error code — engine missing, recovery required, storage unavailable, start failed, stop failed, models folder conflict. That code is what to note down for a bug report.
