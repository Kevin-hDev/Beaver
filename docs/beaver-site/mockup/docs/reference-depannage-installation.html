Quand ça coince

Cette page est rangée par symptôme, pas par système : cherche la phrase que tu as sous les yeux. Elle ne réexplique aucune procédure d'installation — les pages Installation macOS, Installation Windows et Installation Linux font autorité là-dessus. Certains échecs listés ici n'ont pas de solution ; c'est dit franchement à chaque fois.

Les trois causes qui expliquent la moitié des cas

  • Beaver n'est signé par aucun certificat de signature de code. C'est la cause de tout ce que macOS et Windows affichent comme mise en garde.
  • Une seule architecture est distribuée par système : aarch64-apple-darwin, x86_64-unknown-linux-gnu, x86_64-pc-windows-msvc. Un Mac Intel, un PC ARM, un Linux ARM ou un Linux hors famille Debian n'ont pas de fichier à installer.
  • Le premier lancement n'a besoin d'Internet que si tu acceptes d'installer le moteur Ollama — le téléchargement est proposé, jamais imposé, et se rattrape depuis Réglages › Ollama. Tout le reste de l'installation est local.
Attention Aucune signature, et c'est permanent. macOS et Windows afficheront une mise en garde à la première ouverture. Ce n'est pas un incident : c'est le cas de tous les logiciels libres distribués sans certificat, qui est payant et nominatif. Les sections ci-dessous expliquent quoi cliquer.

macOS — « Beaver ne peut pas être ouvert »

Le symptôme. Au double-clic, macOS refuse d'ouvrir l'application et parle d'un développeur non identifié, ou d'une application dont l'origine ne peut pas être vérifiée.

La cause. L'application porte une signature ad hoc et n'est pas notarisée. Quand le fichier .dmg est téléchargé par un navigateur, macOS lui pose son marquage de quarantaine, et Gatekeeper bloque.

Ce qu'il faut faire, dans cet ordre :

  • réinstaller par le script, qui est la voie recommandée : il télécharge par curl, ce qui ne pose pas le marquage de quarantaine. La commande complète est sur Installation macOS ;
  • ou débloquer l'application déjà installée : clic droit sur Beaver dans le dossier Applications, puis « Ouvrir », et confirmer dans la boîte de dialogue ;
  • ou passer par les Réglages Système : Confidentialité et sécurité, faire défiler jusqu'au message concernant Beaver, puis « Ouvrir quand même ».

Windows — « Windows a protégé votre ordinateur »

Le symptôme. Au lancement de l'installeur Beaver_X.Y.Z_x64-setup.exe, Windows affiche un écran bleu et ne propose que « Ne pas exécuter ».

La cause. La même que sur macOS : aucun certificat de signature de code. SmartScreen se déclenche sur un exécutable non signé qu'il ne connaît pas encore.

Ce qu'il faut faire. Cliquer sur « Informations complémentaires » — le lien est discret, sous le texte —, puis sur « Exécuter quand même ». Cet avertissement est permanent, pas un incident.

Windows — le script s'arrête sans explication

Le symptôme. Le script PowerShell affiche une seule ligne, « ERREUR Installation impossible. », et s'arrête. C'est volontairement le seul message d'erreur du script : tous ses contrôles échouent sur la même sortie générique, et il ne dit jamais lequel a échoué.

Les contrôles qui peuvent produire ce message : une architecture différente de AMD64 ; un dossier d'installation refusé — il doit commencer par une lettre de lecteur suivie de :\, faire au plus 1024 caractères, ne contenir ni * ? < > | ", ni caractère de contrôle, ni segment .. ; une empreinte ou une taille non conformes au manifeste de la release ; ou un installeur silencieux qui retourne un code d'erreur.

Ce qu'il faut faire, dans cet ordre : relancer la commande une fois, car un téléchargement interrompu produit le même message et réussit souvent au deuxième essai ; réessayer avec le dossier proposé par défaut, %LOCALAPPDATA%\Beaver, plutôt qu'un dossier personnalisé — c'est la cause la plus fréquente et la plus silencieuse ; si l'échec persiste, installer par l'installeur téléchargé depuis la page des releases, qui affiche ses propres erreurs.

Note L'installeur Windows est configuré en mode « utilisateur courant ». Il n'a pas besoin de droits administrateur, et il installe pour le compte Windows en cours seulement.

Linux — ma distribution n'est pas prise en charge

Le symptôme. Le script affiche « Système non pris en charge. », ou aucun paquet ne correspond à ta distribution sur la page des releases.

La cause, sans ambiguïté. Beaver ne distribue qu'un paquet Debian pour l'architecture x64. Le script n'accepte que Linux:x86_64 et Linux:amd64, ne construit que le nom de fichier _amd64.deb, vérifie le paquet avec dpkg-deb et l'installe avec apt-get. Aucun autre gestionnaire de paquets n'est appelé.

Ce qu'il faut faire. Il n'y a aucune solution sur Fedora, RHEL, Arch, openSUSE ou toute distribution hors famille Debian : il n'existe pas de paquet pour elles. Les deux options honnêtes sont d'utiliser une distribution de la famille Debian — Debian, Ubuntu et dérivées — ou d'attendre et de suivre le dépôt.

Linux — dépendances et paquet refusé

« Paquet d'installation invalide. » Avant d'installer, le script contrôle six métadonnées du paquet : Package vaut beaver, Architecture vaut amd64, Version est identique à celle annoncée par la release, et Provides, Conflicts, Replaces valent tous cl-go. Un seul écart fait échouer l'installation. Ce n'est pas un problème de machine : le fichier publié ne correspond pas à ce que le script attend. Signale-le au projet en indiquant la version, et n'installe pas le paquet à la main pour contourner.

L'application ne démarre pas après un dpkg -i. dpkg n'installe pas les dépendances manquantes et laisse un paquet configuré à moitié. Le script, lui, passe par apt-get, qui les résout. Pour réparer :

$ sudo apt install -f

Ou, mieux, réinstaller proprement en remplaçant X.Y.Z par le numéro de version du fichier téléchargé :

$ sudo apt install ./Beaver_X.Y.Z_amd64.deb

Installation réussie, mais rien ne se lance. Le binaire ne s'appelle pas beaver : taper beaver dans un terminal n'obtient rien. Lance depuis le menu des applications, ou tape cl-go-dash.

Dans tous ces cas, la marche à suivre est la même : cliquer de nouveau sur « Télécharger Ollama » — un échec réseau ne laisse aucun fichier partiel derrière lui —, ou cliquer sur « Passer » pour entrer dans l'application tout de suite. Beaver reste pleinement utilisable avec des modèles distants ; seul le moteur local manque. Tu reprends plus tard dans Réglages › Ollama : tant que le moteur n'est pas installé, cet onglet affiche exactement le même écran.

Note Passer n'est pas définitif — mais ça ne revient pas tout seul. Si tu passes l'installation du moteur local, l'écran ne réapparaîtra pas au démarrage suivant. Tu le retrouves à tout moment dans Réglages › Ollama, et nulle part ailleurs.

Le téléchargement d'Ollama a été interrompu

Le symptôme. L'ordinateur s'est éteint, l'application a été fermée, ou tu as annulé pendant la barre de progression. Au lancement suivant, Réglages › Ollama affiche soit une progression, soit un message d'erreur avec un bouton « Réessayer ».

Ce qui se passe. L'installation d'Ollama est une opération en plusieurs phases — préparation, téléchargement, vérification, installation, validation, finalisation, démarrage. Chaque phase travaille dans un dossier distinct à côté de l'installation active, jamais dessus. L'installation utilisable n'est remplacée qu'à la toute fin.

Ce qu'il faut faire. Redémarrer Beaver : une reprise s'exécute automatiquement au démarrage, avant toute tentative de lancer le moteur, et dans la plupart des cas il n'y a rien d'autre à faire. Si l'écran affiche un bouton « Réessayer », clique dessus. Si le message est « La réparation d'Ollama est temporairement impossible », attends quelques secondes : une autre opération occupe le dossier.

C'est rassurant et c'est vrai : une interruption ne laisse jamais une installation à moitié remplacée. Le nouvel état est construit à côté de l'ancien et ne prend sa place qu'une fois complet ; les restes d'une tentative abandonnée sont mis au rebut puis supprimés à la reprise.

La machine n'a pas de réseau

Le symptôme. L'installation de l'application réussit, mais l'écran « Configuration d'Ollama » échoue immédiatement avec « Le téléchargement d'Ollama a échoué. Vérifie la connexion puis réessaie. »

La cause. Ollama n'est pas embarqué dans l'application. Beaver interroge la dernière release publiée du projet Ollama sur github.com, puis lit son fichier d'empreintes et la taille de chaque archive. Sans réseau, ces requêtes échouent.

Ce qui fonctionne quand même : l'application s'installe et démarre, le dossier de données et toute sa structure sont créés localement, et le moteur de prévision local est installé depuis les fichiers livrés avec l'application, sans réseau. Seule l'étape Ollama échoue.

Ce qu'il faut faire. Cliquer sur « Passer » et utiliser l'application, puis reprendre dans Réglages › Ollama une fois connecté. Sur un réseau d'entreprise ou derrière un portail captif, vérifie que github.com est joignable : Beaver n'accepte que des adresses https sur github.com, sans port, sans identifiant, sans paramètre — un proxy qui réécrit l'adresse ou renvoie une page d'authentification fait échouer l'étape.

Si un moteur Ollama est déjà installé séparément sur ta machine et qu'il tourne, Beaver le réutilise et ne télécharge rien : voir Premier lancement.

« Erreur d'initialisation des données »

Le symptôme. L'application ne démarre pas, ou s'arrête au tout début du démarrage, avec ce message.

La cause. Beaver crée son dossier de données et sa structure avant l'affichage de la fenêtre. Cette étape échoue si le dossier ne peut pas être créé, si les droits ne peuvent pas être posés, ou si l'écriture d'un fichier échoue.

Le dossier de données est le même sur les trois systèmes : ~/.local/share/cl-go-dash/, soit C:\Users\<ton compte>\.local\share\cl-go-dash\ sous Windows. Ce n'est pas %APPDATA% — un utilisateur Windows cherchera au mauvais endroit. Beaver y pose des droits stricts, dossiers en 0700 et fichiers en 0600 sur macOS et Linux, liste de contrôle d'accès restreinte sur Windows, et les répare à chaque démarrage.

Ce qu'il faut faire, dans cet ordre : vérifier l'espace libre du disque de démarrage, car un disque plein produit exactement ce message ; vérifier que ton dossier personnel est accessible en écriture, avec ls -ld ~/.local/share/cl-go-dash sur macOS et Linux — le dossier doit appartenir à ton compte ; si le dossier de données a été copié depuis une autre machine ou restauré depuis une sauvegarde, ses propriétaires peuvent être faux :

$ sudo chown -R "$USER" ~/.local/share/cl-go-dash

Un dernier cas : sur un dossier personnel monté en réseau ou sur un volume chiffré, les droits 0700 et 0600 ne peuvent pas toujours être posés. Il n'y a pas de contournement raisonnable — c'est un cas à signaler au projet.

Attention L'espace disque n'est pas vérifié. Beaver ne contrôle pas l'espace libre avant de télécharger le moteur local. Sur un disque presque plein, l'échec se présente comme un problème de téléchargement ou d'extraction, pas comme un manque de place. Vérifie ton espace libre avant de relancer.

Le GPU n'est pas détecté

Le symptôme. L'installation réussit, mais les modèles locaux sont très lents, et Beaver ne prévient jamais qu'un modèle est trop gros pour la carte graphique.

Deux mécanismes distincts, à ne pas confondre. La détection du constructeur sert uniquement, sous Linux, à choisir l'archive à télécharger : Beaver lit les identifiants constructeur dans /sys/class/drm/*/device/vendor. Une carte AMD reconnue déclenche le téléchargement d'une archive supplémentaire ; si la détection échoue, seule l'archive de base est téléchargée et l'accélération AMD n'est pas installée. Sous macOS la détection lit la marque du processeur, sous Windows elle interroge la liste des cartes vidéo.

La mesure de la mémoire graphique, elle, décide de la taille de contexte par défaut, en trois paliers : 32 768 jetons au-dessus de 24 000 Mo, 24 576 jetons au-dessus de 12 000 Mo, 8 192 jetons en dessous — et 8 192 également quand la mesure échoue. Une mémoire non mesurée ne se voit donc pas : elle se traduit par un contexte réduit au minimum. Deuxième conséquence, plus discrète : l'avertissement « ce modèle ne tient pas dans ta mémoire » ne s'affiche jamais quand la mesure a échoué, parce que le contrôle répond alors que ça tient.

Ce qu'il faut faire. Sous Linux avec une carte AMD, vérifier que la carte est vue par le système avec ls /sys/class/drm/ : si rien n'y correspond, le pilote graphique n'est pas chargé, et c'est un problème de système, pas de Beaver. Sous Windows avec une carte NVIDIA, le pilote doit être installé : c'est lui qui fournit le nom de la carte. Sous Linux avec une carte NVIDIA, il faut un pilote 531 ou supérieur ; CUDA est fourni dans l'archive Ollama. Si le contexte reste à 8 192 jetons alors que ta machine a plus de 12 Go de mémoire graphique, la mesure a échoué : ce n'est pas réglable depuis l'application, signale le problème avec le modèle exact de la carte. Voir aussi Matériel et VRAM.

Note Le moteur local n'écrit pas de journal. Contrairement à ce que suggèrent d'anciennes documentations, le moteur Ollama lancé par Beaver n'écrit aucun fichier de traces : sa sortie va vers /dev/null sur macOS et Linux. Il n'y a pas de journal du moteur à consulter en cas de lenteur.

Désinstaller, et ce qui reste après

Le dossier de données est indépendant de l'application installée. C'est voulu : c'est ce qui permet aux mises à jour de ne rien perdre. Réinstaller après une suppression partielle reprend donc tes conversations, tes réglages et tes clés tels quels.

Retirer l'application, système par système
SystèmeComment
macOSJeter Beaver du dossier d'installation choisi — /Applications par défaut
Linuxsudo apt remove beaver — le nom du paquet est beaver
WindowsParamètres › Applications, ou le désinstalleur posé dans le dossier d'installation

Ce qui reste sur le disque après cette suppression : le dossier de données ~/.local/share/cl-go-dash/ — conversations, mémoire, réglages, projets, coffre chiffré, et l'installation d'Ollama ; les modèles Ollama téléchargés, dans ~/.ollama/models, de loin le plus volumineux et en dehors du dossier de données ; les entrées du gestionnaire de secrets du système, dont la clé maîtresse du coffre sous le service cl-go-dash.

Pour tout retirer : supprime l'application, puis le dossier de données, puis ~/.ollama si tu ne t'en sers pas ailleurs — attention, ce dossier est partagé avec toute autre installation d'Ollama sur la machine —, puis les entrées du gestionnaire de secrets, en cherchant cl-go-dash dans le Trousseau d'accès sur macOS, dans le gestionnaire de mots de passe du bureau sur Linux, dans le Gestionnaire d'identification sur Windows.

Attention Tes données survivent à la désinstallation. Supprimer l'application ne supprime ni tes conversations, ni tes clés, ni tes modèles : ils vivent dans un dossier séparé. La dernière étape, celle du gestionnaire de secrets, est celle qu'on oublie — sans elle, la clé maîtresse du coffre reste dans ton trousseau. Elle ne déchiffre plus rien une fois secrets.enc supprimé, mais elle n'a plus aucune raison d'être là. La procédure complète est dans Confidentialité.
