When it gets stuck

This page is organized by symptom, not by system: look for the sentence you have in front of you. It does not re-explain any installation procedure — the macOS installation, Windows installation and Linux installation pages are the authority on that. Some of the failures listed here have no fix; that is stated plainly every time.

The three causes behind half the cases

  • Beaver is not signed by any code signing certificate. That is the cause of everything macOS and Windows display as a warning.
  • Only one architecture is distributed per system: aarch64-apple-darwin, x86_64-unknown-linux-gnu, x86_64-pc-windows-msvc. An Intel Mac, an ARM PC, an ARM Linux machine or a Linux outside the Debian family has no file to install.
  • The first launch only needs the internet if you agree to install the Ollama engine — the download is offered, never forced, and can be picked up later from Settings › Ollama. Everything else in the installation is local.
Warning No signature, and that is permanent. macOS and Windows will show a warning the first time you open the app. This is not an incident: it is the case for every piece of free software distributed without a certificate, which costs money and is issued to a named person. The sections below explain what to click.

macOS — “Beaver can't be opened”

The symptom. On double-click, macOS refuses to open the app and mentions an unidentified developer, or an app whose origin cannot be verified.

The cause. The app carries an ad hoc signature and is not notarized. When the .dmg file is downloaded by a browser, macOS attaches its quarantine flag, and Gatekeeper blocks it.

What to do, in this order:

  • reinstall using the script, which is the recommended route: it downloads through curl, which does not attach the quarantine flag. The full command is on macOS installation;
  • or unblock the app already installed: right-click Beaver in the Applications folder, then “Open”, and confirm in the dialog;
  • or go through System Settings: Privacy & Security, scroll down to the message about Beaver, then “Open Anyway”.

Windows — “Windows protected your PC”

The symptom. When you launch the Beaver_X.Y.Z_x64-setup.exe installer, Windows shows a blue screen and only offers “Don't run”.

The cause. The same as on macOS: no code signing certificate. SmartScreen triggers on an unsigned executable it does not know yet.

What to do. Click “More info” — the link is discreet, under the text — then “Run anyway”. This warning is permanent, not an incident.

Windows — the script stops without explanation

The symptom. The PowerShell script prints a single line, “ERREUR Installation impossible.”, and stops. That is deliberately the only error message in the script: all of its checks fail on the same generic output, and it never says which one failed. Like its macOS and Linux counterpart, this script speaks French only.

The checks that can produce this message: an architecture other than AMD64; a rejected installation folder — it must start with a drive letter followed by :\, be at most 1024 characters, contain none of * ? < > | ", no control character, and no .. segment; a checksum or size that does not match the release manifest; or a silent installer returning an error code.

What to do, in this order: run the command once more, because an interrupted download produces the same message and often succeeds on the second attempt; try again with the default folder, %LOCALAPPDATA%\Beaver, rather than a custom folder — that is the most frequent and most silent cause; if the failure persists, install using the installer downloaded from the releases page, which displays its own errors.

Note The Windows installer is configured in “current user” mode. It does not need administrator rights, and it installs for the current Windows account only.

Linux — my distribution is not supported

The symptom. The script prints “Système non pris en charge.”, or no package matches your distribution on the releases page.

The cause, with no ambiguity. Beaver only distributes a Debian package for the x64 architecture. The script only accepts Linux:x86_64 and Linux:amd64, only builds the _amd64.deb file name, checks the package with dpkg-deb and installs it with apt-get. No other package manager is called.

What to do. There is no fix on Fedora, RHEL, Arch, openSUSE or any distribution outside the Debian family: no package exists for them. The two honest options are to use a distribution from the Debian family — Debian, Ubuntu and derivatives — or to wait and follow the repository.

Linux — dependencies and a rejected package

“Paquet d'installation invalide.” Before installing, the script checks six metadata fields of the package: Package is beaver, Architecture is amd64, Version is identical to the one announced by the release, and Provides, Conflicts, Replaces are all cl-go. A single mismatch fails the installation. This is not a machine problem: the published file does not match what the script expects. Report it to the project with the version number, and do not install the package by hand to work around it.

The app does not start after a dpkg -i. dpkg does not install missing dependencies and leaves a half-configured package. The script, on the other hand, goes through apt-get, which resolves them. To repair:

$ sudo apt install -f

Or, better, reinstall cleanly by replacing X.Y.Z with the version number of the downloaded file:

$ sudo apt install ./Beaver_X.Y.Z_amd64.deb

Installation succeeded, but nothing launches. The binary is not called beaver: typing beaver in a terminal gets you nothing. Launch it from the applications menu, or type cl-go-dash.

In all these cases, the course of action is the same: click “Download Ollama” again — a network failure leaves no partial file behind — or click “Skip” to enter the app right away. Beaver remains fully usable with remote models; only the local engine is missing. You pick it up later in Settings › Ollama: as long as the engine is not installed, that tab shows exactly the same screen.

Note Skipping is not final — but it does not come back on its own. If you skip the local engine installation, the screen will not reappear on the next start. You find it again at any time in Settings › Ollama, and nowhere else.

The Ollama download was interrupted

The symptom. The computer shut down, the app was closed, or you cancelled during the progress bar. On the next launch, Settings › Ollama shows either progress, or an error message with a “Try again” button.

What is happening. Installing Ollama is a multi-phase operation — preparation, download, verification, installation, validation, finalisation, start. Each phase works in a separate folder next to the active installation, never on top of it. The usable installation is only replaced at the very end.

What to do. Restart Beaver: a recovery runs automatically at startup, before any attempt to launch the engine, and in most cases there is nothing else to do. If the screen shows a “Try again” button, click it. If the message is “Ollama recovery is temporarily unavailable”, wait a few seconds: another operation is using the folder.

It is reassuring and it is true: an interruption never leaves a half-replaced installation. The new state is built next to the old one and only takes its place once complete; the leftovers of an abandoned attempt are set aside and then deleted on recovery.

The machine has no network

The symptom. Installing the app succeeds, but the “Ollama Setup” screen fails immediately with “The Ollama download failed. Check the connection and try again.”

The cause. Ollama is not bundled inside the app. Beaver queries the latest published release of the Ollama project on github.com, then reads its checksum file and the size of each archive. Without a network, these requests fail.

What still works: the app installs and starts, the data folder and its whole structure are created locally, and the local forecasting engine is installed from files shipped with the app, without a network. Only the Ollama step fails.

What to do. Click “Skip” and use the app, then pick it up in Settings › Ollama once connected. On a corporate network or behind a captive portal, check that github.com is reachable: Beaver only accepts https addresses on github.com, with no port, no credentials, no parameters — a proxy that rewrites the address or returns an authentication page makes the step fail.

If an Ollama engine is already installed separately on your machine and it is running, Beaver reuses it and downloads nothing: see First launch.

“Erreur d'initialisation des données”

The symptom. The app does not start, or stops at the very beginning of startup, with this message. It is displayed in French whatever your language: it comes from a stage that runs before translations are loaded.

The cause. Beaver creates its data folder and its structure before the window appears. This step fails if the folder cannot be created, if permissions cannot be set, or if writing a file fails.

The data folder is the same on all three systems: ~/.local/share/cl-go-dash/, that is C:\Users\<your account>\.local\share\cl-go-dash\ on Windows. It is not %APPDATA% — a Windows user will look in the wrong place. Beaver sets strict permissions there, folders at 0700 and files at 0600 on macOS and Linux, a restricted access control list on Windows, and repairs them at every startup.

What to do, in this order: check the free space on the startup disk, because a full disk produces exactly this message; check that your home folder is writable, with ls -ld ~/.local/share/cl-go-dash on macOS and Linux — the folder must belong to your account; if the data folder was copied from another machine or restored from a backup, its ownership may be wrong:

$ sudo chown -R "$USER" ~/.local/share/cl-go-dash

One last case: on a home folder mounted over the network or on an encrypted volume, the 0700 and 0600 permissions cannot always be set. There is no reasonable workaround — this is a case to report to the project.

Warning Disk space is not checked. Beaver does not check free space before downloading the local engine. On an almost full disk, the failure looks like a download or extraction problem, not like a lack of space. Check your free space before running it again.

The GPU is not detected

The symptom. The installation succeeds, but local models are very slow, and Beaver never warns that a model is too large for the graphics card.

Two distinct mechanisms, not to be confused. Vendor detection is only used, on Linux, to choose which archive to download: Beaver reads the vendor identifiers in /sys/class/drm/*/device/vendor. A recognized AMD card triggers the download of an extra archive; if detection fails, only the base archive is downloaded and AMD acceleration is not installed. On macOS, detection reads the processor brand; on Windows, it queries the list of video cards.

Graphics memory measurement, on the other hand, decides the default context size, in three tiers: 32,768 tokens above 24,000 MB, 24,576 tokens above 12,000 MB, 8,192 tokens below — and 8,192 as well when the measurement fails. Unmeasured memory is therefore invisible: it shows up as a context reduced to the minimum. A second, more discreet consequence: the “this model does not fit in your memory” warning never appears when the measurement failed, because the check then answers that it fits.

What to do. On Linux with an AMD card, check that the card is seen by the system with ls /sys/class/drm/: if nothing matches, the graphics driver is not loaded, and that is a system problem, not a Beaver one. On Windows with an NVIDIA card, the driver must be installed: it is what provides the card name. On Linux with an NVIDIA card, you need a driver 531 or later; CUDA is provided in the Ollama archive. If the context stays at 8,192 tokens while your machine has more than 12 GB of graphics memory, the measurement failed: this cannot be adjusted from the app, so report the problem with the exact card model. See also Hardware and VRAM.

Note The local engine writes no log. Contrary to what older documentation suggests, the Ollama engine launched by Beaver writes no trace file: its output goes to /dev/null on macOS and Linux. There is no engine log to consult in case of slowness.

Uninstalling, and what remains afterwards

The data folder is independent of the installed app. That is deliberate: it is what lets updates lose nothing. Reinstalling after a partial removal therefore picks up your conversations, your settings and your keys as they were.

Removing the app, system by system
SystemHow
macOSDrag Beaver out of the chosen installation folder — /Applications by default
Linuxsudo apt remove beaver — the package name is beaver
WindowsSettings › Apps, or the uninstaller placed in the installation folder

What remains on the disk after this removal: the data folder ~/.local/share/cl-go-dash/ — conversations, memory, settings, projects, encrypted vault, and the Ollama installation; the downloaded Ollama models, in ~/.ollama/models, by far the largest and outside the data folder; the entries in the system secret manager, including the vault master key under the cl-go-dash service.

To remove everything: delete the app, then the data folder, then ~/.ollama if you do not use it elsewhere — careful, that folder is shared with any other Ollama installation on the machine — then the secret manager entries, by searching for cl-go-dash in Keychain Access on macOS, in the desktop password manager on Linux, in Credential Manager on Windows.

Warning Your data survives uninstallation. Deleting the app deletes neither your conversations, nor your keys, nor your models: they live in a separate folder. The last step, the secret manager one, is the one people forget — without it, the vault master key stays in your keychain. It no longer decrypts anything once secrets.enc is deleted, but it has no reason to be there any more. The full procedure is in Privacy.
