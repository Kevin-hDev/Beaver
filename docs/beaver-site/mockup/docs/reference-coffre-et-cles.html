Where your key goes

An API key is a password: whoever holds it can spend on your account at the provider. Many apps store them in a configuration file in the clear, readable by any program running under your session. Beaver does not do that, and this page explains what it does instead.

Note The summary in four sentences. Your keys live in a single encrypted file, secrets.enc, readable by your user account alone. The key that opens it is not inside: it is entrusted to your system's secret manager — Keychain on macOS, Credential Manager on Windows, the desktop secret service on Linux. Beaver's interface has no command able to read a key back, and there is no hidden version of one. Copying the file to another machine gives access to nothing.

The vault, concretely

A single file, in a single place, identical on all three systems.

$ ~/.local/share/cl-go-dash/secrets.enc

That file contains three fields: a format number (1 today), a randomly drawn number that differs on each write, and all your secrets encrypted into a single unreadable block. Nothing else — no provider name, no clue about what is inside: the list itself is within the encrypted block.

The file is reserved for your user account. On macOS and Linux, it is created as 0600 — you alone can read and write it — and the folders as 0700. On Windows, Beaver sets an access control list holding a single entry, yours, refuses to inherit the parent folder's rights, then reads back what it set to check. These permissions are rechecked and repaired at every startup.

The file is never written halfway. Beaver first writes a temporary file, forces it to disk, fixes its permissions, then renames it over the old one — a rename is an indivisible operation for the system. A power cut during a save therefore leaves either the old vault whole, or the new one, never a mixture.

The encryption, without jargon

The algorithm is XChaCha20-Poly1305. It does two things at once, and both matter.

  • XChaCha20 makes the content unreadable without the key — the part one spontaneously pictures on hearing “encrypted”.
  • Poly1305 adds a check signature: if a single byte of the file is modified, by another program, by a failing disk or by someone trying to tamper with the file, decryption fails instead of returning dubious data.

Two properties come on top. Each write uses a different single-use number, 24 bytes drawn from a cryptographic-quality random generator: saving the same content twice produces two files that look different, and nobody can deduce from them that nothing has changed. And a vault written by a future version of Beaver is refused, not rewritten: Beaver would rather stop than destroy data it does not understand.

One sentence covers the essential: copying secrets.enc to another machine gives access to nothing. The file does not contain what it takes to open itself.

The master key

The key that opens the vault is not in the vault — that would be putting the house key under the doormat. It is entrusted to your system's secret manager, the very one that keeps your browser's passwords.

LinuxDesktop secret service (GNOME Keyring, KWallet)

The entry carries the service name cl-go-dash and the identifier master-key: that is the name to look for. On the very first launch, Beaver draws 32 bytes from a cryptographic-quality random generator and stores them there. It does not derive that key from a password and does not compute it from the machine: it is purely random.

A single keyring access, at startup. The master key is read once, at initialization. You are not prompted on every request.

Warning Emptying your system keyring makes your keys unreadable. Beaver deliberately refuses to make a new master key when the old one has disappeared but the vault still exists: that would silently overwrite data that is still valid. If you empty the keyring, or if you change machine without it, you will have to enter all your keys again. No backup of secrets.enc will help you: it does not contain what it takes to open itself.

The life cycle of a key

From entry to call, in five stages.

  • Entry. You paste the key into the field on the API keys screen. As soon as the work is done, the copy passed by the interface is overwritten in memory.
  • Validation, once only, on the way in. Beaver checks that the provider exists in its catalog, that the key is not empty, that it is at most 256 characters long and that it holds no control character. An aberrant key is refused rather than stored.
  • Writing to the vault. It is transactional: Beaver makes a complete copy of the vault's content, applies the change to it, checks the whole thing, writes the entire file, and only then replaces what it holds in memory. If the write fails, the previous state stays in place. The working copy is erased from memory whatever happens, including on error.
  • Life in memory. The vault is decrypted once at startup, and the keys stay in memory for the duration of the session, each in a container that erases its content when released instead of leaving it lying around.
  • The call to the provider. Beaver asks for a protected copy of the key, puts it in the HTTPS header, and that copy is erased at the end of the call. The header carrying the secret is additionally marked as sensitive with the network library, which excludes it from its own traces.

Put plainly: the keys are not reloaded from disk on every request, they are in memory while Beaver runs. What is guaranteed is that every copy handed to a call is erased as soon as it has served, and that nothing is left in the clear after the app closes.

The interface cannot read a key back

This is the central guarantee, and it is demonstrated by an exhaustive list rather than by an assertion. Beaver has an interface part, written in JavaScript, and an engine written in Rust. The only passage between the two is a list of commands declared one by one: what is not on it does not exist for the interface.

No read command exists. The same rule applies to web accounts: the OpenAI account status command returns a “connected” boolean and the email address, extracted from the token on the engine side — the token itself never crosses the boundary. The list of account connections returns the provider identifier, its display name, the connection state and the account name, never a token. For connectors, there is only an existence test and a deletion.

Note A stored key can no longer be displayed — including by Beaver. This is not an ergonomics oversight: it is what guarantees that no piece of interface, no interface extension, no display fault can make your key appear on screen. Note it down elsewhere if you need it, or generate a new one at the provider.

What the vault contains besides keys

The vault is not reserved for model keys: everything secret in Beaver goes into it.

  • The API keys of the model, web search and forecasting providers.
  • The OpenAI / Codex account: access token, refresh token, expiry.
  • The Grok (xAI) and Kimi accounts.
  • The OAuth tokens of the MCP connectors, and their secret environment variables.
  • The Google and GitHub OAuth application identifiers.
  • The external channel tokens — Slack, Discord, Telegram —, one entry per channel and per account.
  • The Qwen connection settings.

To these are added technical keys that Beaver makes itself, each of 32 randomly drawn bytes on its first use: the one that encrypts the built-in browser's sessions, the one that signs the allowed attachment paths, the one that computes the reasoning continuity fingerprint, and the one that signs the external channels' audit log.

The built-in browser deserves a separate mention, because that is where the sessions of your web accounts live. They are stored in browser/sessions/, encrypted with the same primitive as the vault, and the key that opens them is itself in the vault.

What is not in the vault

configured-providers.json, the neighboring file, contains no secret: only a sorted list of provider identifiers, used to know which providers are configured without having to open the vault. It is protected by the same file permissions nonetheless.

Warning An approved extension can ask for your secrets. The vault protects your keys from the rest of the system. It does not protect them from code you have approved yourself: an enabled extension can ask for a provider key, a connector token or a channel token, and Beaver hands it over. That is why enabling an extension requires an explicit confirmation — see Extension center.

Older versions stored some tokens outside the vault

Everything secret goes into the vault, but that has not always been true. Older versions of Beaver wrote two connection files in the clear, next to the vault rather than inside it: the one for the Kimi account, kimi-code.json, and the one for the Grok account, auth.json. A program running under your session could therefore read them, which is precisely what the vault is there to prevent.

That is fixed, and the fix asks nothing of you: on the first startup of a recent version, Beaver permanently deletes those two files, along with an old vault copy that had become unreadable. The operation takes place only once, then Beaver remembers it is done. On your machine, those files no longer exist.

Warning An old backup may still contain them. Beaver only cleaned your machine: if you find kimi-code.json or auth.json in an old backup of your computer, or on an external disk, they may hold tokens that are still valid. Deleting the files is not enough — as with an API key, only revocation counts: go and revoke the corresponding accesses at Kimi and at Grok, then sign in again from Beaver.

Deleting a key, signing out of an account

Deleting a key removes its entry from the vault, rewrites the whole file and updates the list of configured providers. Signing out of a web account erases the corresponding entry; the other connections are untouched, each having its own separate entry.

Three things deletion does not do. It revokes nothing at the provider: the key stays valid on your account, it is simply no longer in Beaver. It cannot be undone: no restore is offered and, since no command allows a key to be read back, there is no way to recover it. And it does not take back what has already gone: if an approved extension obtained the key while it was stored, deleting it from the vault does not cancel that copy.

Warning Deleting in Beaver revokes nothing at the provider. A key removed from the vault remains perfectly valid on your OpenAI, Mistral or Brave account. If you think it has leaked, the only effective action is to delete it on the provider's website.

When the system keyring is unavailable

This mostly happens on Linux, on a minimal desktop session or a command-line connection, where no secret service is running. What happens then: the keyring access fails, the vault initialization fails, the app starts anyway — there is no blocking screen —, and two seconds later a banner appears, which goes away when you click it. The delay gives the window time to show before the message.

The text displayed, word for word: “Cannot access keyring. Install gnome-keyring or kwallet to store API keys.”

Note What still works. The vault stays uninitialized: any attempt to store, read or delete a secret is refused. Local models through Ollama, however, need no key and keep working normally. On Linux, install and start gnome-keyring or kwallet, then restart Beaver.

What is written to the traces

Three cumulative protections. The providers' answers are never written raw: they go through a single function that masks sensitive data, strips control characters and truncates to 200 characters. The HTTPS headers carrying a secret are marked sensitive with the network library, which excludes them from its debug traces. And secrets.enc is on the app's list of protected files: an agent trying to read it or manipulate it through a command triggers an alert. The same list covers config.json, agent-settings.json and configured-providers.json.

The error messages meant for you stay generic — the screen shows “Operation failed. Please try again.” whatever the technical detail — and the body of the provider's answer is read then thrown away, without being displayed or logged.
