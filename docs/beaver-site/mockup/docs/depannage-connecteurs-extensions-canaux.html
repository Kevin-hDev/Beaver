When a plugged-in service stops answering

Three different systems share this page because they look alike from the outside. An MCP connector is an external service that lends tools to the agent. An extension is code that runs in a process separate from Beaver. An external channel is a messaging bot that talks to the agent from Telegram, Slack or Discord. They fail in very different ways, and the first thing to do is to work out which of the three is at fault.

What they have in common: a failure in one does not stop Beaver. The agent keeps working without the missing tools.

An MCP connector that won't start

Warning Beaver does not accept just any MCP server. The list is closed: five connectors installable locally, thirteen approved remote endpoints, three programs allowed to start. The command launched must match the one in the catalog character for character. This is not a temporary limit: it is what prevents a connector from running arbitrary code under your account.

The five connectors installable locally are Context7, Hugging Face, Product Hunt, Reddit and iMessage — the last one on macOS only. Each is launched with a pinned version, by one of the only three allowed programs: npx, uvx or deno.

For remote connectors, the list is closed as well: thirteen approved endpoints — Gmail, Google Drive, Google Calendar, Canva, Figma, Notion, Slack, Linear, Lucid, Sentry, Vercel, Apify, GitHub. The address must be HTTPS, with no query parameter, no explicit port, and the path must match character for character.

What the interface shows, whatever the cause above, is a single sentence: “Unable to validate the connector. Check the token and try again.” The message blames the token in every case. So check first that npx, uvx or deno is indeed installed and reachable before suspecting your token: that is the most frequent cause behind this message.

Note npx and uvx download the package on the first launch. That is the most mundane cause of a start that seems stuck: the machine is downloading. No timeout bounds the start itself — only the first query is bounded, at 20 seconds. Wait, then try again.

Three bounds are worth knowing. 32 connectors configured at most. An idle connector is stopped after 10 minutes without use: its restart on the next call is normal, and makes that first call slower. Finally, a connector's tool catalog is kept in memory for 5 minutes — a tool added on the server side can therefore take up to five minutes to appear.

An MCP tool that fails mid-conversation

The agent does not call a connector directly: it goes through a single tool. On failure, you only read the sentence for the error category, never the precise cause.

The advice that follows the error is the part that matters, because it tells you whether trying again is risk-free. When the service was unreachable, Beaver writes “Aucun appel d'outil n'a été envoyé ; une nouvelle tentative est sûre.” In every other case: “Vérifier l'état du service avant de relancer : l'action a pu être exécutée.” — the call went out, and it may have gone through despite the error. Both sentences are written in French whatever your language.

One last useful detail: the output of an MCP tool is cut at 4,096 characters and marked as truncated. An incomplete answer is not necessarily a failure of the service.

A connector's OAuth sign-in failed

The sign-in goes like this: Beaver queries the service to find its authorization server, checks that the addresses obtained are among the approved ones, opens a local port, opens your browser, waits for the return, exchanges the code for tokens, tests the connector, then saves.

Seven distinct failure causes exist — authorization server not found or not approved, local port impossible to open, registration address not in HTTPS, service with no usable credentials, wait exceeded after 5 minutes, 50 requests arriving on the port with no valid return, connector refusing the token on the final test.

In all seven cases, you read the same sentence: “Connection failed. Please try again.” The exact reason is not displayed. In practice, by far the most frequent cause is the fifth: finish the sign-in in your browser in under five minutes, without closing the Beaver window.

Three details worth knowing:

  • Five OAuth sign-ins at most in parallel. Beyond that, the next ones are refused.
  • Restarting the same sign-in while it is running does nothing: the second attempt is discarded silently, with no message. The “Didn't work? Retry.” button therefore only has an effect once the first attempt has finished or been cancelled — close the window, then start over.
  • The page shown in the browser after a successful sign-in says “Authentification en cours — Vous pouvez fermer cet onglet et retourner dans l'application.”. It is in French whatever the language of the app, and it does not follow the theme: that is normal.

The full journey is described on Connector authentication.

A connector's token has expired

Beaver renews the token 30 seconds before it expires, under a per-connector lock: two simultaneous calls do not renew twice. The renewal endpoint is rechecked against the approved list before every call — a service that changed address would break the renewal rather than send your token elsewhere. That is deliberate.

Two situations have no automatic way out, and they are what explains why a once-reliable connector stops answering:

  • The service provided no refresh token. You have to sign in again.
  • The renewal fails — service unreachable, or token revoked on your side. Beaver does not retry and does not warn: the failure comes back as a plain tool unavailability.

In both cases, the manoeuvre is the same: disconnect from the connector, then sign in again. The tokens live in the encrypted vault, not in a configuration file — see The vault and API keys.

The extension host is unavailable

Extensions do not run inside Beaver: they run in a separate process, the host. Its state is visible in Settings › Extensions › Host: Stopped, Starting, Running, Error. Node.js 20 at minimum is required; an earlier version makes the start fail.

Warning The host does not restart indefinitely. Beaver allows itself 3 automatic restarts per 300-second window. Past that budget, nothing relaunches on its own until you act: that is exactly when the “Restart host” button is good for something. If the host goes straight back into error, the last resort is “Disable hosted extensions”, presented in the app under the heading “Recovery mode”: “Disables Beaver plugins and local extensions so Beaver can return to a working state.”

A rejected or incompatible extension

An extension is rejected before being loaded when its manifest announces an API version different from Beaver's — currently 1. The message is “This extension is not compatible with this version of Beaver.” and the state shown in the list is “Incompatible”.

There is no compatibility mode: the comparison is strict. The only way out is an update of the extension, or of Beaver.

The other refusals happen at installation time: Git repository not downloadable, Git repository that did not answer in time, invalid Git address or reference, invalid npm name or version, package that is not a Beaver extension, invalid manifest or entry point, symbolic link not supported, identifier already installed, maximum number reached, dependencies not installable, invalid or oversized installation environment.

The message “The maximum number of extensions has been reached.” corresponds to four limits: 128 personal extensions, 132 in total including official plugins, 64 tools per extension, 256 tools overall.

Security An enabled extension receives trust, not a limited permission. The activation window says so bluntly: “This extension will have full access to your account data, secrets, and features. Beaver has not audited it.”, with the “Trust and enable” button. After an update, the extension is disabled and must be approved again — “Updating will disable the extension. Review the new version before trusting it again.” And if the files change outside Beaver, the extension is stopped with “The extension files changed and must be reviewed again.”

Individual loading errors are listed under “Latest loading errors”, with the extension's identifier, the diagnostic sentence and, when it is known, the position in the file. The most frequent: “Module or dependency not found”, “Syntax error”, “Activation failed”, “Module import failed”, “The extension entry point is unavailable”, “The host did not confirm that this extension loaded”.

Refusals that concern an extension's interface, on the other hand, are all reduced to a single sentence: “This extension's interface contribution was rejected”. The detail is not exposed — if you are writing the extension, checking goes through your own control of the interface contract, described on Writing an extension.

An interrupted extension load

If Beaver stopped while loading an extension, it knows on the next start and stops before reloading it. A window opens: “Interrupted extension loading — Beaver stopped while loading an extension. Review it before choosing what to do.”

Five answers are possible: open the extension's page, keep it disabled, retry the load, delete the recovery information, or restore the previous registry.

The case of extension interfaces is treated more severely: after an interruption while loading an interface, Beaver starts in safe mode and shows no third-party interface element at all. The banner then says: “Extension interfaces disabled — This launch remains in safe mode and displays no third-party interface.” That is consistent with the project's rule: a feature is available and works, or it is invisible — never visible and broken.

A silent external channel

Warning A channel showing “Active” may be answering nobody. Four checks refuse messages silently: allowed users list, rate limit, account not configured, invalid message. Nothing is replied to the sender, nothing appears in Beaver, the status stays “Active”. That is a security choice, not a fault: a bot that replied “you are not authorized” would confirm its existence to anyone.

A message coming from outside goes through five checks before reaching the agent.

The five checks, and what triggers them
CheckWhat triggers it
Message validationMalformed identifiers, empty or overlong message
Account not configuredThe account matches no configuration
Allowed users listThe sender is not on it
Rate limitToo many messages in the past minute
Restricted providerThe chosen model is not allowed outside the interactive chat
Warning The allowed users list is not optional. Empty, it blocks everyone: the * wildcard is refused when saving, and only an entry present opens access. It is the first setting to check when a bot answers nobody. The field is called “Allowed users”; the comparison ignores case and surrounding spaces, and the list is bounded at 1,000 entries of 128 characters, the oldest being evicted beyond that.

The default rate limits are 12 messages per minute per user, 120 per minute per channel, 300 per minute overall, counted over a sliding 60-second window. A bot that answers then goes quiet after a few messages has almost always hit the first one.

The second cause of silence, specific to groups: the “Mention required in groups” option. When it is on, a group message that does not mention the bot is ignored before even entering the queue. If the bot answers in private but not in a group, that is it.

An external channel in error

Five states are shown: “Stopped”, “Starting…”, “Active”, “Error”, “Stopping…”.

Reconnection is automatic and bounded: the delay starts at 1 second and doubles on each failure up to 60 seconds. It goes back to 1 second if the previous connection held for more than 5 minutes. After 10 attempts, Beaver gives up and puts the channel into “Error”. A second reconnection, internal to the channel's permanent connection, ranges from 1 to 30 seconds and resets after 60 seconds of stable connection.

An authentication error stops everything immediately, with no attempt at all: a revoked or invalid token puts the channel into error on the first try. That is the right reaction — retrying ten times with a bad token leads nowhere, and some services hold it against you. A channel in instant error means a token to check; a channel in error after several minutes means the network or the service.

The three sentences shown on a channel

The test button shows “Connection successful” or “Connection failed”. Before starting an account, the engine checks the channel and account identifiers, the presence of a provider and a model, the validity of the allowed user identifiers, and the presence of every token required for that channel. Slack asks for two: “Slack bot token” and “Slack app token” — providing only one prevents the start.

The channel audit log

This is the only place to find what happened to messages refused silently. It cannot be consulted from inside the app: you have to open the file.

$ ~/.local/share/cl-go-dash/logs/gateway-audit.jsonl

One line per event, seven fields: timestamp, channel, account, user fingerprint, action, security decision, error. Eight actions are written: message received, message sent, message blocked, rate exceeded, agent error, channel started, channel stopped, authentication failure.

Security The sender's identifier is never written in clear. It is replaced by a fingerprint computed with a randomly drawn key kept in the vault. Practical consequence: you cannot read from this log who was refused — only see that two lines concern the same person.

The log keeps 10,000 entries at most, 2,048 bytes per line, with a purge by age according to the configured retention — 30 days by default, forced back between 1 and 365 days. It can be disabled in the configuration: it is then silent, with no error.

Warning When the log cannot be written, the message is refused. An audit failure is not ignored: it blocks processing. A channel can therefore go silent for a reason that has nothing to do with the channel — a full disk, or missing permissions on the log folder. That is the first thing to check when a bot goes quiet without any setting having changed.
