When the agent stops or refuses to act

A refused action, a failing tool, an answer that breaks off with no explanation: this page covers what happens between your request and the tool. Each symptom is given with the exact message you read on screen, its real cause, and what there is to do — including when the answer is “nothing”.

API key and provider failures are on Keys and providers; local engine ones on Ollama engine; connector, extension and bot ones on Connectors, extensions, channels.

The three places where a failure is read

Beaver does not put every failure in the same place, and that is the first thing to know: looking in the wrong place leads you to conclude there is no message at all.

Where a failure is read, and how long it stays
WhereWhat you find thereLifetime
Under a tool block, in the conversationThe failure of one tool: one sentence per error category, plus a piece of advice when there is oneStays in the conversation
Under the answer, when generation stopsThe failure of the whole stream: one sentence, plus a short technical summaryThe technical summary disappears when the conversation is reloaded
The permission log, on the diskEvery permission request and every answerFile rotated at 2 MiB, a single generation kept

Beaver also keeps in session memory the last 20 stream failures and the last 20 execution diagnostics, saved in the conversation file.

Note The technical summary of an interruption does not survive a reload. It appears under the answer at the moment of the failure — for example “Interruption pendant le tool read_file (stream_error).”, written in French whatever your language — then disappears when you reopen the conversation. Copy it before switching tabs if you want to report it.

Why Beaver asks you for permission

The permission mode is chosen per conversation and changed from the keyboard with Shift+Tab. In Chatbot, the agent only has two tools, web_search and web_fetch, and no access to files. In Full access, no question is asked. In Ask permission, a window opens before every action classified as sensitive. The detail of each mode is on Permission modes.

The question that comes up most often in troubleshooting is not “why does Beaver ask” but “why does Beaver ask for that”. The answer almost always lies in a single rule, the one about shell commands.

Note A pipe changes everything. grep -r pattern . asks for no permission; grep -r pattern . | head asks for one. As soon as a command contains |, &&, ;, ||, >, <, &, a line break or a substitution, it leaves the list of commands recognized as safe and comes back to you.

The commands recognized as safe, as long as they stay alone, number twenty: ls, cat, head, tail, wc, grep, find, git status|log|diff|show|remote|tag, git branch alone, pwd, echo, which, cargo check|test|clippy|build, npx tsc, npm run|test, tree, file, stat, du, df.

For tools brought in by an extension, the request depends on the effect the extension declares.

Extension effects and what they allow

The last three effects never offer “Always allow”: every call asks the question again.

“Allow …?” — the request window

The exact title is “Allow {{action}}?”, with three buttons: “Deny” — the Esc key does the same —, “Allow once” and “Always allow”.

Only four tools have a translated label in this title: “write a file”, “edit a file”, “run a command”, “fetch a URL”. For all the others, the title shows the technical name of the tool: you can therefore read “Allow forecast_backtest?” or “Allow apply_subagent_changes?”. That is the real name of the tool, not a display fault.

Two cases where no window appears even though you expect one:

  • More than 64 requests are pending — the 65th is refused without any window opening. Stop the answer and start again.
  • The answer is cancelled while waiting — the request is withdrawn, and that withdrawal counts as a refusal.

A refused action: what the agent sees, what you see

When you refuse, the agent receives an error result carrying the message “L'utilisateur a refusé cette action.”, written in French whatever your language. You, on the other hand, read the sentence for the category: “This operation is not permitted.” — the same one as for a write guard or a forbidden tool. The exact detail is not displayed: you have to reread the tool's context to know which of the three cases applies.

There are ten tool error categories, and each has one sentence and only one. Recognizing the sentence means recognizing the category.

The ten tool error categories and their sentence
CategorySentence displayed
Invalid requestThe request sent to the tool is invalid.
PermissionThis operation is not permitted.
Resource missingThe requested resource could not be found.
State conflictThe current state prevents this operation.
Timed outThe tool did not respond in time.
CancellationThe operation was cancelled.
UnavailabilityThe tool is temporarily unavailable.
External serviceAn external service prevented the operation.
ExecutionThe tool could not complete the operation.
Internal errorAn internal error prevented the operation.

The advice under the error. Some failures add a guiding sentence. The most frequent is “Check the resulting state before retrying because the action may already have run.”, and it means exactly what it says: the failure concerns the answer, not necessarily the action. Three shell command cases carry it explicitly — timed out, output unavailable, unclassified failure.

A missing tool result. If the stream ends while a tool has not returned its result, Beaver writes “The tool result is missing after the stream ended.”. This is not a tool failure: it is the stream that stopped before it, and the action may have taken place.

A command blocked outright

Some commands are not submitted to you: they are refused. The refusal applies in every mode, including Full access. It is not a setting, and no setting unblocks it.

The fifteen forbidden patterns, word for word: sudo rm, chmod 777, dd if=, mkfs., > /dev/sd, fdisk, shutdown, reboot, init 0, init 6, :(){:|:&};:, del /f /s /q, rd /s /q, format c:, format d:.

Four additional forms are detected by pattern: an eval on a variable, a find with -delete, an rsync with --delete, a dd targeting of=/dev/, and a standalone mkfs.

The exact messages are “Commande bloquée : pattern dangereux « … »” or “Commande bloquée : pattern dangereux détecté”. They are addressed to the agent, in French, and do not follow the language of the app. The only way out is to reword the command.

“Écriture bloquée : fichier non lu avant modification”

The exact message is “Écriture bloquée : fichier non lu avant modification. Utilise read_file sur ce chemin d'abord.”, in French whatever your language. It is a protection against blind overwriting: Beaver only allows modifying an existing file if the agent has read it during the conversation. A file that does not exist yet is not concerned.

Note This is not an error, and there is nothing for you to do. The agent rereads the file and carries on by itself. The only situation worth reporting is an endless repetition, covered further down.

The memory of files read is bounded at 1,000 paths, and adding the 1,001st erases the 100 oldest. On a very long conversation touching many files, a file read at the beginning may therefore require another read. That is the expected behavior.

A file outside the allowed areas

Two messages, depending on the direction of the operation: “Lecture interdite hors des zones autorisées” and “Écriture interdite hors des zones autorisées”, both in French whatever your language.

The allowed areas are the folders configured in the settings, the session output folder if one is configured, the system temporary folder, the working folder of the conversation, and the agent's own resources — memory, skills and instruction files.

On the interface side, refusing a session folder carries a different label: “Folder not allowed”, followed by “Sessions are limited to the following folders:” and “To use another folder, change Settings > Advanced > File Access.” That is where the list is set, described on Settings · Agent.

Two bounds frame this list: 70 allowed paths at most, 4,096 characters per path. Beyond that, the setting is refused. Finally, a symbolic link is never followed for the agent's resources: a memory folder pointing elsewhere is simply ignored.

The required context exceeds the model capacity

This is the only Beaver error message that gives its numbers. In its complete form:

Message “The required context exceeds the model capacity: system prompt {{systemTokens}} tokens + required reports {{reportTokens}} tokens + active tools {{toolTokens}} tokens = {{requiredTokens}} tokens, with an input limit of {{maxInputTokens}} tokens in a {{contextWindow}}-token window.”

When the model's actual window could not be determined, the sentence ends with “The model's actual context window could not be determined.” and speaks of a reduction target rather than a capacity.

What is overflowing is not your conversation. It is what Beaver must send before even the first message: the system instructions, the subagent reports still to be delivered, and the description of every active tool. The conversation does not enter the sum — emptying it changes nothing.

The three terms are the three levers, and that is all the calculation allows you to state: fewer active tools — MCP connectors and extensions carry most of them —, no pending subagent report, or a model with a larger window. The app suggests no action in this message: it shows the numbers and stops.

The numbers displayed are checked on both sides before they appear: the sum must be exact, each value below 16,777,216, and the input limit less than or equal to the window. If a counter is inconsistent, Beaver shows no number at all rather than a wrong one.

How the context itself works is described on Context.

The agent reached its turn limit

A turn is one model-then-tools round trip. The limit is 200 turns per answer: the stop is decided at turn 199, and Beaver uses the opportunity to unload the model from graphics memory before handing back control.

What you read at the moment of the stop is generic — “Stream was interrupted.” —, with no mention of the 200 turns. The precise sentence, “The agent reached its turn limit. Continue in a new message.”, appears when you reopen the conversation. The same incident therefore produces two different messages depending on when you look: it is the second one that names the real cause.

The same limit serves in a second case, unrelated to the 200 turns: when a subagent is still active, when a report has not been delivered, or when a fix is still queued. The turn is then refused to let the child finish.

In both cases, the course of action is the same: start again in a new message.

The agent was going round in circles

Beaver counts strictly identical tool calls that follow one another — same tool name, same arguments. At the sixth in a row, it stops the answer. The message displayed is “The response stream was interrupted. Try again.”

When you have seen the agent repeat the same action six times before the stop, that is this circuit breaker. Starting again identically is no use: the repetition signals that the agent has no new information. Reword the request, or give it the missing element.

Warning A single changing argument resets the counter to zero. A loop where the agent rereads the same file with a different offset each time will therefore not be cut by this mechanism: it is the 200-turn limit that eventually takes care of it, several minutes later. If you see that, stop the answer by hand.

A failed subagent

Four states are shown under the subagent bubble: “completed”, “failed”, “cancelled”, “interrupted”. Three distinct failures hide behind “failed”.

What a “failed” subagent covers
SituationInternal message
The subagent collapsed along the way“Le sous-agent n'a pas pu terminer correctement.”
Its preparation failed before it even startedThe same sentence
It worked but could not deliver its report“Le sous-agent n'a pas pu finaliser son rapport.”
A tool is forbidden to it“Outil indisponible pour ce sous-agent.”

A collapse is caught, not propagated: the failure is captured in the task that owns the subagent, and a recovery routine marks the terminal state. For a subagent tasked with writing code, Beaver first tries to recover the changes already made in its workspace before concluding.

Two limits worth knowing. You cannot write in a subagent's conversation: any attempt returns “This subagent session is read-only.” Write in the parent conversation instead. And reread the subagent's summary before reopening the conversation, since the technical summary does not survive a reload.

Warning A subagent asks you nothing. Child sessions run in an internal mode that bypasses the permission guard. In Ask permission, the parent's actions are submitted to you; those of its subagents are not. That is a choice, not a fault — see Subagents.

Where the diagnostics are written

Every permission request and every answer is written to a log, one line per event, with four fields: timestamp, event, tool, detail.

$ ~/.local/share/cl-go-dash/logs/permission-diagnostics.jsonl

The file is renamed with the .1 suffix past 2 MiB, and a single generation is kept: beyond that, the oldest history is lost.

The events written to the permission log
EventWhat it means
Request sentA window was sent to the interface
Answer received — allow, allow for the session, denyYour answer was recorded
Orphan answerAn answer arrived for a request that no longer existed
Automatic bypassThe current mode does not ask for permission
Memory write allowedA write covered by the policy dedicated to memory

The Ollama engine, for its part, writes no log — see Ollama engine. And the agent's other visible traces are described on Diagnostics and errors.
