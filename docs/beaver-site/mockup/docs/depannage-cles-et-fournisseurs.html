Keys and providers, when they refuse

Your key is rejected, your quota is reached, your connection has expired, or a provider has gone from the list. This page starts from the message displayed and works back to the cause. It also says, plainly, what cannot be settled inside Beaver: a good part of these situations is handled at the provider, on their site, and knowing that right away saves half an hour of looking in the wrong place.

It does not re-explain entering a key, signing in with a web account, or how the vault works — it points to them.

The first question to ask: key or account?

Beaver knows two ways of accessing a provider. The symptoms look alike, the remedies have nothing in common.

Two access mechanisms, two different failures
API keyWeb account
What you provideA string copied from the providerA sign-in in a browser
What expiresNothing, unless you revoke the keyThe token, regularly
What Beaver renews on its ownNothingThe token, automatically
What happens when it breaksThe key is rejected on every requestThe connection is erased and the provider disappears
Providers concernedAll those on the API Keys screenOpenAI (Codex), Grok (xAI), Kimi

The practical question: is your provider in the “API Keys” tab or in the “OAuth” tab? The four sections that follow deal with the first case; signing in with an account comes next.

“Operation failed. Please try again.” when saving a key

What you see — in the add-a-key dialog, after “Add and test”, the indicator goes from “Testing key…” to “Operation failed. Please try again.”. When all is well, the message is “Key valid, provider connected.” and the dialog closes after half a second.

This message never says what failed. Beaver does distinguish seven causes internally, all replaced by this single text on screen. Here they are, with their remedy.

The seven real causes behind a single message
What happenedRemedy
The key is empty or longer than 256 charactersCheck that no space or line break was pasted along with it
The key contains a control characterCopy the key again from the provider's site, without going through a word processor
The provider is not in the catalogGo through the API keys screen, not through a value typed by hand
The provider rejected the key (401 or 403)See “Authentication failed”, further down
The provider reported a quota exceeded (429)See “Quota, rate limit, credits”
The provider refused for another reasonCheck the service status at the provider
The test could not be sent — network, proxy, service unreachableSee “Network errors”

The special case of Qwen is worth knowing, because it produces a failure where the key is nonetheless valid: a key starting with sk-sp- is rejected before it is even tested. Those are workspace keys, which Beaver does not support. You need an account key.

What to do, in this order:

  • Copy the key again from the provider's site, in one go, with no surrounding space.
  • Check that it is active in the provider's dashboard.
  • Check that the account has credit — many providers reject a valid key on an account with no balance, and that looks exactly like an invalid key.
  • Try again later if the provider's service is having an incident.

“Authentication failed, check your API key”

What you see — this message appears in a conversation, or in place of a provider's model list.

The cause — the provider answered 401 to a request from Beaver. In other words: the saved key is not, or is no longer, accepted. Four possible reasons, the third of which is surprising:

  • The key was revoked or deleted at the provider.
  • The key was copied wrong when it was saved — and nobody can read it back to check.
  • The account was suspended, or its payment method expired. Many providers then answer 401, which presents itself as an invalid key.
  • The key is valid but not for this model — some providers restrict access per key.
Note A saved key can no longer be read back, including by Beaver itself: no command displays a key from the vault. If you have a doubt about the one in place, there is no way to check it — you must generate a new one at the provider and enter it again. That is the only reliable route. See The vault and API keys.
Security Deleting a key in Beaver does not revoke it. It stays perfectly valid on your account at the provider. If you think it has leaked, the only effective action is to delete it on the provider's site.

A neighboring case, with a different message: “The OAuth connection has expired. Reconnect the provider.”. That one concerns web accounts, not keys. The same 401 code produces one message or the other depending on the context: on a key test it is “Authentication failed”, on a model catalog it is the expired connection message.

Quota, rate limit, credits exhausted

Three distinct situations, three different messages, and they are better kept apart because the remedies have nothing in common.

a) “The service or its upstream provider is currently rate limiting requests. Try again later. Available credit does not remove these limits, especially for free models.”

The provider answered 429. This is a rate limit: too many requests in a short interval. The remedy is to wait.

Warning Topping up your account does not lift a rate limit. Beaver's message already says so, and it is right to: a requests-per-minute limit is independent of your balance, and it is particularly low on models advertised as free.

b) “xAI reports that a Grok subscription or credits are required.” and “The xAI subscription quota is exhausted or temporarily unavailable.”

The provider answered 402, and its response carried xAI's own over-limit code. The remedy is at xAI: check the Grok subscription or add credits. Nothing to do inside Beaver.

c) “Moonshot cannot confirm an active Kimi Code membership.”

Same mechanism, on a specific message returned by Moonshot in response to a 402. Check the Kimi Code subscription at Moonshot. This message also appears right after a successful sign-in, in a longer form: “Sign-in succeeded, but Moonshot cannot confirm an active Kimi Code membership. Check the subscription and try again.”

Two other refusals are easily mistaken for a quota:

  • “OpenRouter requires age confirmation for this model. Confirm that you are 18 or older at openrouter.ai/settings/preferences, then try again.” — the only message in the product that gives the exact address of the page to open.
  • “The provider is currently refusing access to the model.” — a generic access refusal, on an unrecognized 402 or 403.

Network errors, and why nothing is retried

The network messages and what they cover
MessageCause
“Unable to connect to the provider.”The request could not leave or reach the provider
“Connection to the provider was lost. Try again.”The response was interrupted midway
“The provider took too long to respond. Try again.”Timed out
“The provider is temporarily overloaded. Try again shortly.”The provider reports an overload
“The provider is temporarily unavailable. Try again shortly.”Service having an incident
“The provider rejected the request.”Unclassified refusal — any HTTP code other than 401, 402, 403 and 429
“The provider could not complete the request. Try again.”Generic failure
Warning Beaver never retries a request to a remote provider on its own. That is a choice, not an oversight: a request that seems lost may well have gone through at the provider, and replaying it automatically would bill it twice. As long as a transport does not carry an idempotency key — something to tell the provider “this is the same request, do not count it twice” —, automatic retries stay closed. When a message ends with “Try again”, it is an instruction, not a courtesy: it is up to you to send it again.

The asymmetry with the local engine is deliberate: that one retries up to ten times, because it bills nothing.

What to do — check your connection, check the provider's status page, then send the request again by hand. On a corporate network, check that a proxy is not blocking the provider's domain.

A web account sign-in has expired

What you see — “The connection has expired. Reconnect this provider.” on the provider screen, or “The OAuth connection has expired. Reconnect the provider.” in a conversation.

How it works when all is well, because it sheds light on the failure: an access token has a short life, and Beaver renews it on its own, before it expires, without ever asking you.

The renewal margin, by connection type
AccountMargin before expiry
Grok (xAI) and Kimi60 seconds
OpenAI (Codex)5 minutes
MCP connectors30 seconds

When the renewal fails, two very different outcomes:

  • The provider answers “not authorized” — refresh token revoked, password changed, session closed from their site. Beaver erases the connection and treats it as non-existent. The provider then disappears from the list of connected accounts, and nothing warns you it happened.
  • The renewal fails for another reason — network, service down. The connection is kept; you only need to try again later.

This distinction matters and it is invisible on screen: in one case you must sign in again, in the other you must wait. In practice, try once; if the provider has gone from the list, it is the first case.

A reassuring detail: for OpenAI, if the renewal fails while the current token is still valid for a few minutes, Beaver carries on with the current token instead of failing. A brief network cut at the wrong moment therefore does not break the session.

What to do:

  • Open the OAuth tab, select the provider, click “Connect”.
  • Follow the journey in the browser. The steps shown are “Waiting for sign-in…”, “Verification required”, then “Connected”; on failure, “Unable to connect”, and if you give up, “Sign-in cancelled”.
  • If the message comes back immediately after a successful sign-in, it is not a connection problem but a subscription one: see above.

“Disconnect” erases the vault entry for that provider only; the other connections are untouched.

A provider has gone from the list

What you see — a provider that was there yesterday no longer appears in the model selector, or no longer in the list of connected accounts. Four causes, to be handled separately.

  • Its key was deleted. The list of configured providers is rebuilt on every change, and a provider without a key no longer appears.
  • Its web account sign-in was erased after a refused renewal. This is the case described just above: Beaver itself erases the connection when the provider declares the refresh token invalid. No message reports it — the provider is simply absent on the next load.
  • Its model catalog failed — and there, it does not disappear completely. It stays visible with a counter at 0, and the reason is shown inside when you expand it.
  • The whole catalog is unreachable. If Beaver cannot obtain the list of available providers, all the configured providers go into failure with the same reason: “The model catalog is temporarily unavailable. Try again later.”
Note A provider at zero models is not broken. Expand it: the exact reason is shown inside. That is the only way to know whether it is a passing limit, an expired connection or a subscription problem.

What to do:

  • Open the API Keys screen: if the provider is listed there, its key is still saved and the problem is elsewhere.
  • Open the OAuth tab: if the provider is listed there as disconnected, you need to sign in again.
  • Expand the provider in the model selector to read the exact reason.
  • Click “Try again” on the provider screen, which fetches the catalog again.

The provider is there, but no model appears

What you see — the provider is visible, its counter shows 0, and a grayed line inside gives the reason. There are six of them.

These six messages come from the catalog, not from a conversation. A provider can perfectly well have a failing catalog and work otherwise, or the reverse: testing a key and fetching the catalog are two different calls.

One last message, met during a conversation: “This model is no longer available. Choose another model and try again.” The provider withdrew this model. There is nothing to repair — you have to choose another one.

The web search providers

The three search providers — Brave, Exa, Firecrawl — use the same key screen and the same messages as the model providers, with one difference worth knowing.

Warning Testing a search key consumes quota. The test is not an empty check: it is a real search on Brave, a real search on Exa, a credit lookup on Firecrawl. On a tight monthly quota, test once, not ten times. See Web search.
