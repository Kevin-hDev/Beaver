Connected services.

MCP is a standard protocol that lets an assistant use outside services: task tracker, knowledge base, messaging, design tool, deployment platform. Once a connector is configured, the agent can create a ticket, read a page, post a message — without Beaver having written a single line of code specific to that service.

This page describes the tool. To add a service and authenticate it, see MCP connectors.

A single tool for every service

search_mcp_tools belongs to the External connectors group, which is locked. It is of no use as long as no connector is configured and enabled: in that case, it simply answers "No MCP connector enabled".

Beaver does not expose the connectors' tools to the model as so many separate tools. A connector may offer fifty functions; injecting all of them into the context on every request would consume an enormous amount of room, for functions that are almost never used.

Instead, the agent has a single two-step tool: search — "which external tools exist for dealing with issues?" — then call — "run this specific tool with these arguments". The cost in the context is that of a single tool, whatever the number of configured connectors.

Searching for an external tool

  • The agent sends one or more keywords. Beaver queries every enabled connector and returns the tools whose name, description or connector name contain one of the words.
  • An empty search lists everything available.
  • Each tool is identified as service.tool_name, with its description.
  • At most 15 tools per connector come back from a search: a broad search may therefore not show everything.
  • When a connector does not answer, the result says so — it lists the skipped connectors instead of acting as though they did not exist.
  • If no connector answers, that is an outright error, not an empty list.

Calling an external tool

The agent gives the tool's full identifier and its arguments. Beaver checks that the connector is indeed enabled, then passes it on. The call is abandoned after 60 seconds.

Approval

Searching requires nothing. Calling requires approval in Ask permission mode. The distinction is logical: browsing a catalogue has no effect, whereas a call can create, modify or delete something in an outside service — off the machine, and out of reach of an undo.

Key point Searching is free, calling commits. An MCP call acts on an outside service: it cannot be undone from Beaver, and its effect outlives the conversation.

What is checked before the call

  • The identifier must have the form service.tool.
  • The connector's name and the tool's name are validated separately. A tool name accepts at most 64 characters, only letters, digits, hyphens and underscores.
  • The connector must be enabled. A connector that is configured but switched off is out of reach — the check happens at call time, not only at search time.
  • Arguments are validated against the schema declared by the service itself before being sent. A malformed call is refused locally, without going out over the network.

What Beaver does with the answer

An external service's answer is content Beaver does not control. It is therefore cleaned before entering the conversation.

  • Invisible control characters are removed — notably those that reverse the reading direction of text or that hide content. A compromised service cannot display one thing on screen and pass something else to the model.
  • The answer is capped at 4,096 characters. Beyond that, it is truncated and the result says so.
  • An error returned by the service stays an error. It is never presented to the agent as a success on the grounds that the communication itself worked.
Security External services' answers are cleaned of the invisible characters capable of deceiving the display, before they even enter the conversation.

When it fails

Failures are classified, and that classification decides whether the agent may retry.

The five failure types of an MCP call
Failure typeRetryableWhy
Service unreachableYesNo call went out: retrying is risk-free
Error returned by the serviceNoThe service received the call and refused it
Unintelligible answerNoThe service received the call; its state is unknown
Transmission failureNoSame
60-second timeoutNoThe action may have gone through
Careful A timeout does not mean "nothing happened". The error message says so explicitly: check the service's state before trying again. Without that precaution, a slow action may be carried out twice — and the same ticket created twice.
