Les neuf outils de délégation.

Ils forment le groupe Sous-agents, optionnel et actif par défaut. Cette page est la référence des outils ; le fonctionnement des sous-agents — sessions isolées, espaces de travail Git séparés, limites — est expliqué dans Sous-agents.

Le groupe est indivisible : impossible d'autoriser la délégation sans autoriser le suivi, ni l'inverse. Tout dépend de l'outil de délégation — s'il est absent, les huit autres sont retirés automatiquement.

Un seul de ces neuf outils demande une approbation : celui qui intègre du code écrit par un sous-agent dans ta branche. C'est le seul qui modifie durablement le projet.

Déléguer une tâche

Deux types de sous-agents, et le choix détermine ce qu'ils peuvent faire.

Explorateur et codeur
TypeOutils dont il disposeÉcrit dans le projet
ExplorateurSept : commandes d'exploration en liste blanche, lecture de fichiers, listing, recherche par motif, recherche par nom, recherche web, ouverture de pageNon
CodeurDix, plus le chargement de skills si le groupe Skills est activé : commandes shell et pilotage d'un processus, lecture, création et modification de fichiers, listing, recherche par motif, recherche par nom, recherche web, ouverture de pageOui, mais à l'écart

Deux points à ne pas manquer. L'explorateur dispose de commandes shell, contrairement à ce que « il ne fait que lire » laisse croire : ce sont des commandes d'exploration en liste blanche stricte, sans opérateur de shell, et il n'écrit toujours rien dans le projet. Et le chargement de skills n'est donné qu'au codeur, seulement si le groupe Skills est activé dans les réglages — couper ce groupe prive aussi tes sous-agents codeurs de leurs guides.

Autres points à retenir :

  • Le résultat d'un sous-agent ne t'est pas montré directement. Il revient à l'agent principal, qui doit le résumer. Sa conversation reste visible : tu peux l'ouvrir pour voir le détail.
  • Un sous-agent travaille dans sa propre conversation pendant que l'agent principal continue, et plusieurs peuvent travailler en parallèle sur des sous-tâches indépendantes.
  • L'agent a pour consigne de ne pas refaire lui-même le travail délégué, et de ne pas conclure avant d'avoir reçu les rapports.
  • La délégation est déconseillée pour les tâches courtes : lire un fichier connu, chercher une fonction précise, une opération en une ou deux étapes.
  • Un sous-agent ne peut pas déléguer. La récursion est interdite : il est la seule et unique génération d'enfants de sa conversation.

L'instruction donnée au sous-agent doit être structurée — contexte, tâche, contraintes, format attendu. Un sous-agent ne voit rien de la conversation parente : ce que l'agent oublie de lui écrire, il ne peut pas le deviner, et une instruction laconique produit un résultat superficiel.

Une variante existe : réutiliser un sous-agent déjà créé plutôt que d'en lancer un neuf, ou pointer vers une définition d'agent spécialisé écrite d'avance dans le projet. Les chemins absolus et les remontées d'arborescence y sont refusés.

Suivre les sous-agents

  • Lister donne pour chaque sous-agent son état, son nom, sa description et son identifiant.
  • Consulter donne le détail d'un seul, avec son résumé final quand il a terminé.
  • Envoyer une instruction à un sous-agent déjà lancé : s'il travaille encore, l'instruction est mise en file et traitée ensuite.
  • Annuler arrête un sous-agent en cours ; archiver range un sous-agent terminé. Un sous-agent qui travaille encore doit être annulé d'abord.

Tous ces outils ne voient que les sous-agents de la conversation en cours. Une conversation ne peut ni lister ni piloter les sous-agents d'une autre.

Récupérer le travail d'un sous-agent codeur

Un sous-agent codeur ne modifie pas le projet directement. Il travaille dans un espace Git isolé, et son travail devient un changement en attente — une proposition, pas une modification.

Le cycle est en trois temps :

  • Examiner — l'agent récupère le détail du changement et le différentiel complet. Aucun effet, aucune approbation.
  • Intégrer — le changement est appliqué sur ta branche courante. C'est l'étape approuvée.
  • Abandonner — le changement est rejeté et sa branche temporaire supprimée.

L'agent a pour consigne d'examiner avant d'intégrer, sauf si le contenu a déjà été passé en revue. Et après une intégration faite à la main par tes soins, la bonne pratique est d'appeler quand même l'abandon : cela nettoie le changement et sa branche temporaire, qui sinon restent sur le disque.

Les identifiants nécessaires — celui du sous-agent et celui du changement — sont fournis à l'agent dans les données du changement. Ce sont des identifiants uniques, vérifiés avant toute opération.

À retenir Un sous-agent codeur ne modifie jamais ton projet directement : il produit une proposition dans un espace isolé. Rien n'entre dans ta branche sans une intégration explicite — la seule opération approuvée des neuf.

Ce qui peut mal tourner

L'intégration d'un changement touche à Git, donc à l'état réel du dépôt. Les échecs sont classés avec soin, parce qu'ils n'appellent pas la même réaction.

Les échecs d'intégration et la réaction attendue
SituationCe que ça veut direCe qu'il faut faire
ConflitLe changement ne s'applique pas sur l'état actuelExaminer et résoudre avant de poursuivre
Branche cible différenteLa branche a changé depuis la création du changementRevenir sur la bonne branche, ou refaire le changement
État incompatibleLe changement n'est ni prêt à être intégré, ni abandonnableExaminer l'état du dépôt et du changement
Changement introuvableIl n'existe plusRien à faire
Échec de restaurationBeaver n'a pas pu ramener le dépôt à son état antérieurVérifier le dépôt à la main avant toute opération Git
Dépendance indisponibleUn élément nécessaire manqueVérifier le dépôt : l'opération a pu être partiellement appliquée
Capacité atteinteTrop de projets isolés en coursNettoyer les changements en attente

Le message d'échec d'intégration dit quoi faire : le changement isolé reste non résolu, il faut inspecter son état, et après une intégration manuelle appeler l'abandon pour nettoyer. Aucune de ces erreurs n'est présentée comme rejouable à l'aveugle, sauf la capacité atteinte : une opération Git interrompue laisse un état que seul un examen permet de connaître.

Ce que l'explorateur peut lancer comme commande

Le bash de l'explorateur n'est pas le bash ordinaire. C'est une liste blanche stricte, vérifiée avant toute exécution.

Les commandes d'exploration autorisées
Commande autoriséeContrainte
pwdSans aucun argument
lsOptions d'affichage seulement, chemins confinés au dossier de travail
tree-L obligatoire, profondeur de 1 à 8, aucune autre option
file, stat, wc, du, dfOptions d'affichage seulement, chemins confinés
git status, git diff, git log, git show, git rev-parse, git ls-filesOptions de mise en forme et de sélection seulement, chemins confinés
git remote -v, git tag --listExactement cette forme
git branchSeules les options d'affichage : -a, --all, -r, --remotes, -v, -vv, --list, --show-current

Une option hors liste est refusée avec « Option d'exploration refusée. » ; une commande ou une sous-commande hors liste, avec « Commande d'exploration refusée. » S'y ajoutent trois règles de forme : aucun opérateur de shell — leur seule présence fait refuser la commande —, 32 mots au maximum, et tous les chemins confinés au dossier de travail du sous-agent.

Note Il n'existe qu'un seul contexte où ces neuf outils sont refusés : à l'intérieur d'un sous-agent, puisqu'un sous-agent ne délègue pas. Une automatisation programmée en dispose comme n'importe quelle conversation — voir Skills et automatisations.
