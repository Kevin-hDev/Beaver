The nine delegation tools.

They form the Subagents group, optional and on by default. This page is the tools reference; how subagents work — isolated sessions, separate Git workspaces, limits — is explained in Subagents.

The group is indivisible: you cannot allow delegation without allowing follow-up, nor the other way round. Everything hangs on the delegation tool — if it is absent, the eight others are removed automatically.

Only one of these nine tools requires approval: the one that integrates code written by a subagent into your branch. It is the only one that changes the project for good.

Delegating a task

Two types of subagent, and the choice determines what they can do.

Explorer and coder
TypeTools it hasWrites in the project
ExplorerSeven: allow-listed exploration commands, reading files, listing, pattern search, name search, web search, opening a pageNo
CoderTen, plus skill loading if the Skills group is enabled: shell commands and driving a process, reading, creating and editing files, listing, pattern search, name search, web search, opening a pageYes, but off to one side

Two points not to miss. The explorer does have shell commands, contrary to what "it only reads" suggests: they are exploration commands on a strict allow list, with no shell operator, and it still writes nothing in the project. And skill loading is given to the coder only, and only if the Skills group is enabled in the settings — switching that group off also deprives your coding subagents of their guides.

Other things to remember:

  • A subagent's result is not shown to you directly. It goes back to the main agent, which has to summarise it. Its conversation stays visible: you can open it to see the detail.
  • A subagent works in its own conversation while the main agent carries on, and several can work in parallel on independent subtasks.
  • The agent is instructed not to redo the delegated work itself, and not to conclude before it has received the reports.
  • Delegation is discouraged for short tasks: reading a known file, finding a specific function, a one- or two-step operation.
  • A subagent cannot delegate. Recursion is forbidden: it is the one and only generation of children of its conversation.

The instruction given to the subagent must be structured — context, task, constraints, expected format. A subagent sees nothing of the parent conversation: whatever the agent forgets to write down, it cannot guess, and a terse instruction produces a superficial result.

A variant exists: reusing a subagent already created rather than launching a new one, or pointing at a specialised agent definition written in advance in the project. Absolute paths and directory traversal are refused there.

Following the subagents

  • Listing gives, for each subagent, its state, its name, its description and its identifier.
  • Consulting gives the detail of a single one, with its final summary once it has finished.
  • Sending an instruction to a subagent already launched: if it is still working, the instruction is queued and handled afterwards.
  • Cancelling stops a running subagent; archiving puts away a finished one. A subagent that is still working has to be cancelled first.

All these tools only see the current conversation's subagents. One conversation can neither list nor drive another one's subagents.

Picking up a coding subagent's work

A coding subagent does not modify the project directly. It works in an isolated Git workspace, and its work becomes a pending change — a proposal, not a modification.

The cycle has three steps:

  • Review — the agent fetches the change's detail and the full diff. No effect, no approval.
  • Integrate — the change is applied to your current branch. This is the approved step.
  • Discard — the change is rejected and its temporary branch deleted.

The agent is instructed to review before integrating, unless the content has already been gone over. And after an integration you did by hand, good practice is to call discard anyway: it cleans up the change and its temporary branch, which otherwise stay on the disk.

The identifiers needed — the subagent's and the change's — are supplied to the agent in the change's data. They are unique identifiers, checked before any operation.

Key point A coding subagent never modifies your project directly: it produces a proposal in an isolated workspace. Nothing enters your branch without an explicit integration — the only approved operation of the nine.

What can go wrong

Integrating a change touches Git, and therefore the repository's real state. Failures are classified carefully, because they do not call for the same reaction.

Integration failures and the expected reaction
SituationWhat it meansWhat to do
ConflictThe change does not apply to the current stateReview and resolve before carrying on
Different target branchThe branch changed since the change was createdGo back to the right branch, or redo the change
Incompatible stateThe change is neither ready to be integrated nor discardableReview the state of the repository and of the change
Change not foundIt no longer existsNothing to do
Restore failureBeaver could not bring the repository back to its earlier stateCheck the repository by hand before any Git operation
Dependency unavailableA required element is missingCheck the repository: the operation may have been partially applied
Capacity reachedToo many isolated projects in flightClean up the pending changes

The integration failure message says what to do: the isolated change stays unresolved, its state has to be inspected, and after a manual integration discard should be called to clean up. None of these errors is presented as blindly replayable, except capacity reached: an interrupted Git operation leaves a state that only an inspection can reveal.

What commands the explorer can run

The explorer's bash is not the ordinary bash. It is a strict allow list, checked before any execution.

The permitted exploration commands
Permitted commandConstraint
pwdWith no argument at all
lsDisplay options only, paths confined to the working folder
tree-L required, depth from 1 to 8, no other option
file, stat, wc, du, dfDisplay options only, confined paths
git status, git diff, git log, git show, git rev-parse, git ls-filesFormatting and selection options only, confined paths
git remote -v, git tag --listExactly this form
git branchDisplay options only: -a, --all, -r, --remotes, -v, -vv, --list, --show-current

An option outside the list is refused with "Exploration option refused."; a command or subcommand outside the list, with "Exploration command refused." Three shape rules come on top: no shell operator — their mere presence gets the command refused —, 32 words at most, and all paths confined to the subagent's working folder.

Note There is only one context in which these nine tools are refused: inside a subagent, since a subagent does not delegate. A scheduled automation has them like any other conversation — see Skills and automations.
