Putting Beaver to work on a schedule

A wakeup is an instruction written in advance and tied to a time. At that time, Beaver opens a conversation, drops the instruction into it and lets the agent work until it has answered. This page describes the mechanism and the form; reading past results is covered in Wakeup history.

Warning Beaver has to be running. The scheduler lives inside the application, not inside your system's own: no task is registered with the macOS, Windows or Linux scheduler. Computer off or Beaver closed, nothing fires — the occurrence will simply be logged as “Missed” on the next startup. The form says so itself: “Wakeups only fire while your computer is on and Beaver is running.”

What a wakeup is

It is not a notification. It is a full agent turn, with its tools: the scheduler has no second engine, it borrows the agent's. Anything a normal conversation can do, a wakeup can do — read a folder, run a command, write a file, query a model.

The screen is called “Wakeups”, and its subtitle reads “Automate scheduled tasks for any LLM”. The tab that leads there still carries the name “Heartbeat” — it's the same place.

The three possible rhythms

The form offers three tabs.

The three rhythms and what they ask for
RhythmWhat you enterWhat it gives
“Once”A date and a timeA single firing, then the wakeup disables itself
“Daily”A timeEvery day at that time
“Weekly”A day of the week and a timeOnce a week, from “Monday” to “Sunday”

Everything is in your machine's local time. A daily wakeup at 8 a.m. stays at 8 a.m. after a daylight-saving change or a move to another time zone: the time shown by the computer is what counts, not a frozen offset.

The form's starting value is “Daily” at 08:00. Switching tabs resets the time: “Once” lands on the present moment, “Daily” and “Weekly” on 08:00, and “Weekly” on Monday.

Creating a wakeup, field by field

The button is called “New wakeup”, and the form is titled “New wakeup” or “Edit wakeup” depending on the case.

An empty field, or one made only of spaces, is refused for the name, the model, the provider and the instruction. Only the description may stay empty.

Only models capable of using tools are offered. The model list is filtered on that capability; when none fits, the field is disabled and shows “No tool-capable model”. That's logical: a wakeup without tools could only produce text, never read a file or run a command.

Some providers are not accepted. The rule fits in one sentence: the provider has to be usable for automation. The OpenAI web account qualifies; the Grok and Kimi web accounts are reserved for manual conversations and are refused. For those two, you need an API key from the same provider — see Account connection.

The “Project” field attaches the wakeup to a saved project, whose folder becomes the working directory of the conversation created. Without a project, the wakeup works in the default space, offered under the label “Beaver workspace”.

A one-off wakeup whose date is already past is refused at creation time, as long as it is enabled.

What happens at the appointed time

The scheduler does not wake every second: it computes the next useful moment and sleeps until then, with a ceiling of one hour. It is also woken immediately whenever a wakeup is created, edited, enabled or deleted — you never have to wait for a change to be taken into account.

The next moment is always strictly in the future. A daily wakeup at 8 a.m. looked up at exactly 8 a.m. therefore points to the next day, not to the present moment.

Wakeups due in the same minute go off together, and the same occurrence cannot fire twice: each firing reserves its slot and a duplicate is discarded silently.

A firing can be refused for two reasons, and that refusal is written to the log: Beaver is shutting down, or too many operations are already in flight — the capacity is 64 wakeups at once.

The conversation created by a wakeup

Each firing creates a fresh conversation. It never reuses the previous firing's: a daily report produces thirty conversations in thirty days, not one conversation of thirty messages.

Its name is built automatically, from the wakeup's name, the provider and the model. It always starts with Heartbeat •, which makes these conversations easy to spot in the list. On a local model, the name takes the form Heartbeat • <wakeup name> • <model>; elsewhere, the provider's name is inserted in between.

What a wakeup spends is counted separately: in the usage screen, everything coming from a wakeup is filed under the origin “Automation”. See Usage and costs.

Warning A wakeup works with full access, and that is a deliberate choice. It never asks for approval, because there is nobody in front of the screen to answer: a confirmation prompt at 3 a.m. would block the wakeup until the next morning, which would amount to not running it at all. Everything the instruction asks for — reading a file, writing one, running a command, deleting something — therefore happens with no possible confirmation. Write a wakeup's instruction with that in mind, and check it the way you would check a command you are about to run yourself. The permission modes of normal conversations are described in Permission modes; none of them applies here.

Two possible endings, and they don't look alike. If the agent produced text, the wakeup is recorded as “Succeeded”. If it produced no text, it is treated as a failure — even if the work did happen. A wakeup instruction must therefore always ask for a written answer, if only a one-line report.

A conversation that stayed empty is deleted. If the turn fails before writing a single message, the conversation created moments earlier is erased. You don't end up with a list of empty shells after a provider outage.

The one-off wakeup: once, truly

A one-off wakeup disables itself before starting its work, not after. The order is deliberate: the decision “this occurrence is consumed” is written to disk before the action, so that a power cut in the middle cannot produce a second firing on restart.

Note A one-off wakeup does not delete itself. After its single run, it stays in the list, marked “Inactive”. That's useful for finding what it produced; remember to delete it once it's no longer needed.

A one-off wakeup interrupted by the application closing is written to the log with the status “Cancelled”, and stays disabled: it will not fire again on the next startup.

Pausing: one wakeup, or all of them

Two switches exist, and they don't do the same thing.

The individual switch, in a wakeup's detail view, enables or disables that wakeup alone. Its tooltip is “Enable/Disable”.

The master switch, at the top of the side panel, puts everything to sleep. Its tooltip toggles between “Pause all” and “Resume”.

The master pause proceeds in two steps. Every enabled wakeup is disabled and marked as switched off by the pause; on resume, only the wakeups carrying that mark are switched back on.

Note Resuming only wakes what the pause put to sleep. A wakeup you had disabled yourself stays disabled after a master pause followed by a resume. That's intended: the pause is a parenthesis, not a reset.

While paused, the individual switch is locked and its tooltip becomes “Wakeups paused — disable the master switch”. A wakeup created during the pause is born disabled and will start up on resume. Finally, no moment is computed at all: the “Next run” field stays empty for every wakeup as long as the pause lasts.

If Beaver wasn't there at the scheduled time

That's the question everyone asks, and the answer is clear-cut.

Beaver remembers the date of its last run. On the next startup, it compares that date with the present time and looks, for each enabled wakeup, for the occurrences that fell in the interval. Each one is written to the log with the status “Missed” and the reason “The wakeup was missed while Beaver was unavailable.”

Warning A missed occurrence is never caught up. It is noted and recorded, not run. A missed 8 a.m. daily report will not be produced at 10 a.m. when the application launches: it will be flagged as missed, and the next one will be tomorrow's.

A five-minute tolerance separates “late” from “missed”. A wakeup fired four minutes late — machine coming out of sleep, disk busy — runs normally. Beyond five minutes, it is classified as missed.

Closing the window doesn't mean the same thing everywhere, and that's the main trap of this area.

What closing the main window does, by system
SystemClosing the windowDo wakeups keep running?
macOSThe window is hidden, the application stays aliveYes
Windows, LinuxThe application quitsNo

Two advanced settings serve exactly this need: “Launch at startup” — “Open Beaver automatically at system startup” — and “Start hidden” — “Start in the background without opening the window”. Together, they make sure Beaver is there when the time comes, without you having to think about it. See Application settings.

On a deliberate shutdown, running wakeups are notified and waited for within the time budget shared by the whole shutdown. A wakeup interrupted there is recorded as “Cancelled”, not “Failed”.
