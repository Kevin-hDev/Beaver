Searching in the project.

Two tools make up the File search group, locked and impossible to turn off. They answer two different questions: where a word is written, and which files carry a given name.

Two tools, two questions

The question the agent asks itself, and the tool it picks
The agent's questionTool
"Where is this word written in the project?"grep — searches the content
"Which files carry this name?"glob — searches by file name

Neither modifies anything and they never ask for approval. They start from the working directory by default and can target a subfolder; as everywhere, the folder they target must stay inside the areas allowed for reading.

A side effect worth knowing: a file that appeared in a search result is recorded as "seen". It therefore becomes editable without a fresh read — see the "read before write" rule.

Searching the content

grep searches for a regular expression in files.

  • Every match comes back as path:line:content. The line number is always there: the agent can therefore quote an exact location.
  • The search is case-sensitive, with no way to prevent it.
  • There are no context lines around a match, no "file list only" mode, no count mode. A single mode: the lines that match.
  • A file name filter can narrow the search — to files with a single extension, for instance. That is what makes a search fast on a large project.
  • The pattern is limited to 500 characters.
  • The regular expression syntax is Rust's: no back-references, no lookahead. A pattern that uses them is rejected with an explicit message, and the agent rephrases it.
Careful grep is case-sensitive, always, with no option to turn that off. A search for Config does not find config. The agent knows this and adapts its pattern; if you read the command, know it too.

Searching by file name

glob lists the files whose path matches a name pattern.

  • The syntax is that of classic file patterns: * for any sequence of characters, ? for one character, ** to cross subfolders, [abc] for a choice of characters, {a,b} for an alternative.
  • Only files are returned, never folders.
  • Paths come back absolute, one per line.
  • The order is not guaranteed: it depends on the file system and is not alphabetical. This matters if you compare two runs.
  • The pattern applies to the path relative to the starting folder, not to the absolute path.

What gets searched

Both tools completely ignore Git's exclusion rules. That is an explicit choice, and it has consequences:

  • hidden files are searched;
  • files listed in a .gitignore are searched — including node_modules, build folders and caches;
  • the environment and secret files present in the project are searched.

Two practical effects. First, a search on a project with its dependencies installed is slow and noisy: the agent quickly learns to filter by extension or target a subfolder, but the first search in a conversation can cast a very wide net.

Second, the agent sees the project's configuration and environment files. That is intended, and it is necessary: an agent blind to a .env file concludes it does not exist and heads down a false trail — it will offer to create a configuration that is already in place. Every command-line development assistant works this way. The protection does not live in what the agent can see, but in the permission mode, the disk access scope and the choice of model.

A workaround exists, and it is even suggested to the agent: go through a shell command when it needs a view that respects Git's exclusions.

Note Git's exclusions are not honoured: hidden files, dependency folders and build artefacts are all searched. This is deliberate, at the cost of a slower broad search.

The result limits

Number of results before the search stops
ToolMaximum results
grep250 matches
glob100 files

Beyond that, the search stops and the result carries a truncation note. It does not carry on silently.

A second limit comes further down the chain: the result passed to the model is capped at 10,000 characters for grep and 5,000 for glob. A longer result is reduced to a preview, the full text being written to disk and readable back by the agent.

When no file matches, the result says "(no results)" — never an empty answer.

When a search takes too long

  • A search is abandoned after 600 seconds, or ten minutes, with a timeout error flagged as retryable.
  • This limit is very generous on purpose: it exists to stop a search launched across an entire disk from blocking the conversation indefinitely, not to pace ordinary searches. A normal search takes less than a second.
  • The stop is clean: the work in progress is interrupted, it does not carry on in the background.

What escapes these tools

When some files or folders could not be read — insufficient rights, broken link, file being written — the result is marked as partial and gives the number of skipped items. It never claims to have searched everything.

If no file could be read, that is an outright error, not an empty result. The distinction matters: "I found nothing" and "I could read nothing" do not lead to the same conclusions.
