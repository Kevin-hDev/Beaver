What protects you, and where it stops

This page answers four questions: what leaves your machine, what never leaves it, what protects you, and where the limits are. Every protection is written with the condition that turns it on — a protection announced without its condition would be a lie by omission.

Warning Beaver starts in full access. On installation, the agent can run its tools without asking anything, across your whole disk. That is the original setting and it is deliberate: Beaver is built to work inside your projects. If you prefer to approve each action, switch to Ask permission and restrict disk access to your working folders. These are the two most important settings in the app.

A desktop app, not a service

Beaver runs on your computer, with the rights of your user account. There is no Beaver server, no account to create, no synchronization. Three consequences.

  • Your data stays as files on your machine. Everything lives under ~/.local/share/cl-go-dash/, identical on macOS, Linux and Windows.
  • What goes out to an outside service goes out because you asked for it — by choosing a cloud model, a connector, a web search or a messaging channel.
  • Beaver cannot protect you from what you authorize. An agent in full access does what the model decides, with your rights.

The local Ollama engine only listens on the loopback: it is started on 127.0.0.1 and its port is reserved there. No machine on the network can query it. The SearXNG meta search engine, when used, is bound to 127.0.0.1 in the same way.

What never leaves it

  • Your API keys. They only leave the vault for the HTTPS request that uses them, and the interface cannot read them.
  • The content of your messages in the external channels' audit log. A line there holds the timestamp, the channel, the account identifier, a fingerprint of the user identifier, the type of action, a decision code and an error category. Nothing else: the text of the message is never written.
  • The raw body of the providers' answers. Before anything is written to the traces, it goes through a function that masks the recognized secret formats and truncates to 200 characters.
  • Approval requests. Even when a conversation is driven from Telegram, Slack or Discord, an approval request is not sent into the messaging app: it appears in the Beaver window.

Layer 1 — The agent's permissions

The default mode is Full access. On the first installation, Beaver starts in this mode, and it returns to it if its settings file is missing, unreadable or holds an unknown value. In full access, the agent runs its tools without ever asking: writing a file, running a command, changing a Git branch.

The recommendation, plainly: switch to Ask permission unless you have a precise reason to stay in full access. The detail of the three modes is in Permission modes.

A ceiling protects the external channels. When a conversation arrives from Telegram, Slack or Discord, the bridge asks for full access, but that request is capped by your setting: if the mode requested is more permissive than yours, yours is the one that is kept. An external channel can never obtain more rights than the ones you consented to in the app.

Warning Nobody approves in your place, remotely. No approval request is sent into the messaging app: it appears in the Beaver window, on your computer. A sensitive action requested from Telegram therefore waits in front of your screen — it cannot be approved from the phone.
Warning Scheduled wakeups are the exception. A conversation triggered by a wakeup runs in Full access, even if your manual conversations are in Ask permission. It is a deliberate choice: a wakeup works with nobody in front of the screen, and an approval request with nobody to answer it would block execution instead of protecting it. Your consent is given when you create the wakeup and write the task it will run. Only automate what you would accept leaving to run unattended.

Layer 2 — The system sandbox, and its condition

A sandbox, here, means that the operating system confines the command inside a space it cannot get out of. It is Beaver's strongest argument, and it is conditional: the two halves are read together.

What Beaver does. When you restrict the agent's disk access to one or more folders, each shell command is no longer launched directly: it goes through an intermediate process that applies an isolation policy before running the command. That policy is enforced by the operating system kernel, not by Beaver's code.

The isolation mechanism used on each system
SystemMechanism
macOSSeatbelt, with a policy profile generated for the occasion
LinuxLandlock, read and write rules set per path
WindowsA dedicated AppContainer, with rights granted folder by folder
Security A protection guaranteed by the system, not by Beaver. It is the only Beaver setting whose effect does not depend on Beaver working correctly: even if the app is at fault, the kernel refuses the access.
Warning And it does not switch itself on. This sandbox is conditional on restricting the disk scope. The original scope is the root of the disk — / on macOS and Linux, C:\ on Windows — and as long as the agent has access to the whole disk, its commands run with no isolation at all. That is the most concrete reason to declare your working folders: you are not just limiting a scope, you are switching a protection on.

What the restriction controls besides. Every path coming from the interface is first validated in its shape — absolute path, no control character, no .. segment, at most 4,096 characters — then resolved, symbolic links and shortcuts included, then compared against the allowed roots. At most 70 folders can be declared.

Layer 3 — The key vault

Your API keys are stored in an encrypted file, secrets.enc, in XChaCha20-Poly1305. The key that opens that vault is not on the disk: it lives in the system keyring — Keychain on macOS, Credential Manager on Windows, the desktop secret service on Linux. It is read only once at startup. None of the commands exposed to the app's JavaScript code returns a secret; the detail is in The vault and API keys.

Warning The vault protects your keys, not your conversations. secrets.enc is encrypted; your conversations, on the other hand, are stored in the clear in your home folder, protected by the file system permissions alone — 0600 for files, 0700 for folders on macOS and Linux, a restricted access list on Windows. In other words: readable by any program run under your account. Treat ~/.local/share/cl-go-dash/ as a sensitive folder, and reread a log before sharing it.

Layer 4 — The bounds

Beaver caps what it can consume, so that a runaway — an agent loop, an oversized answer, a flood of incoming messages — ends neither in memory saturation nor in a full disk.

Two mechanisms deserve an extra sentence. Requests that carry a secret are held tight: the HTTP client used for those requests refuses any redirect and accepts HTTPS only, the sole exception being a local service on the loopback — a malicious redirect therefore cannot carry a key off to a third-party server. External channels are closed to strangers by default: a message coming from Telegram, Slack or Discord is only processed if its sender appears in the account's allowed users list, and the * wildcard is refused when that list is built. A sender who is absent is blocked and logged, then a per-user rate limit applies.

Layer 5 — Extensions and connectors

MCP connectors are hardened. Beaver only agrees to launch three programs — npx, uvx, deno —, never goes through a shell, and clears the parent process environment before passing on an explicit list of variables. Your environment variables and your secrets therefore do not leak to a connector by simple inheritance. See MCP connectors.

Extensions are not in a sandbox. An extension you approve is trusted code: it runs with the rights of your account, can read and write your files, launch programs, use the network, and ask for your keys through the development kit's programming interface. The isolation by process — one host process per third-party extension — protects the app's stability, not your data.

What Beaver guarantees nonetheless: an explicit double decision — install, then trust —, a fingerprint of the files that revokes the approval as soon as they change, an identity assigned by Beaver rather than declared by the extension, and a log of every secret handed over. The detail is in Extension center.

The limits we own up to

  • The default mode is the most permissive one — full access across the whole disk. Switch to Ask permission and restrict the disk scope.
  • Without a scope restriction, no command is isolated. Declare your working folders: that is what switches the kernel protection on.
  • Scheduled wakeups run in full access, whatever your setting. Only automate what you would accept leaving to run on its own.
  • The code of an approved extension is constrained by nothing. Read the code before approving; if in doubt, revoke the key at its provider, not just the extension.
  • Your conversations are not encrypted. Treat the data folder as a sensitive folder, and reread the logs before sharing them.
  • There is no code signing on the macOS binaries. Install through the script provided rather than through the browser — see Installation troubleshooting.

What is out of Beaver's reach

Three cases no desktop app can cover: physical access to an unlocked machine, where everything is readable under your session; malware already running under your account, which has the same rights as Beaver; a compromised system keyring, where the vault's master key lives — if the keyring falls, the vault falls. That is a property inherent to storing secrets on a workstation, not a choice made by Beaver.

The five settings that change everything

In decreasing order of effect.

  • Restrict disk access to your working folders — the only gesture that switches on a kernel protection.
  • Switch to Ask permission — see Permission modes.
  • Choose a local model for any sensitive content — see Choosing your model.
  • Only approve an extension after reading its code — and revoke the key, not just the extension, if in doubt.
  • Restrict the allowed users list on every external channel — see External channels.
