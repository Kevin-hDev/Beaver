Twenty models on your machine

Beaver's forecast catalog holds twenty models that run without a network, spread across ten families. This page says what each one can do, what it asks of your machine, and what really happens during an installation.

What a forecast model is in Beaver

A forecast model is a weights file downloaded onto the machine, together with a Python environment that knows how to run it. Those two pieces are installed separately and counted separately — that's the key to understanding the states and messages shown.

A model belongs to a family, and the Python environment is shared by an entire family: installing a second Chronos-Bolt model doesn't reinstall the engine.

The interface's vocabulary: Install, Prepare, Installed, Preparation required, Update required, Uninstall, Disk size, RAM, Max horizon, Frequencies, Model capabilities, Engine used.

Key point A model is two installations: the weights on one side, the Python environment of its family on the other. That's why the button sometimes reads Prepare instead of Install — the weights are already there, only the engine has to be rebuilt, and nothing is downloaded again.

The adjustable parameters, by family

Each family exposes its own list of settings, shown under Parameters. Four appear almost everywhere: raising the model's horizon bound, choosing how many past points it looks at, requesting quantile levels in addition to the chosen interval, and preventing negative forecasts.

The others are specific to a family: decoding block size and presence of missing values for Toto; batch size for MOIRAI; scale factor and dimension order for FlowState; probabilistic output for TabPFN-TS; output type — quantiles or mean — for TiRex; positivity preservation, averaging with the reversed input and generation for Kairos; number of samples and numeric precision for Sundial.

At most 16 quantile levels are kept, and the three levels of the chosen interval are never evicted by levels added by hand.

What happens during an installation

1. Downloading the weights. The files come exclusively from Hugging Face, at a pinned revision written into the application — a precise version identifier, never a moving branch. Any other destination is refused, including after a redirect. The download happens in a separate staging folder; the final folder is only replaced at the very end, by an indivisible rename. An interruption along the way therefore leaves either the old installation whole, or nothing — never a half-written model.

2. Verification. Each downloaded file has an expected size and fingerprint. Verification reads the whole file and compares; any difference makes the installation fail. The result is recorded in a receipt dropped next to the weights.

3. Preparing the Python engine. Beaver creates an isolated Python environment for the family, then installs the libraries into it. Four points matter:

  • Python 3.12 exactly has to be present on the machine. Neither 3.11 nor 3.13. Without it, the message is “No compatible Python runtime available”.
  • Each library is pinned and verified by fingerprint, and installed from the official public repository only. A list containing an unpinned package, an extra repository or a local source is refused before it even starts.
  • The engine is prepared alongside too, then swapped into place once validated.
  • If preparation fails, the engine prepared for nothing is removed — unless it already existed beforehand.

4. The smoke test. Before declaring the model ready, Beaver runs it once for real, on the processor and with no network access. The test gets fifteen minutes; beyond that, it is stopped and the installation fails. That's why the end of an installation can feel long even though the download is finished.

How to read the progress bar
What the bar showsWhat's happening
From 0 to 70%Downloading the weights

The installation can be cancelled: the Cancel button is present throughout, and the Esc key does the same thing. Cancelling erases the staging folder.

Warning Python 3.12 has to be installed on your machine — exactly that version, neither 3.11 nor 3.13. Without it, no local model can be prepared.
Note Everything is verified, nothing is taken on trust. The weights come from a pinned version and are checked file by file against their fingerprint; the Python libraries are pinned to a version and a fingerprint. A single difference makes the installation fail rather than letting it through.

The four states of a model

A model's states and what they mean
Label shownWhat it means
Not installedThe weights aren't on disk
No label of its ownThe files are there but their sizes no longer match what is expected; the installation has to be run again
Update required / Preparation requiredThe weights are there, but the receipt, the Python engine or the smoke test are no longer up to date
InstalledEverything is verified, the model is usable

Reaching the Installed state requires five simultaneous conditions: weights present with their completion marker, sizes matching, receipt up to date, family engine ready, smoke test passed.

A Beaver update can send a model back to “Preparation required” without anything having moved on disk: it's enough for a library version to have changed in the pinned list. The button then reads Prepare instead of Install, and the weights aren't downloaded again.

Hardware: what Beaver checks before launching

Every model entry carries three figures: the size on disk, the system memory required and the video memory required. Beaver measures the machine and compares.

The comparison rule between the stated requirement and the machine
VerdictCondition
ComfortableAvailable memory is at least double the requirement
ConstrainedIt covers the requirement plus 20% margin, without reaching double
InsufficientIt doesn't cover the requirement plus 20%
UnknownThe measurement failed

Beaver keeps the better of the two verdicts, graphics card and processor: a model that doesn't fit on the graphics card stays usable if it fits in system memory. An Insufficient verdict gives “Insufficient resources for this model”; an Unknown verdict on a model asking for more than 2,048 MB gives “Resources unavailable for this model”. This check is done at every forecast and before every model evaluation.

On an Apple silicon Mac, memory is shared: the available system memory also serves as video memory in the calculation.

Note Beaver adds 20% to the stated memory. A model asking for 4,200 MB is only launched if 5,040 MB are genuinely available. Below that, it refuses instead of starting a calculation that would crawl or fail halfway through.

Uninstalling

Uninstalling happens in three steps: the staging folder possibly left over from an interrupted installation, then the model's folder, then the family's Python engine — but only if no other model from that family is still installed.

Uninstalling a Chronos-Bolt while another model from the same family is installed therefore doesn't touch the engine, and the second one stays usable straight away.

The action asks for confirmation, and it is unavailable while a download is in progress. There is no undo afterwards: reinstalling means downloading again.

Confidence intervals: two behaviors

Not every model can produce the interval you ask for, and Beaver doesn't pretend.

The confidence levels accepted, by family
BehaviorFamilies concernedWhat's offered
Fixed gridTimesFM 2.5, Toto 2.0, FlowState, TabPFN-TS, TiRex, Kairos60% or 80%, nothing else
ContinuousChronos-Bolt, Chronos-2, MOIRAI 2.0, Sundial, TimeGPT-2Any whole level from 50% to 99%

An unsupported level is refused instead of approximated. It is a deliberate choice: a 90% interval announced by a model that can only produce an 80% one would be wrong with nothing to flag it.
