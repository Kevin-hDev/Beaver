Forecasting in conversation.

Forecast is first of all a dedicated space in the application, with its screens, its charts and its exports. Seven tools open a second door: driving Forecast in natural language from a conversation. "Forecast the next three months of sales for me from this file" becomes a series of tool calls, and the result is a saved analysis, which you can then consult in the Forecast space.

They form the Forecast group, optional and off by default.

The three approved tools are the three that consume real resources: they run models, sometimes for several minutes, sometimes in the cloud and therefore at a cost.

The mandatory sequence

The order of the calls is imposed. No forecast can be run without a prior audit. The audit produces a data profile identifier which then acts as a pass: it is that identifier that is passed to the forecast, not the data itself.

This mechanism has three practical consequences: the data only travels once, whatever the number of forecasts; the requested confidence level is tied to the profile and can no longer be changed along the way; data problems are detected before a model runs, not after.

What is audited before any forecast

The audit checks a dozen points, and that is what sets Forecast apart from a simple call to a model:

  • validity of the dates and chronological order;
  • duplicates and missing periods;
  • consistency of the declared frequency;
  • length of the history — enough data to forecast;
  • number of series and presence of future rows;
  • validity of the numeric values and outliers;
  • prediction budget — is the requested volume still manageable.

A failing audit prevents the forecast. The agent cannot override it.

Key point No forecast without an audit. Dates, duplicates, gaps, frequency, history length, outliers: the data is checked before a model runs.

Choosing the model

Two policies, set in the Forecast space, and the very definition of the tools changes with the active policy: the agent does not see the same parameters in the two cases.

In manual mode — you have designated a model. The agent has to check that this model supports the requested confidence level, and stick to it. If no model is designated, its instruction is to ask you to choose before any forecast.

In automatic mode — the agent consults the list of models usable for this data profile, picks a single one, and passes its choice along with:

  • a short-lived selection identifier, issued at the moment of the consultation;
  • the origin of the choice: the agent's decision, or an explicit request from you;
  • structured reasons, picked from a closed list: best validation result, beats the baselines, accuracy requested, speed requested, local execution required, cloud allowed, requested by the user, suited to the hardware.

These reasons are not decorative: they make the choice of model traceable. You can find out why a given model was picked, without having to believe a freely worded justification.

Note The confidence level is never rounded. If a model cannot produce the requested interval, it is not a candidate — the request is not degraded to make it fit.

Validating a forecast

A forecast on its own does not say whether it is any good. Validation by rolling windows answers that question: the model is replayed over past periods whose result is known.

  • The model is compared against four baseline methods: the previous value, the value from the same period of the previous season, a simple trend, and exponential smoothing.
  • Up to 5 models evaluated on the same windows, 3 windows by default, 5 at most.
  • The results are saved on the analysis.

Two strict instructions frame the agent here: never present a partial validation as complete — it has to inspect the model failures — and never call a model "best" if it does not beat the baseline methods. A sophisticated model that does no better than "tomorrow will be like today" is not a good model, whatever its reputation.

The comparison returns the accuracy measures, the actual coverage of the intervals, the duration and the observed memory — without ever returning the raw data.

Enriching an analysis

On a saved analysis, the agent can annotate — add a dated note — and create a scenario in two shapes:

  • a percentage adjustment — "what if everything went up by 15%?", which derives a curve without rerunning the model;
  • a contextual adjustment — changing an explanatory variable known for the future and genuinely rerunning the model.

It can also modify or delete a scenario, and build an ensemble out of several validated models — from 2 to 4 models, weighted by their performance. A notable detail: an ensemble is explicitly marked as not independently validated. Beaver refuses to let anyone believe that a combination of validated models is itself validated.

What the agent is not allowed to do

Several advanced analyses — decomposition of the series, residual anomalies, variable importance, drift — are computed automatically by Forecast. The instruction given to the agent is unambiguous: read them, never fabricate them. Likewise, when an analysis is unavailable or unreliable, it has to say so as such rather than replacing it with a rough calculation of its own.

Key point The statistics come from the engine, never from the language model. Forecast is built to stop the model inventing figures: an unavailable analysis is announced as unavailable.
