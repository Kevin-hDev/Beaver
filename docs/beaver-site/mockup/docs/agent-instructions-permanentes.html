Standing instructions

Instructions the agent applies to every conversation, without you having to repeat them. Six sources are assembled in a precise order, and that order decides who wins in case of contradiction — the thing to know when an instruction seems ignored.

The two mechanisms

AGENTS.md and personality, two ways of doing it
AGENTS.mdPersonality
ContentConventions, project commands, prohibitionsTone, behavior, way of working
ScopeGlobal and per projectGlobal

The two stack. A third mechanism exists for what has to evolve on its own: memory. The distinction is worth stating — AGENTS.md is what you write, memory is what the agent keeps.

AGENTS.md — the assembly order

Six sources, assembled in this order.

The order in which sources are read
OrderSourceLocation
1Global instructionsAGENTS.md in the data folder
2Enabled imported instructionsDocuments carried over from another assistant
3Selected external rulesImported rules, sorted by source
4Project instructionsAGENTS.md at the root of the project
5Project instructions.cl-go/AGENTS.md inside the project
6Project rules.cl-go/rules/*.md, sorted by file name

The whole is preceded by a header telling the model that it must follow these instructions to the letter, and that the project instructions, being more specific, come after the global ones. Each section is labeled with its origin, which lets the model tell a global instruction from a project one.

Who wins in case of contradiction Project instructions are read after the global instructions, and the model is explicitly told they are more specific. In case of contradiction, the project should win.

Where to put your instructions

  • What holds for all your work → AGENTS.md in the data folder, editable from the application.
  • What holds for one project → AGENTS.md at the root of the project. It is versioned with the code, so it follows the repository and benefits the whole team.
  • Many rules on one project → separate files in .cl-go/rules/, one per subject. They are read in alphabetical order: number them to fix their order.
AGENTS.md is versioned Placed at the root of a project, AGENTS.md follows your Git repository. The whole team then works with the same instructions.

Personality

Markdown files that can be enabled individually. Four exist on installation, all disabled by default, and they do not all live in the same place.

The four personality files
FileLocationPurpose
identity.mdmemory/core/Who the agent is
principles.mdmemory/core/Its working principles
user.mdmemory/core/Who you are
idea-discovery.mdinbox/Its way of exploring ideas

Only the enabled files are injected; the enablement of each is recorded in personality-injection.json. To those four is added the global AGENTS.md file, presented on the same screen: it is that one the application edits when you edit AGENTS.md from the Personality section — never a project's.

The list is fixed. The three locations and the file names are set by the code: a file dropped by hand into memory/core/ will not appear on the Personality screen and will never be injected.

Where standing instructions are not injected

Warning In two situations, neither AGENTS.md nor the personality files are injected: in Chatbot mode and in a subagent session. An instruction that seems ignored in either of those cases really is — it was not passed on.

For subagents, this is consistent with their principle: a child sees nothing of the parent conversation. But if you have written your project conventions into AGENTS.md, you need to know they do not follow them, and to restate them in the delegation instruction.

The size limit

200 KB in total, all sources combined. When the limit is reached, the remaining instructions are omitted and a warning is added.

An important point: the order decides what survives. The sources read first — the global instructions — get through; those at the end — the project rules — are the first to be sacrificed. If you accumulate rules, lighten the global ones first.

Writing good instructions

  • Be imperative and precise. “Use npm test before concluding” rather than “tests are important”.
  • Give the reason when it is not obvious. A rule without its why only covers the cases you foresaw.
  • Do not duplicate between global and project: two overlapping instructions end up contradicting each other on an edge case.
  • Stay brief. These instructions take up context in every conversation, out of the 200 KB available.
