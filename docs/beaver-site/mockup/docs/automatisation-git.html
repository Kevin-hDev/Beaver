Git, without leaving Beaver

Beaver can switch branches, commit, push and merge without you opening a terminal. It doesn't claim to replace Git for all that: several common operations don't exist in the application, and this page starts by naming them. Better to know right away what stays in the terminal than to find out at the first error message.

Warning Beaver never retrieves anything from the remote repository. No fetch, no pull: neither operation exists in the application. The lag shown against the remote — “Remote changes are available” — is computed from what your local repository already knows, and it is only refreshed by a fetch started elsewhere, or by a successful Push from Beaver. To stay up to date, keep a terminal alongside.

Two words deserve clarification. “Clone” in Beaver is not about Git: it refers to cloning a conversation, described in Cloning a conversation. And “resolving a conflict” doesn't exist: when a merge produces one, Beaver cancels it cleanly instead of leaving you in an intermediate state — the resolution happens in the terminal or in an editor.

Where it happens in the application

Git appears in two places, with different roles.

The branch selector, in a conversation's control bar. It carries the current branch's name and opens a menu containing a “Search branches” field, the list of “Branches”, the list of “Worktrees”, the “Uncommitted: {{count}} file(s)” counter and the “Create and checkout a new branch…” entry.

The Git section of the conversation summary, which carries the actions and the history: the “Commit”, “Push” and “Merge into {{branch}}” buttons, then the list of “Commits”.

When the folder is not a Git repository, the branch selector disappears entirely and the summary shows “No Git repository”. Nothing is shown broken: what isn't usable is invisible.

The entry condition: a registered project

Every Git operation goes through the same check: the folder must exist and sit inside a project registered in Beaver. A repository opened any other way is refused.

A subfolder of a repository works: detection walks up the tree to the parent repository. On the other hand, a repository without a working folder — a so-called “bare” repository — is refused.

Switching branches, creating one

Only local branches are listed: remote branches don't appear, which follows directly from the absence of fetching. The current branch comes first, the others in alphabetical order, and the list stops at 500 branches.

Creating a branch starts from the current position and switches to it right away, without committing anything: your work in progress stays in place and follows onto the new branch.

The name is checked as you type and at creation time, with the same rules on both sides.

Three further refusals exist: the branch already exists — “This branch already exists”; the repository has no commit — “The repository has no commits. Create a commit first”; the GitHub connector isn't connected — “Connect GitHub before creating a branch”.

Warning GitHub is required even for a purely local branch. If one of your repository's remotes points to GitHub — in the form https://github.com/, ssh://git@github.com/ or git@github.com: — Beaver requires the GitHub connector to be connected before creating a branch, including when that branch will never be published. A dialog offers it on the spot: “Connect GitHub to create a branch”, with the “Connect GitHub” button. Failing that, create the branch in the terminal. The connector is described in MCP connectors.

Switching branches is refused if uncommitted files remain, and the refusal comes before Beaver touches the disk: it doesn't try to check out and then undo. The dialog is titled “Commit changes to switch branch” and explains: “Changes to the following files would be overwritten by checkout:”. It offers “Commit and switch branch…”, which creates a save commit then checks out. If nothing has changed, the checkout happens directly, with no commit.

Uncommitted changes

Pending files are classified “Created”, “Modified”, “Deleted”, “Renamed” and “Copied”, each with its number of lines added and removed.

The list stops at 200 files, but the real count is kept and the cut-off is announced: “{{count}} files changed. The displayed totals are partial.”

For a new file, lines are only counted below 1 MB. Beyond that, Beaver reports zero rather than read a big file — a bulky addition can therefore appear with a line count of zero.

Committing: “Commit”

The dialog is titled “Commit changes”, with the “Commit message (optional)” field and the “Commit” button.

Note The commit takes everything. There is no file selection: the button commits the entire working folder. To split work into several commits, go through the built-in terminal.

The message is optional. Left empty, the commit carries an automatic save subject. There is no minimum length, a maximum of 2,000 characters, line endings are normalised, and control characters other than newline and tab are refused — the error message is then “The commit description is invalid or too long.”

If there is nothing to commit, the operation succeeds doing nothing. No empty commit is created.

The commit author is your Git identity, looked up first in the repository's configuration, then in the one git declares. If no identity is configured, the commit fails with “Configure your Git name and email address before creating a commit.” — Beaver never fabricates a substitute author.

One discreet safeguard is worth knowing: before each commit, the repository's index file is copied; if the commit fails, the original index is put back. A failed commit doesn't leave the repository in an intermediate state.

Publishing: “Push”

The indicator above the button reads “{{count}} commit(s) to Push to {{destination}} · {{branch}}”, the destination being “GitHub” or “the remote repository”.

Beaver pushes the current branch to its remote, without forcing. The remote is chosen in this order: the one configured for the branch, then origin, then the first in the list. After a successful push, Beaver updates the local remote reference and sets the upstream branch — that is the only moment when the remote's state is refreshed.

Authentication is attempted in a precise order, each step only once: the system's Git credential helper, then the connector's GitHub token — only for an address in https://github.com/ — then the agent's SSH key, then the username, then the default value. If there is no usable credential, the call fails: nothing goes through silently. A GitHub repository over SSH does not use the connector's token.

The five Push refusals and their message
SituationMessage shown
No usable credential“Git authentication is required to Push.”
The remote refuses“The remote repository rejected the Push. Check your access or branch protection.”
The remote branch has moved ahead“The remote branch has newer changes. Sync the repository before pushing again.”
Network unreachable“Unable to connect to the remote repository.”
The branch changed since it was displayed“The project or branch changed. Start the Push again.”

The third case is the one that will come up most often, and it follows from the box at the top: Beaver can't catch up on a lag, since it fetches nothing. The fix is a git pull in the terminal, then a new Push.

Two network timeouts are set to 30 seconds each, for connection and for inactivity. No allowlist of addresses exists: any remote configured in the repository is usable.

Merging: “Merge”

The dialog is titled “Merge into {{branch}}” and explains “Choose the branch to integrate into {{branch}}.”, with the “Source branch” field. The merge is local: a local branch into the current branch, never a remote branch.

The preview announces the scale before acting: “{{count}} commit(s) will be added to {{branch}}.”, and where relevant “{{count}} local change(s) will be Committed before the Merge.”. When there is nothing to do: “This branch is already merged into {{branch}}.”

Four situations cause the merge to be refused: the source is the target or there is nothing to merge; the current branch isn't the expected one; the repository is already in the middle of another Git operation; uncommitted changes remain — unless you choose to commit them first, via “Commit then Merge into {{branch}}”.

Note A conflict breaks nothing. Beaver cancels the merge, then checks that the position has returned to its original value, that the repository is clean and that no file is modified — only after that check does it report the conflict to you, with “The Merge creates a conflict. It was cancelled without changing the branch.”. It doesn't offer to resolve it: that happens in the terminal or in an editor.

The repository's hooks are neutralised during the merge. The hooks path points to an empty temporary folder, cryptographic signing is disabled, and no terminal prompt can block the operation. It is a deliberate security choice: a repository hook is executable code, and a merge started from a graphical interface must not run it without your knowledge. See Security model.

Deleting a branch or a worktree

A preview always precedes the deletion. It announces, where relevant: that this is the current branch and which branch Beaver will fall back to, the uncommitted files, and the number of unmerged commits — “{{count}} unmerged commit(s)”.

The fallback branch is the current branch if it differs from the target, otherwise main, master, develop, dev in that order, otherwise the first other branch. The message is “This branch is in use. Beaver will switch to {{branch}} before deleting it.”; with no fallback branch at all, “Create another branch first so this one can be deleted.”

The three deletion modes

Counting unmerged commits stops at 10,000. A worktree follows the same logic, with the same three modes and a ten-second timeout on the operation; the current worktree, however, cannot be deleted.

Reading the history and the diffs

The history covers the current branch only. It loads in pages of 24 commits, the next one arriving as you approach the bottom of the list, up to 1,000 commits shown. Each commit shows only the first line of its message, capped at 160 characters; with no message, “Commit without a message”. The walk stops at 10,000 commits; beyond that, the list answers “Commit history is unavailable.”. A branch with no commit shows “No commits on this branch”.

Opening a commit shows the files it touches — 200 at most — then, file by file, its diffs. Those are read in two modes: a commit against its parent, or the working folder against the last commit, with three lines of context around each change.

A diff preview is truncated rather than abandoned when it exceeds its bounds, and the truncation is announced: “Limited preview: this file contains more changes.”. A binary file shows no diff, only the indication that it is one; an unreadable file shows “The changes for this file cannot be displayed.”

Previews of versioned files have their own bounds, and any preview error surfaces a generic message: no path, no internal detail is ever shown.

Worktrees

A worktree is a second working folder attached to the same repository: it lets you have two branches open at the same time on disk, without juggling checkouts.

Beaver lists them but doesn't create them. Creation happens in the terminal, with git worktree add.

The list stops at 100 worktrees and excludes two categories: repositories without a working folder, and all the internal worktrees Beaver creates for its own subagents. That's intended — those are temporary working folders, not yours. See Subagents.

Switching worktrees means switching working folder, which can't happen in the same conversation. The “Folder change” dialog explains it — “This worktree uses a different working folder. Create a new session to keep the current conversation intact.” — and offers “New session”.

Automatic change detection

Beaver watches the repository and refreshes its display on its own. Inside the .git folder, it watches the current-position file, the branches folder and the packed references file, grouping changes over 200 milliseconds.

The working folder itself is re-read every three seconds, and the interface is only notified if something has genuinely changed: branch name, position, number of modified files, or a fingerprint of the folder's first entries.

Note What you do in the terminal shows up on its own. A commit, a checkout or a simple edit made outside Beaver appears in the application within three seconds at most, without refreshing anything by hand — including when the number of modified files doesn't change.

Only one repository is watched at a time for the whole application: opening another project stops watching the previous one. And if no .git folder is found, watching doesn't start and reports nothing.
