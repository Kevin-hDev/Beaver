System prompt and extensions

The short answer fits in one sentence: an extension does not touch the system prompt, neither to read it, nor to write it, nor to insert itself into it. Editing, replacing or disabling the system prompt is a native Beaver feature, unrelated to extensions. This page says where customization is configured, what extensions actually do around the prompt, and by which path their text still reaches the model.

System prompt customization is native

Beaver lets you view, edit, replace and disable the system prompt. That setting lives in the application. The prompt actually sent is computed from your saved settings, the model's name, the mode, the level of detail, the Ollama model's native prompt where applicable, and Beaver's default prompt. Four states are possible: default, Beaver prompt, custom, disabled.

No extension figures among those inputs. The full mechanism — modes, scopes, native Ollama prompts, how to edit and restore — is described in System prompts. That is the page to read if you are trying to change the instructions given to the model.

What an extension can do, and what it cannot

An extension talks to Beaver through a closed channel: a list of methods declared in a contract, and nothing else. That list is written once — the version Beaver uses is produced at build time from the same contract file the extension reads. So there is no second, more permissive list anywhere.

The twelve methods an extension can call are app.info, sessions.list, sessions.get, projects.list, mcp.connectors.list, mcp.tool.call, channels.config.get, secrets.provider.get, secrets.mcp.oauth.get, secrets.mcp.env.get, secrets.channel.get and host.load.stage. None of them concerns prompts or agent settings; any other name returns an error.

What an extension can declare: tools, skills, resources, interface elements, and event listeners. In advanced mode, it can additionally cover a native tool — which concerns tools only, and has a page of its own. On the event side, only one exists, session.turn.started: it signals that a conversation turn has begun, it does not allow intervening in how the prompt is built.

Note The "advanced" door is shut, not ajar. An extension declared in advanced mode gets a generic call, beaver.unstable.call(...). You might think it gives access to hidden functions in Beaver's core: it does not. That call only accepts methods marked "advanced" in the contract, and no method in the current contract carries that marking — the twelve declared methods are all stable. The set of methods unstable.call can reach is therefore empty today.
Warning Do not confuse two mechanisms that share a name. In Beaver, "replacement" refers to an extension covering a native tool — web search, for example. It never concerns the system prompt. See Replacing a tool.

The only text Beaver adds because of extensions

There is indeed a paragraph added to the system prompt because of extensions — but it is written by Beaver, not by an extension, and its text is fixed. It is appended at the end of the system message, in Agent mode only; in Chatbot mode, it is not added. It only appears if both discovery tools are active, list_extensions and inspect_extensions; if one is missing, nothing is added.

Its content explains to the model how to consult the extension catalog: inspect 1 to 4 exact identifiers directly, use the full list only for an overview, and never look for an extension by keyword. That text is in English in the code, like the rest of the system prompt.

How an extension's text still reaches the model

This is the important point for security, and it does not go through the system prompt.

Extension skills do not enter the system prompt. The prompt contains a list of available skills, built from the global catalog — and that catalog explicitly excludes extension skills: any entry whose identifier starts with extension: is removed from it. The comment next to the filter says why: that namespace is authorized session by session and must never enter the global catalog.

The content of an extension skill does, however, enter the conversation when the model loads it. The model asks for a skill by its identifier; if that identifier starts with extension:, Beaver loads the Markdown file the extension provides. Two guardrails surround that load: the text is prefixed with its provenance, in the form Skill source: <extension identifier>, so the model sees where the instruction comes from; and the load is refused if the session excludes extensions.

The descriptions declared by the extension are also third-party text seen by the model: a tool's description is mandatory, non-empty and bounded. It is through those descriptions that an extension tool introduces itself to the model.

Security That is the whole difference. An extension's content reaches the model inside the conversation, after the system prompt, and signed with its provenance. It remains a text that the system prompt frames, instead of becoming the frame itself. The system prompt is the only text the model receives before any outside content: it is what sets the rules the rest is supposed to obey, including those governing tool use.
