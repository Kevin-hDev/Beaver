Skills and automations.

Two tools, two separate groups, both on by default and switchable independently in Settings › Agent › Tools. The first loads a guide written in advance; the second schedules a task the agent will carry out on its own, at the appointed time.

The two tools and their group
ToolGroupDefault
load_skillSkillsOn
manage_automationAutomationsOn

Loading a skill

A skill is a guide written in advance: a procedure for a specific task — code review, security audit, interface design. It lives in a file on your disk.

The mechanism has two steps, and that is what makes it frugal. The list of available skills — their name and their short description, nothing more — is present in the conversation at all times; the full content of a skill is only loaded when the agent asks for it, through this tool.

  • Fifty installed skills cost fifty short descriptions, not fifty complete guides.
  • The description decides everything. It is the only thing the agent bases its decision to load a skill on. A vague description gives a skill that never triggers.
  • The agent can only load a skill that is present in the list: identifiers cannot be invented.
  • A skill already loaded in the current turn is not loaded again.

A strong instruction goes with the tool: when a skill matches the request, the agent must load it before saying anything at all about the task. That is what stops it from starting to work its own way and then discovering the guide halfway through.

Key point A skill's description decides whether it will ever be used. It is the only thing the agent sees before loading the guide: a description saying "for reviews" will not trigger, a description saying when to use it will.

What the agent receives from a skill

The injected content is preceded by two pieces of information: where the skill comes from and which folder it sits in. That second point matters, because a skill can refer to neighbouring files — templates, examples, scripts — and the agent needs to know where to look for them.

Checks applied at load time: the identifier cannot contain a slash, .., or a null character; the file must exist, must be a file, and must weigh at most 256 KB; the description header is stripped, only the body of the guide is passed on; the displayed name is reduced to a single line and capped at 120 characters.

What an automation is

An automation is a scheduled agentic task: at the appointed time, Beaver opens a conversation, drops the saved instruction into it, and lets the agent work through to the end, with nobody in front of the screen.

It is a scheduled wake-up like any other: it lives on the same screen as non-agentic wake-ups and shares their common ceiling of 64.

An automation runs in Full access

This is the most important information on this page, and it comes before any procedure. The scheduled conversation is launched in Full access mode, whatever mode you chose for your ordinary conversations.

  • No approval request is possible. Nobody is there to answer, and the mode does not provide for it.
  • Every tool enabled in the application is available — exactly the same list as in an ordinary conversation, read at execution time. Including the ones that write files, run shell commands and delegate to subagents.
  • Every installed skill is available.
  • There is no tool list specific to an automation, neither at creation nor at execution. Nothing is restricted, nothing is refused by nature.
  • An automation therefore has manage_automation at its disposal: it can create, modify and delete others. The only bound is the ceiling of 64 wake-ups.

Setting Beaver to Ask permission does not bound automations. The corollary: whatever you entrust to an automation, you entrust without a safety net. The only control points are the text of the instruction and the choice of tools enabled in the settings — both decided in advance, once and for all.

Warning At the appointed time, Beaver opens a conversation in Full access and lets the agent work alone, with every tool and every skill enabled: writing files, shell commands, delegating to subagents. Before scheduling a task, reread its instruction asking yourself what it allows at worst, and switch off in Settings › Agent › Tools the groups it does not need.

Creating an automation

The agent can create an automation itself — "remind me to check the dependencies every Monday". Its instruction is to create or modify only after your confirmation on three points: the trigger, the instruction and the active state.

Three trigger shapes, and only three
ShapeWhat has to be specified
OnceA date and a time, in the format YYYY-MM-DDTHH:MM
DailyA time, in the format HH:MM
WeeklyA day of the week (0 to 6) and a time

There is no free-form scheduling expression: a cron-style syntax is refused. A one-off date already in the past is refused if the automation is created active.

What an automation freezes

At creation time, it takes from the current conversation and freezes the model, the provider and the project if there is one. It additionally records its name, its description, its instruction, its trigger, its active state and its creation date — and nothing else.

The provider is checked at creation: a provider that does not accept automation requests — some connected web accounts, reserved for interactive use — makes creation fail with "Provider not supported".

Modifying and deleting

  • Modifications are partial: whatever is not supplied stays unchanged. The model, the provider and the project cannot be changed through this tool.
  • Deletion requires an explicit confirmation in the call. Without it, the call is refused — that is the protocol's only technical guard.
  • Only agentic automations are concerned: the tool does not touch the other scheduled wake-ups.
  • Any creation, modification or deletion notifies the scheduler immediately — the change takes effect without a restart.
  • When wake-ups are globally paused, an automation created or modified as active is saved but paused, and marked as such. It resumes when the global pause is lifted.
