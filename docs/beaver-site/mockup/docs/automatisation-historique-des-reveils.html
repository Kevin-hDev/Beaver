Knowing what a wakeup actually did

Every wakeup run leaves a trace: succeeded, failed, missed or cancelled, with its reason when there is one. This page says where to read those traces, how to interpret them, how long they stay — and what they never contain. Creating and firing wakeups is covered in Scheduled wakeups.

Note The history is per wakeup, and short. It appears in a wakeup's detail view, not on a screen shared by all of them, and shows the last eight runs. The file on disk keeps more, all runs combined.

Where the history is read

There is no general screen listing every run of every wakeup. The “History” section is rendered at the bottom of a wakeup's detail view, filtered to that wakeup alone. When it has never run, it shows “No runs yet”.

Two summary pieces of information appear higher up in the same view: “Last status” and “Last run”.

The display refreshes on its own. The log is watched on disk: a wakeup that finishes while the detail view is open makes its line appear immediately, without you having to reload anything.

What a run records

The log is a file of lines, ~/.local/share/cl-go-dash/logs/wakeups.jsonl — one line per run, each independent of the others.

What a log line carries
InformationContentAlways present
Wakeup identifierThe wakeup concernedYes
Scheduled momentThe time the wakeup was due to fire, in local timeYes
Recording momentThe time the result was writtenYes
StatusSucceeded, failed, missed or cancelledYes
ReasonOne of the seven codes in the next sectionOn failure or miss
Conversation producedThe conversation created by the wakeupOn success
Tokens producedAn estimateOn success

Identifiers are cleaned before being written: only letters, digits, hyphen and underscore are kept, and the length is cut at 128 characters. An identical line is not written twice: Beaver keeps in memory what it just recorded and discards the duplicate.

Runs are returned from the most recent to the oldest.

The four statuses

What each status means
StatusWhat happened
“Succeeded”The agent produced text
“Failed”The turn failed, or produced no text
“Missed”Beaver wasn't running at the scheduled time
“Cancelled”The application closed during the run

When no run has ever taken place, the “Last status” field shows “Never run”. When a date is missing or unreadable, the interface shows “None”.

The seven failure reasons

A “Failed” or “Missed” status carries a reason, rendered on screen as a complete sentence.

The seven reason sentences and what triggers them
Sentence shownWhen it appears
“The wakeup failed.”Default reason, when no other one matches
“The provider request limit was reached.”The provider refused on rate grounds
“Provider authentication failed.”API key missing, expired or refused
“Ollama was unavailable.”The local engine did not answer
“The wakeup was missed while Beaver was unavailable.”Occurrence found missed on the next startup
“The wakeup did not start because Beaver was closing.”The time fell during the application's shutdown
“The wakeup did not start because too many operations were already running.”More than 64 wakeups at once
Note The reason is a hint, not a diagnosis. Three of the seven — request limit, authentication, Ollama — are inferred from the text of the error returned by the provider, not from a code it would supply. An outage worded differently falls back to “The wakeup failed.”. That doesn't mean the cause is unknown, only that Beaver couldn't name it: open the corresponding conversation, it carries the detailed error.

A reason Beaver doesn't recognise also falls back to “The wakeup failed.”: a log written by a newer version doesn't break the display.

How long the history is kept

The log is bounded at 500 lines. This is not a line-by-line deletion: when adding a line would exceed the budget, Beaver rewrites the whole file keeping only the 250 most recent lines. The file therefore drops back to 250 and grows again until the budget is reached once more.

Note There is no retention period in days. The bound is a number of lines, shared by all your wakeups: with a single daily wakeup you keep months of history, with twenty wakeups a few weeks. And when the limit is reached, the older half disappears all at once, not line by line. If you want to keep more than that, copy the wakeups.jsonl file elsewhere.

The rewrite is atomic: temporary file then rename. A power cut during a rotation leaves either the old log whole, or the new one, never a mix.

A line that is too long is refused rather than truncated: beyond 2,048 bytes, the write fails. Given what a line contains, this case shouldn't happen; it exists as a safeguard.

On reading, only the last megabyte of the file is scanned, and a cut first line is discarded so as not to produce a truncated record. A file replaced by hand with a much bigger one will therefore not grow Beaver's memory.

What the log does not contain

This is the most important point on the page if you're considering attaching this file to a problem report.

  • Not the text of your instruction — it lives in the wakeup's configuration, not here.
  • Not the agent's answer — it lives in the conversation produced.
  • Not the provider's raw error message — it is reduced to one of the seven reasons before being written. The log therefore contains no excerpt of an external service's response.
Note The log contains nothing sensitive. Only an identifier, two dates, a status and a reason code. It's a file you can attach to a problem report without having to reread it line by line.

When the log itself becomes unavailable, the wakeup isn't interrupted for all that: a warning is written to the traces and the work continues.

A decision not written to the log is not considered taken. If the write fails, Beaver does not advance its last-run date: the occurrence will be re-examined on the next pass. The log is the authority on what has been decided, which prevents a write failure from silently making an occurrence disappear.
