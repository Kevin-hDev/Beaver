Concepts clés

Les mots employés partout ailleurs dans cette documentation, définis une fois. Chaque terme renvoie vers la page qui le détaille quand elle existe.

L'agent et son travail

Agent — le modèle de langage augmenté d'outils. Il reçoit une demande, décide des actions, les exécute, et recommence jusqu'à avoir terminé. La différence avec un chat : le chat répond, l'agent agit.

Conversation (ou session) — un fil de discussion. Chacune a son historique, son modèle, son répertoire de travail, ses outils actifs et ses permissions. On navigue de l'une à l'autre par la barre latérale ; elles ne s'ouvrent pas en onglets.

Clone — une copie d'une conversation arrêtée à un message précis, ouverte dans un onglet à côté de l'originale. Deux modes : abandonner ce qui suivait, ou en garder un résumé. Les onglets n'existent que pour les clones, trois au maximum par groupe.

Outil — une capacité concrète : lire un fichier, lancer une commande, chercher sur le web. L'agent choisit lui-même lequel appeler et avec quels arguments.

Groupe d'outils — les outils sont rangés par famille, et on active ou désactive un groupe entier. Il y a onze groupes : quatre verrouillés — core, web, mcp, extensions — et sept optionnels — workflow, automation, subagents, todo, git, forecast, office.

Outil verrouillé — toujours disponible, non désactivable. Les quatre groupes verrouillés portent quatorze outils : core en fournit huit pour les fichiers, la recherche et les commandes, web deux, mcp un et extensions trois.

Outil optionnel — s'active dans les réglages. 32 outils optionnels peuvent être actifs simultanément, et le catalogue en compte aujourd'hui exactement 32 : le plafond n'écarte donc rien. → Outils — vue d'ensemble

Le contrôle de ce que fait l'agent

Mode de permission — détermine ce que l'agent peut faire sans demander. Trois modes te sont proposés : Accès complet, Demander l'autorisation et Chatbot. Un quatrième mode existe uniquement en interne, pour les sessions enfants ; il n'est jamais proposé.

Garde de permission — le mécanisme qui intercepte une action avant exécution et demande approbation. Il ne s'applique qu'à une liste précise d'outils, et sous conditions pour certains. → Modes de permission

Mode Plan — l'agent explore sans rien modifier, rédige un plan Markdown et le soumet. Aucune écriture n'a lieu avant approbation. Les plans sont conservés dans plans/<session_id>/*.md.

Liste de tâches (todos) — la liste que l'agent tient lui-même pour découper un travail long, visible en direct. Cinq outils lui sont associés : todo_write, todo_history, todo_pause, todo_resume, todo_delete. → Liste de tâches

Répertoire de travail — le dossier auquel une conversation est rattachée. Il détermine ce que l'agent peut lire et écrire. → Répertoire de travail

Projet — un répertoire de travail enregistré, retrouvé d'une conversation à l'autre. Il est stocké dans projects.json.

Déléguer et se souvenir

Sous-agent — une conversation enfant lancée par l'agent principal pour traiter une partie du travail de façon isolée, avec son propre contexte. Neuf outils servent à le contrôler. → Sous-agents

Worktree (copie de travail) — une copie de travail Git séparée, dans laquelle un sous-agent modifie des fichiers sans toucher au dossier courant. Les changements s'inspectent avant d'être appliqués ou jetés. Elles vivent dans subagent-worktrees/.

Mémoire — des notes conservées d'une conversation à l'autre, en portée globale ou par projet, en mode manuel ou automatique. Stockage dans memory/global/ et memory/projects/. → Mémoire persistante

Contexte — l'information que le modèle garde sous les yeux : ta demande, l'historique, les résultats d'outils, la mémoire, les instructions système. Il est limité, et surveillé par l'application. → Contexte

Compression — le résumé automatique de l'historique ancien quand le contexte se remplit, pour que la conversation continue sans être coupée.

Ne pas confondre La mémoire persiste entre les conversations ; le contexte est ce que le modèle voit dans la conversation courante. C'est la confusion la plus fréquente chez les utilisateurs d'agents.

Les instructions permanentes

Prompt système — les instructions données au modèle avant le premier message. Il en existe deux jeux, Chatbot et Agentique, chacun en variante Compact et Détaillée. Ils se consultent, se modifient, se remplacent et se désactivent. → Prompts système

AGENTS.md — le fichier d'instructions permanentes que tu écris, lu à chaque conversation : conventions à respecter, commandes du projet, interdits. → Instructions permanentes

Personnalité — des fichiers Markdown décrivant le ton et le comportement attendus, injectés dans les instructions. Ils sont stockés dans memory/core/.

Skill — un mode d'emploi rangé dans un dossier, chargé à la demande quand la tâche correspond. Dossier skills/, outil load_skill. → Skills

Les modèles

Modèle local — installé sur ton disque, servi par Ollama. Aucune donnée ne quitte la machine, aucun coût par requête, et la performance dépend de ton matériel.

Modèle distant — exécuté chez un fournisseur, atteint par le réseau. Généralement plus rapide et plus capable, facturé à l'usage. → Choisir son modèle

Provider (fournisseur) — le service qui héberge un modèle distant. Onze fournisseurs sont gérés par clé API : Google Gemini, Mistral, Cerebras, OpenRouter, OpenAI, DeepSeek, xAI, Moonshot Kimi, Z.ai GLM, Anthropic Claude et Qwen. → Fournisseurs API

Clé API — l'identifiant secret d'authentification auprès d'un fournisseur. Stockée chiffrée, jamais exposée à l'interface. → Le coffre et les clés API

Compte web — une alternative à la clé API pour trois fournisseurs : OpenAI/Codex, Grok (xAI) et Kimi (Moonshot, expérimental). → Connexion par compte

Ollama — le logiciel qui exécute les modèles locaux. Beaver le télécharge quand tu le lui demandes, puis le pilote pour toi. Il est facultatif : sans lui, seuls les modèles distants sont disponibles. → Moteur local

Raisonnement (thinking) — la phase où certains modèles réfléchissent avant de répondre. Beaver l'affiche, et permet d'en régler l'intensité quand le modèle le supporte. → Raisonnement

Les intégrations

MCP (Model Context Protocol) — un standard qui permet à des programmes externes d'exposer des outils au modèle, et donc d'ajouter des capacités sans modifier Beaver.

Connecteur — une instance de serveur MCP configurée dans Beaver, locale ou distante. La configuration vit dans mcp-connectors.json. → Connecteurs MCP

Extension — un module installable qui modifie l'interface elle-même, distribué et mis à jour depuis une source Git. Une extension peut contribuer son propre onglet de réglages, des entrées de navigation, un thème et des skills, et trois outils verrouillés du groupe extensions la rendent visible à l'agent. C'est ce qui la distingue d'un connecteur MCP, qui n'ajoute que des outils. → Centre d'extensions

Channel (canal) — une passerelle vers Telegram, Slack ou Discord.

Gateway — le service d'arrière-plan qui fait tourner les canaux, associe chaque conversation externe à une session, et journalise les échanges. L'audit est écrit dans logs/gateway-audit.jsonl. → Canaux externes

Ne pas confondre Un sous-agent est une session enfant, un connecteur expose des outils via MCP, une extension modifie l'application. Les trois ajoutent des capacités, par des mécanismes sans rapport.

Automatisation, données, sécurité

Réveil (wakeup) — une instruction programmée, de trois types : once, daily, weekly. Le résultat atterrit dans une conversation dédiée.

Ordonnanceur (scheduler) — le mécanisme interne qui déclenche les réveils. Il est interne à l'application et n'utilise pas les tâches planifiées du système.

Forecast — l'espace de prévision de séries temporelles : audit, choix de modèle, prévision, évaluation, comparaison, export. → Forecast

Backtest — une évaluation qui rejoue le passé pour mesurer la qualité d'un modèle sur des données dont on connaît la suite.

Coffre (vault) — le fichier chiffré contenant les clés API et les jetons. Chiffrement XChaCha20-Poly1305, fichier secrets.enc.

Trousseau (keyring) — le magasin de secrets du système : Trousseau macOS, DPAPI Windows, Secret Service Linux. Il contient la clé maîtresse du coffre, et rien d'autre.

Zéroïsation — l'effacement volontaire d'un secret en mémoire après usage, pour qu'il ne subsiste pas dans un fichier d'échange ou une image mémoire. → Modèle de sécurité
