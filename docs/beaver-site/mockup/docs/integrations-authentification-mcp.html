Authorizing a connector

A remote connector reaches personal or company data: messages, documents, tickets, repositories. So it has to be authorized explicitly, service by service. For that, Beaver uses the standard delegated authorization mechanism: you authenticate with the service, which hands Beaver a limited, revocable access token.

The flow

  • From Settings › Integrations › Connectors, you start the service's sign-in.
  • Beaver opens your browser on the service's page.
  • You authenticate there and accept the access requested.
  • The service redirects back to Beaver, which receives the reply on a small local server active only during the sign-in.
  • Beaver exchanges that reply for an access token and stores it in its vault.
  • The browser shows a confirmation page.

The sign-in is abandoned after 5 minutes without a reply. Up to 5 sign-ins can be in progress at the same time, and a sign-in already started for the same service is not duplicated.

What Beaver never sees

Beaver never sees your credentials. Neither the password, nor the second factor. Authentication takes place entirely on the service's site, in your browser.

What Beaver receives is an access token: an authorization limited to what the service agreed to grant, revocable at any time from your account, and unrelated to your password.

The protections around the exchange

Authentication addresses are checked per service. Beaver automatically discovers the service's authorization addresses, but it refuses any address that does not belong to the domain expected for that particular connector: a Notion address presented for a Sentry sign-in is refused. That is what stops a compromised service from redirecting authentication elsewhere.

Encryption is mandatory, and no address containing credentials is accepted. The request is tied to the session by a single-use secret generated at the start: a third party intercepting the service's reply could do nothing with it. The local server listens only on your machine, on a randomly chosen port, only during the sign-in, and the requests it accepts are size-bounded.

Security These checks also apply to renewal, not just to the first sign-in: the address is revalidated at every exchange. A compromised service therefore cannot hijack authentication later on.

Where the tokens go

Into the encrypted vault, like the API keys and the account sign-ins: encryption on disk, master key in the system password manager, no read command exposed to the interface, memory protected and erased after use. Each connector has its own separate entry: signing out of one does not touch the others. The vault is detailed in The vault and API keys.

Renewal

An access token expires. Beaver renews it automatically, 30 seconds before the actual expiry — that margin stops a request that left just before from failing in flight. You have nothing to do: an authorization granted stays valid until you revoke it or the service invalidates it.

Two design details avoid real problems. One renewal at a time per connector: if several requests notice at the same moment that a token has expired, only one renews it and the others wait for the result — without that, several simultaneous renewals can invalidate each other's tokens, because some services only accept one at a time. And the token is checked again after getting its turn: another call may have renewed it in the meantime, in which case no pointless exchange happens. When a service does not return a new refresh token, the old one is kept — some only return it once.

Revoking access

Two places, and they have to be told apart. In Beaver, signing out erases the tokens from the vault and the connector becomes unauthenticated again. At the service, your account's security page lets you withdraw the authorization granted to Beaver: that is the real revocation, the one that holds even if tokens survived somewhere else.

Warning Signing out in Beaver is not always enough. To cut access off completely, also revoke the authorization from your account's security page at the service. Do both.
