Reading and writing files.

Four tools make up the Files group, locked and impossible to turn off: without them the agent could do nothing with a project. This page describes what they can do, their limits, and the guards that protect your disk.

The four tools

The Files group
ToolRoleWrites to disk
read_fileReads a text fileNo
edit_fileReplaces a specific passage in an existing fileYes
write_fileCreates a file or replaces it entirelyYes
list_dirShows a folder's treeNo

The two tools that write ask for approval in Ask permission mode. The other two do not.

Reading a file

  • read_file only reads UTF-8 encoded text. An image, a PDF, a .docx or an executable return an error. Dedicated tools exist for these formats, in optional groups you have to turn on.
  • Maximum size: 20 MB. Beyond that the file is refused, not truncated.
  • The content comes back numbered line by line, which lets the agent point at an exact spot and quote a line number in its answer.
  • By default the agent receives the first 2,000 lines, and up to 50,000 if it asks. When some are left over, the result states how many lines were not read and where to resume — the agent then carries on by itself.
  • The path can be relative to the working directory or absolute. Either way it must fall inside an area allowed for reading.

The "read before write" rule

This is Beaver's most useful guardrail, and you can see it in the conversation. The agent cannot edit an existing file without having seen it first. If it tries, the write is blocked with a message telling it to go and read the file.

Without this rule, a model that "thinks it remembers" a file's content could rewrite it from memory and erase everything it did not know about. With the rule, it has to observe the real state before touching anything.

These count as "having seen the file":

  • having read it with read_file, or with the document, spreadsheet and image reading tools;
  • having seen it appear in a result from a pattern search, a filename search or a folder listing;
  • having written or edited it earlier in the same conversation;
  • having modified it through a shell command — files touched by a command are recorded automatically.

Two details: the rule only applies to existing files — creating a brand new file requires nothing — and the list of seen files is capped at 1,000 paths per conversation. Beyond that, the 100 oldest are forgotten: a file read very early in a very long conversation may therefore require a fresh read.

Key point The agent does not rewrite a file from memory. It must have looked at it in the current conversation before it can edit it.

Editing an existing file

edit_file replaces one exact passage with another, a single time.

  • The passage being searched for must appear exactly once in the file. If it appears several times, the tool refuses and says how many times it found it, suggesting that surrounding lines be added to remove the ambiguity. The agent tries again with more context.
  • The match is exact down to the character: spaces, tabs and line breaks included.
  • There is no global replace. Renaming a symbol that appears twenty times takes twenty calls, or a full rewrite of the file.
  • On success, the tool returns the number of the edited line, which feeds the diff display in the conversation.

This is the tool to prefer for any edit: it only transmits the changed portion, where a full rewrite sends back the whole file and consumes far more context. A full rewrite, for its part, overwrites without discussion everything that was not in the new content.

Creating or replacing a file

write_file writes a whole content. It serves to create a file, or to rewrite it end to end.

  • Missing parent folders are created automatically.
  • Writing is refused outside the allowed areas: the working directory, the paths configured in the advanced settings, and the workspaces managed by the application.
  • Symbolic links are never followed. Writing to a link is refused, and the refusal is checked three times: before path resolution, after it, and at the very moment the file is opened.
  • The real parent folder is re-checked after resolution: a path that goes through a link to come back out outside the allowed areas is refused.
Security A symbolic link placed in the project cannot serve as a passage to the rest of the disk: that is exactly what this triple check prevents.

Browsing a folder

list_dir gives an indented tree, not a flat list.

  • Goes down 3 levels deep. Folders are suffixed with a slash, in alphabetical order.
  • No size, no date, no permissions — just names. For that information, the agent goes through a shell command.
  • Hidden from view: anything starting with a dot, along with node_modules and target, which hold tens of thousands of pointless entries.
  • Capped at 500 entries. Beyond that, the result says so explicitly.
  • An empty folder returns "(empty folder)", not an empty result.
  • When some subfolders could not be opened, the result says so and gives their number — it never claims to have listed everything.
Careful list_dir does not show everything. It is not a file explorer, it is a structural overview. An agent you ask to read a hidden file will not find it by listing the folder: give it the name.

When the agent leaves the working folder

Any operation that modifies a file outside the working directory adds a warning to the result, reminding the agent which workspace is active and asking it to come back unless you explicitly asked otherwise.

This is not a block: the operation did happen. It is a reminder aimed at the model, to avoid the silent drift where a session ends up scattering files all over the place.

A write interrupted by a timeout is never announced as retryable, and the message adds that the file's state may be partial. You do not blindly replay a write when you do not know whether it went through.

System errors are rewritten before being surfaced: neither the agent nor you see the operating system's raw message, which would reveal internal paths, user names or the disk's structure.
