Replacing a tool

An extension can take the place of a Beaver tool. From that moment on, the model sees only one tool under that name: the extension's. It does not know a replacement happened, and it cannot ask for the original tool. This page says how it works, what it commits you to, and how to go back.

What "replace" means exactly

The mechanism is a substitution by name, not an addition. Beaver builds the list of core tools, then injects the extensions' tools into it: when a name already exists, the extension's tool takes its place in the list, it is not added alongside. The original tool is not lost for all that — Beaver stores it inside the replacement definition, as a fallback, and uses it again in the cases described below.

An ordinary extension tool is always prefixed with its extension's identifier, in the form my-extension.my-tool. A replacement is the only case where an extension publishes a tool without a prefix. The code is written like an ordinary tool — a name, a description, a parameter schema, an effect class, an execution function; only the entry point changes, beaver.unstable.registerReplacement(...) instead of beaver.registerTool(...).

Warning Replacement rests on the advanced API, which Beaver's own contract describes as unstable: "The advanced API is unstable and may change between Beaver versions." The behavior when no name matches carries the same note: "This behavior is unstable and may change between versions." An extension that replaces a tool can therefore stop working, or change behavior, at the next update — without that counting as a regression.

The prerequisite: the advanced level

Replacement is only available to extensions whose manifest declares "apiLevel": "advanced". The check happens twice, and the two failures do not look alike.

The two advanced-level checks
WhereWhat happens if the level is not advanced
In the extension, at registration timeThe call fails immediately with the error advanced_api_required
In Beaver, on receiptAll of the extension's contributions are refused, not just the replacement, with the message "Advanced mode is required to replace a built-in tool"

The second check is the one that counts: the first lives in the extension's code, so in a process Beaver does not control. The second is on Beaver's side, it applies whatever the extension did, and it rejects the entire batch of its contributions.

Note The advanced level is not a skeleton key. It opens up tool replacement and the advanced interface — nothing else. The generic call beaver.unstable.call(...) exists for future methods declared advanced, but the current contract publishes none: the twelve exposed methods are all at the stable level, and any call to unstable.call is rejected today with core_method_unavailable.

There is no list of replaceable tools

This is the most important point on the page. Beaver keeps no allowlist of replacement points. The rule is mechanical: if the declared name matches a tool in the catalog of the moment, the extension's definition covers it; if the name matches nothing, the definition becomes a new tool, published without a prefix.

Two direct consequences. A typo produces no error — it produces a tool. And the reference catalog is the one of the installed version: it holds 14 locked tools, among them bash, bash_control, read_file, write_file, edit_file, list_dir, grep, glob, web_search, web_fetch and search_mcp_tools, plus 32 optional tools. A tool that disappears or is renamed in a later version silently turns a replacement into an extra tool.

When the original tool comes back

A registered replacement is not a permanent replacement. Beaver goes back to the original tool in several situations, without telling the model. Two conditions govern everything: the extension has to be enabled and approved — the extension tool index only keeps entries that meet both criteria — and it has to be selected for the current conversation, because Beaver does not load every extension into every conversation: it picks the ones that fit within the model's tool budget.

One detail in replacement's favor deserves saying: a replacement uses up no room in that budget. The count excludes definitions that carry a fallback. An extension whose tools are all replacements therefore weighs nothing.

What the model receives depending on the situation
SituationWhat the model receives
Extension enabled, approved and selected for the conversationThe extension's tool, under the original name

Activation, confirmations and Plan mode

The replacement obeys the original tool's enablement setting. If you disabled the tool in the settings, the replacement is disabled with it. That is consistent: disabling web_search must cut web search off, not delegate it to someone else.

Confirmations come from the effect class the extension declares, not from the tool being replaced. As soon as a tool is known to the extension index, Beaver decides whether or not to ask for confirmation solely from its effect class, bypassing the original tool's logic entirely.

A missing, misspelled or unknown effect is not refused: it becomes unknown, the most restrictive class. The process hosting the extension already normalizes the value, and Beaver revalidates it on its own side.

In Plan mode, the effect class decides too. That mode normally allows a closed list of reading tools; for an extension tool, that list is ignored and the effect policy applies instead. Only the read-only class is allowed there. The consequence runs both ways: replacing a tool allowed in Plan mode with a tool declared local-write takes it out of Plan mode; replacing a tool forbidden in Plan mode with a tool declared read-only brings it in.

What this really commits you to

This section is not editorial caution. It describes what the code does. An extension is not isolated: it is code run with your account's rights, with full access to Node.js — files, network, processes.

Security Replacing bash or web search is the most committing act in the application. The replacing tool receives every command the agent meant to run, or every search query, plus the conversation's working directory. It can run something else, send it elsewhere, or return a fabricated result: the model has no way of noticing, and neither do you. Only install a replacement if you have read the code of the extension and its dependencies, and you accept doing that reading again at every update.
Warning The original tool's guards do not come along. A replacement inherits none of the protections written for the tool it covers. Two examples: a replacement for bash no longer goes through the analysis that tells a safe command from one needing confirmation; a replacement for web search declared external-read reuses web_fetch's confirmation dialog but not its anti-SSRF filter — approved code keeps its direct network access. After a replacement, what protects you is only the effect class the extension declared itself.
Warning A replacement declared read-only never asks for anything. It is the only class without confirmation, and the only one allowed in Plan mode. Nothing stops an extension from declaring read-only on a tool that replaces bash: the result is a third-party tool that runs whatever it likes, with no dialog, including during a planning phase that is meant to change nothing. The effect class is a declaration by the author, not a check by Beaver.

Diagnosing a replacement

In the application. The extension's entry — Settings › Extensions, then the entry, Registered contributions section — lists every tool with its name, its translated effect class, and the label Replaces a built-in tool when it is one. That is the only place where the information is shown as such.

From the agent. Two tools exist, both always present and allowed in Plan mode: list_extensions, which lists the known extensions, and inspect_extensions, which details one or more extensions by identifier with their tools, skills and resources. Their limitation is worth knowing: inspect_extensions returns each tool's identifier, name and a summary, but neither the effect class nor the fact that it replaces a Beaver tool. The only clue available to the agent is the name itself — an extension tool without a prefix is a replacement.

Going back

Going back is immediate and requires no file handling.

  • Disable the extension from its entry. It leaves the index, its process and its session permissions are revoked, and the original tool takes its place back in the next conversation.
  • Remove the extension if trust is broken. For a Git or npm source, Beaver only removes its own copy; your local files stay untouched.
  • Disabling the original tool in the settings also cuts off the replacement, since it follows that setting. Useful when you want to suspend the tool without touching the extension.
  • If the interface itself is broken by the extension's advanced module, Beaver launches without any third-party interface by holding Shift at startup, or with the --safe-mode argument.
Security One point cannot be settled by disabling: if the extension asked for a secret, disabling or removing it does not take back a copy it may already have obtained. To invalidate that copy, revoke the access at the provider concerned.
