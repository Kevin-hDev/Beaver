One key, one provider

Eleven model services plug into Beaver with an API key. This page says where to create that key, how to save it, and above all where it goes once entered — that is the point which sets Beaver apart from an application that would write your key into a configuration file.

What a key adds

Beaver works without any key at all, with local models. Adding a key gives access to a provider's remote models: more powerful, faster, without consuming your machine's resources — and billed per use.

The choice between local and remote is covered in Choosing your model. This page is about setting things up.

Note Beaver works without any key. Local models require no account. A key adds possibilities, it is never a prerequisite.

Adding a key

  • Open Settings › Integrations › Providers.
  • Pick the provider: its description and its entry offer appear.
  • Follow the link to the provider's page, create an account, generate a key.
  • Paste the key into Beaver.
  • Test the connection.

The key is validated on entry — format, length, characters. An obviously wrong key is refused immediately, before any network call.

Once saved, the provider shows as configured and its models join the selector in the input bar.

Where the key goes

The key is encrypted on disk. It lives in a vault encrypted with a modern algorithm. The key that unlocks that vault — the master key — is not in the vault: it is entrusted to the operating system's password manager (Keychain on macOS, Credential Manager on Windows, the desktop wallet on Linux).

Direct consequence: copying the vault file onto another machine gives access to nothing. Without the system master key, it is unreadable.

Beaver's interface never sees a key. The available commands make it possible to save a key, delete it, know whether it exists, list the configured providers and test the connection. None of them can read it back.

In memory, the key is protected and erased after use: it is loaded at the moment of the call to the provider, then overwritten. And none of this appears in the logs — provider response bodies are filtered and truncated before being written.

There is no read command. That is deliberate: nothing in the interface can ask for a key's value. The vault is detailed in The vault and API keys.

Warning A key you have entered can never be displayed again — not even by Beaver. If you lose it, you have to generate a new one at the provider. That is the price of a key the application itself cannot read.

Testing the connection, removing a key

Every provider has a test that sends a minimal request and returns a clear verdict. That is how you tell an invalid key from a network problem, before you start working.

Deleting a key removes it from the vault: the provider disappears from the list of configured services and its models leave the selector. Writing to the vault is transactional — either the operation completes entirely, or the vault stays in its previous state. An interruption at the wrong moment cannot leave it half written, therefore unreadable, therefore with every key lost.

One provider removed: Groq

Groq has been removed from the product. It no longer appears in the list above and can no longer be configured.

If you had configured it: on the first start of a version that no longer offers it, its key is erased from the vault and from the system password manager. The erasure follows the same care as the rest — a copy of the vault is made before the operation and is only deleted after the next successful start, and a marker prevents the cleanup from running again.

The word "groq" can still appear as a prefix in the names of models resold by OpenRouter. That is not a configurable provider, it is an origin hint inside a model name.
