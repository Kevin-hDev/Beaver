The agent's tools.

A tool is a capability the agent invokes on its own while it answers: reading a file, running a command, searching the web, delegating a task. Deciding which tools are on means deciding what the agent can reach — the most structuring setting in the application, more so than the choice of model.

What a tool is

The agent does nothing but produce text and call tools. Everything Beaver can do on your machine goes through a tool, without exception.

A disabled tool is never offered to the model: the model does not know it exists. And if it calls it anyway — because the setting changed in the middle of a conversation, for instance — the call is refused with a clear message. Both barriers exist; the second one is only a fallback.

Key point A disabled tool is invisible first, refused second. So the agent will not say "I'm not allowed": it will work around it, or answer beside the point. When a capability is missing, the first thing to check is the Settings › Agent › Tools screen.

Essential tools and optional tools

Two categories, shown as such in Settings › Agent › Tools.

  • Essential tools — always on, no switch, with the "Always on" badge to their right. They form the base without which the agent cannot do anything useful.
  • Optional tools — one switch per group. Some are on out of the box, others are not.

The setting covers an entire group, never a single tool. Turning on "Subagents" turns on all nine tools in the group at once.

In figures: 5 essential groups for 11 tools, 11 optional groups for 32 tools, of which 5 are on by default and 6 are off. Three additional tools (list_extensions, inspect_extensions, load_extension_resource) are always on, serve the extensions, and appear in neither of the two tables on the settings screen.

What is on out of the box

The starting choice follows a simple logic: whatever serves almost every conversation is on, whatever belongs to a specific use is off so it does not clutter the model.

Direct consequence: if you ask "read me this Excel file" without having turned on the Spreadsheet group, you will get an evasive answer or a workaround through the terminal, not a clear error message. The model does not know the tool exists.

Turning a group on or off

  • Path: Settings › Agent › Tools, one switch per optional group.
  • The switch takes effect immediately and applies to every conversation — it is not a per-conversation setting. External connectors, on the other hand, are enabled conversation by conversation.
  • For each group the screen shows a title and a sentence explaining what it is for and when to turn it off.
  • If saving fails, the switch returns to its previous position and an error message appears.
  • A dependency worth knowing: the Subagents group is driven by delegate_task. Without it, the eight other tools in the group are removed automatically; turning it on brings them all back.
Note Turning everything on is not free. Every active tool takes up room in the context on every request, including when the agent does not use it. On a local model with a small context window, turning on all eleven optional groups mechanically leaves less room for the conversation — see context.

What the model sees

This is the part that is visible nowhere in the interface, and that explains the agent's behaviour when a group is off.

  • The tool definitions sent to the model are filtered before every request: a disabled tool does not appear in the list.
  • The system prompt is filtered too. Every line that names a disabled tool is removed, and two whole sections disappear when their group is off: the one about interactive choices when ask_user_choice is off, and the one about working with subagents when delegate_task is. Removing lines one by one would leave orphan bullets, since several lines in these sections name no tool at all.
  • No list of disabled tools is passed to the model. That is a deliberate choice: mentioning an absent tool led the model to announce capabilities it did not have.

Results that are too large

Two mechanisms stack up.

1. Per-call truncation. Some tools have a character ceiling for a single result. Beyond it, the model receives a header stating the total size, then the first 2,000 characters, then the number of omitted characters. The full result is written to disk and its path is given to the model, which can read it back with read_file.

$ ~/.local/share/cl-go-dash/tool-results/<conversation id>/

The cut is made by character and not by byte: a result full of accents or emojis is never cut in the middle of a character. If writing to disk fails, the result carries an explicit warning — the full output is then lost. Result files are deleted automatically after 24 hours.

2. The conversation-wide budget. The whole set of tool results still present in a conversation is capped at 100,000 characters. Beyond that, the oldest results are emptied and replaced by a note saying the output was removed from the context, with the path of the full file when there is one. The two most recent results are never emptied.

read_file has no ceiling here: its limits lie elsewhere, 20 MB per file and 2,000 lines per call — see Files.

When a call is malformed

Every tool call is validated before execution. A missing required parameter, a wrong type or an unknown parameter produce an error message that lists the accepted parameters. The agent receives that message and corrects itself, usually on the next turn. You see the back-and-forth in the conversation, but you have nothing to do.
