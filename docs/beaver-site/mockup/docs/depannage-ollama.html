The Ollama engine, when it gets stuck

This page starts from what you see on screen and works back to the cause, then to the remedy — or to the admission that there isn't one, because several situations described here cannot be settled from inside the app. It assumes the engine is already installed: the first installation, its download and its recovery are covered in Installation troubleshooting.

One reflex before anything else: open Settings › Ollama and read the status shown. Everything that follows flows from it.

The three engine states, and how to read them

The engine has only three possible states, and the whole page follows from them.

The three states shown in Settings › Ollama
Label displayedWhat it means
“Ollama managed by Beaver”Beaver launched the engine itself and controls it entirely
“External Ollama”An engine was already running on the machine; Beaver uses it without controlling it
“Ollama unavailable”No engine reachable

While measuring, the screen shows “Loading Ollama status…”, and a “Try again” button lets you run the measurement again.

The distinction between “managed by Beaver” and “external” is not cosmetic. It decides what works and what does not: it is the heart of this page, and probably the most useful piece of information it contains.

How Beaver measures this state. A background loop queries the engine every 2 seconds, with a response timeout of 2 seconds. If the call fails, the state immediately flips to “unavailable”. The interface is only notified when the state changes, not on every loop iteration.

“Ollama unavailable” — the engine no longer responds

What you see — Settings › Ollama shows “Ollama unavailable”, the list of local models empties, and the agent refuses any local request.

The causes, in likely order of frequency:

  • The engine process stopped. Whatever the reason — a crash, a shutdown by the system, a lack of memory — the measurement loop notices in less than two seconds and flips the state.
  • The engine does not respond within 2 seconds. This timeout is fixed. A heavily loaded machine, or a model being loaded into memory, can exceed it: the engine is then announced as unavailable while it is still running. The state comes back on its own at the next iteration.
  • The engine never started. The launch has a budget of 10 seconds. Beyond that, or if the version answering is not the one installed, Beaver stops the process it just launched and shows “Ollama could not start.”
  • A repair is pending. If the engine installation is in a state that requires a resume, the start is refused before even trying, with one of the repair messages from the table that closes this page.

What to do, in this order:

  • Wait ten seconds and look again — the measurement is automatic and fixes itself in the second case.
  • Click “Try again” in Settings › Ollama.
  • Restart the engine — see below.
  • Restart Beaver. An installation recovery runs at startup, before any launch attempt.
  • If the message is one of the repair messages, follow the table: they do not all have the same outcome.
Note There is no engine log to consult. Contrary to what older documentation suggests, the engine launched by Beaver writes no trace file: its output is discarded on macOS and Linux, and is not redirected on Windows. That file does not exist — no point looking for it. The only usable traces are Beaver's own, which carry an error code, not a message from the engine.

Port 11434 and the reused external engine

This is the most misunderstood mechanism in the product, and it deserves to be laid out in full. Every time the engine starts, Beaver does this, in this order:

  • It attempts a connection on 127.0.0.1:11434, Ollama's usual port, with a timeout of 250 milliseconds.
  • If something answers on that port, it declares it “External Ollama” and launches nothing.
  • If the connection is refused, it asks the system for a random free port and launches its own engine there.
Note Beaver does not use port 11434. It is the port it watches to find out whether an engine is already running. Its own starts on a free port drawn at random on each launch, and only listens on your machine — the address built is always local, and any other form is refused: another machine, a login, a password, a URL parameter. An occupied port 11434 therefore never blocks Beaver. It is the opposite of the usual reflex: this is not a conflict, it is a detection.

What you see — “Settings shows External Ollama even though I never installed Ollama”. The likely cause: another program occupies port 11434, or an Ollama installation made before Beaver is still running, for instance launched automatically when your session opens.

What to do — stop the other engine, then restart the engine from Settings › Ollama. Beaver will find nothing on 11434 any more and will launch its own.

And if you go looking for Beaver's engine on 11434, you will not find it: it is never there.

What does not work with an external engine

Warning An external engine is not the same product. If Settings › Ollama shows “External Ollama”, Beaver is using an engine it did not launch. Chatting with a model works; downloading, deleting or creating a model does not, and the acceleration settings have no effect. Nothing on screen announces it beforehand.
What each engine state allows
FunctionEngine managed by BeaverExternal engine
Chat with a local modelYesYes
List the installed modelsYesYes
Download a modelYesNo

Create a custom modelYesNo
Choose processor or graphics cardYesNo effect

Why this split exists. The acceleration and multi-model settings are passed to the engine when it is launched, as environment variables. An engine Beaver did not launch never received these values, and there is no way to apply them afterwards. Conversely, the time before memory is released travels in every request: that one applies in both cases.

What to do — to get all the functions back, stop the external engine then restart Beaver's. There is no other route.

A model download fails

What you see — under the model install button, a red line: “Download failed”.

This message never says which of the causes is at play. Every possible download failure ends up on the same single code. The causes Beaver distinguishes internally, without ever passing them to the screen:

  • the engine is not managed by Beaver — that is the case above, and probably the first thing to check;
  • the engine is unreachable at the time of the request;
  • the model registry refuses the requested name, or the model does not exist;
  • the download goes past one hour — the overall timeout is 3,600 seconds;
  • disk space is missing, which comes back as an engine error;
  • the progress stream goes past 500,000 lines, a safety bound.

What to do, in this order:

  • Check the engine state. If it shows “External Ollama”, downloading cannot work.
  • Check the free disk space. Models live in ~/.ollama/models, outside Beaver's data folder, and a common model weighs several gigabytes.
  • Start the download again. Ollama reuses the chunks already obtained: a second attempt does not necessarily start from zero.
  • Check the model name in the catalog, going back through search rather than typing a name by hand.
  • On a corporate network, check that ollama.com is reachable: that is the address of the model registry.

One queue, one download at a time. Beaver runs only one model download at a time and accepts no more than 16 waiting. Beyond that, a transient notification announces “This model could not be added to the queue.” Waiting models show “Queued”, the others the current step: “Starting”, “Downloading”, “Installing”, “Preparing engine”, “Completed”.

A model download was interrupted

What you see — you clicked “Cancel” (or pressed Esc, which does the same), or Beaver was closed during a download.

Warning Cancelling a download deletes it. The chunks already obtained are erased and the model is removed from the engine. Starting again starts from the beginning: this is not a deferred resume, it is a cleanup. The only exception is the update of an already installed model — cancelling there leaves the previous version intact, and that is deliberate.

The queue does not survive closing the app. It lives only in memory: no file records it. After a Beaver restart, nothing resumes on its own and nothing signals that a download was in progress.

What to do — start the download again from the models screen. There is no other route, and there is nothing for you to clean up yourself.

The graphics card is not used

What you see — local models answer very slowly, and the hardware indicator shows “CPU · RAM” instead of “VRAM” or “RAM”.

That indicator is reliable, and it is the right place to look. Beaver computes it from what the engine actually declares it is loading: if no loaded model occupies graphics memory, the label becomes “CPU · RAM”. It appears if the “Show GPU status” setting is enabled.

Three distinct causes, not to be confused:

  • The setting is on processor only. The “processor” mode forces the engine to use no accelerator. The setting is in Settings › Ollama, under “Inference engine for local models”. It is not shown on Mac: on an Apple silicon Mac, the engine decides on its own.
  • The card vendor was not recognized. On Linux, Beaver reads the vendor identifiers of the cards present; on Windows, it queries the system's list of video cards and recognizes names containing nvidia, geforce, quadro, amd, radeon or intel; on macOS, it reads the processor brand. A missing driver, or a card whose name contains none of these words, yields an unknown vendor.
  • The model does not fit in graphics memory and the engine moves part of it to ordinary memory. That is the next section.

What to do:

  • Check the setting in Settings › Ollama, outside Mac.
  • On Linux, with an AMD or NVIDIA card: check that the card is seen by the system. If nothing matches, the graphics driver is not loaded — that is a system problem, not a Beaver one.
  • On Windows: the card driver must be installed; it is what provides the name Beaver reads.
  • Take a smaller or more compressed model — see Hardware and VRAM.
$ ls /sys/class/drm/

One clarification that avoids a false trail: vendor detection is only used to choose which archive to download on Linux, when installing the engine. It does not drive the processor or graphics card choice at runtime: that choice comes from the setting and from the engine's own autodetection.

The model is too heavy for the memory

What you see — when an installation starts, a transient notification: “This model may require more memory than your machine has. The download will continue.”, shown for four seconds.

What this check actually does: it compares the announced file size to the measured graphics memory, and warns if it does not fit. It blocks nothing — the message says so itself.

Three limits are worth knowing:

  • When memory cannot be measured, the check answers “it fits”. On a machine where the measurement fails, the warning therefore never appears, whatever the size of the model.
  • It only counts the model file, not the conversation context, which adds to it and grows with it.
  • It is a transient notification, not a confirmation. Four seconds of inattention and it is gone; nothing brings it back afterwards.
Warning Unmeasurable memory has a second, more discreet consequence. The measurement also decides the context size granted to local models, in three tiers: 32,768 tokens above 24,000 MB, 24,576 tokens above 12,000 MB, 8,192 tokens below — and 8,192 as well when the measurement fails. A context stuck at 8,192 tokens on a well-equipped machine is therefore the symptom of a failed measurement, not of a choice. This cannot be adjusted from the app.

What to do — take a more heavily compressed version of the same model, or go down one size. The full mapping table is in Hardware and VRAM.

Restarting the engine

Where — Settings › Ollama. The button is always present next to the acceleration setting outside Mac, and a line “Restart required — Changes will be applied after restarting Ollama” is added as soon as an affected setting has been modified.

Which settings require this restart: the time before memory is released, the processor or graphics card choice, and loading several models at once. The “Show GPU status” setting does not require it.

What the restart really does: it stops the engine with a budget of 10 seconds, then runs the full sequence again — detection of an external engine on 11434, then launch on a free port.

The three outcomes of a restart
What happenedMessage displayed
Beaver's engine restarted“Ollama restarted”
An external engine was found again“External Ollama reused”

Warning “External Ollama reused” means nothing changed. On an external engine, stopping does nothing at all and the restart merely finds the same engine again. The settings you just changed are not applied, even though the notification presents itself as a success. This is trap number one on this page.

If stopping fails, the message is “Ollama could not stop cleanly.”. There is then no possible action from inside the app: close Beaver and launch it again.

“Connection to Ollama lost” during a conversation

What you see — in the middle of an answer, the conversation stops on “Connection to Ollama lost”.

The cause — the request to the engine did not go through, either because the connection failed or because it timed out. This is the symptom of an unavailable engine, met from a conversation rather than from the settings.

To be distinguished from “Ollama server error”: there, the engine answered, but with an error. That message only arrives after the retries are exhausted.

Automatic retries are invisible and generous. On a temporary engine error — HTTP codes 500, 502, 503, 504 — Beaver retries up to ten times, with a growing wait of 350 milliseconds multiplied by the attempt number, capped at the sixth. Two other retries exist, more discreet: dropping a capability the model does not support, and a small number of retries after a failure to parse tool calls.

This generosity is specific to the local engine. Remote providers have no automatic retry — Keys and providers explains why, and the reason is a good one.

What to do — resume the conversation after checking the engine state. The conversation itself is kept; only the answer in progress is lost.
