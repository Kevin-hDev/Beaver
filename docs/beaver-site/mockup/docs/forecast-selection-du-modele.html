Choosing the model, or letting it choose

Beaver knows two selection modes: Manual, where you name the model, and Auto, where Beaver draws up a shortlist of acceptable models. This page describes the choosing mechanism, not the models themselves — the catalog is in Local models.

What “Auto” means here Auto doesn't decide on its own: it eliminates the models that can't do the job on your data and your machine, ranks the ones that remain, and keeps only five. The final choice within that shortlist stays yours, or the agent's when you hand it the work. In exchange, a model that doesn't fit can no longer be launched by mistake.

The two modes, and where to change them

The setting lives in the model selector's dropdown, at the bottom of the Forecast panel when the main view is open. It carries the title “Selection”, with two buttons Manual and Auto. In Auto mode, an extra switch appears below the two buttons: “Allow cloud models”.

The button that opens the list changes label depending on the mode: in Manual it shows the name of the chosen model, in Auto it simply shows Auto.

The setting is global to the application, not specific to a conversation: it is written to a single file, bounded at 4 KB, in two steps — temporary file then rename. The starting values are: Manual mode, no model chosen, remote models not allowed in Auto.

What Manual mode does

One model is chosen, and that's the one used. The check is strict on both sides:

  • No automatic-selection data is accepted. A request arriving with a selection identifier or choice reasons is refused — “Auto metadata is forbidden in Manual mode”.
  • No model chosen? The calculation stops: “No Forecast model selected”.
  • A different model requested? Refusal: “The requested model does not match the manual selection”.

The consequence to remember: in Manual mode, the agent cannot change model on its own initiative. The lookup tool returns the imposed model and its state, with the instruction not to depart from it.

One convenience on the screen side: when the mode is Manual and the chosen model no longer exists or is no longer usable, the interface picks another one from the list rather than sitting on a dead choice.

What Auto mode does — and what it doesn't

This is the most important point on the page, and the easiest to misunderstand. Auto mode does not choose the model for you from the screen. It builds a shortlist of acceptable models, ranked, and checks that the model finally launched is part of it. The choice within that list is still made by someone: you from the screen, the agent from the conversation.

From the configuration screen. In Auto mode, no model is preselected: the list opens empty and you choose. At launch, Beaver rebuilds the list of candidates and checks that your choice is in it, otherwise the calculation is refused with “The model is not among the Auto candidates”. The result is then recorded as an explicit user choice.

From the conversation. The agent requests the candidates by passing the data profile identifier. It receives the ranked candidates, the basis of the ranking, a task profile, a hardware profile, and a selection identifier to pass back when computing. The instruction that accompanies the answer is explicit: pick a single candidate, and never call a ranking based solely on capabilities and resources the “best model”.

Five candidates at most are returned, with at most eight reasons each. Auto mode also requires an up-to-date data profile: a profile computed by an earlier version makes the selection fail with “Forecast profile is outdated”.

Before any ranking, each model in the catalog goes through a series of filters. A single failure sets it aside.

Warning The confidence level is never rounded. If you ask for an 85% range, a model that can only produce 60% or 80% is set aside — it isn't used “as the nearest match”. This is deliberate: a range announced at 85% that is actually worth 80 is false information, and nothing on screen would tell it apart from correct information.

“Can do the task” covers six conditions, all checked together:

  • the requested horizon doesn't exceed the model's maximum horizon;
  • the model accepts the chosen frequency;
  • if there is more than one series, the model can handle several series;
  • if there are covariates, the model can exploit them;
  • if there are covariates and known future rows, the model can exploit the known future;
  • the model can produce a range — this condition is required of all of them, without exception.

The ranking: what separates the ones that remain

Two different rankings apply, and knowing which one is in force is what separates a measured recommendation from a merely plausible one.

At least one candidate has been measured over past windows. Measured models come ahead of all the others. Among themselves, first come those that beat the best simple baseline, then those about which nothing is known, and last those that don't beat it; then a comparison across several measures at once — accuracy, quality of the range, duration, observed memory.

No candidate has been measured. The ranking then rests on three criteria only: memory comfort, in the order Comfortable, Cloud, Constrained, Unknown, Insufficient; at equal comfort, the model asking for the least memory; at a complete tie, alphabetical order of the identifier.

The word “recommended” is reserved. The first candidate is only marked as recommended in two cases: either no candidate has been measured, or that one beats the best simple baseline. A measured model that doesn't beat the baseline is never recommended, even if it comes out on top.

When you explicitly name a model, it is moved to first position and marked as requested, whatever its rank. If it has been eliminated, it isn't silently replaced: its exclusion reason is returned, and the agent is instructed to explain it and to change model only after your agreement.

Note Two very different rankings. As long as no model has been measured on your past data, the ranking only speaks of compatibility and available memory: it says “this model can do the job”, never “this model forecasts better”. For a ranking based on quality, you have to run an evaluation — see Evaluation and comparison.

Measuring your machine's resources

Auto mode measures the machine before ranking. The measurement is specific to Forecast and isn't exposed anywhere else. What is recorded: the type of graphics memory — dedicated, shared with the processor, or unknown — total graphics memory, available graphics memory, and available system memory.

The five resource verdicts and their rank in the ranking
VerdictConditionRank
ComfortableAvailable memory ≥ 2 × the requirementThe best
CloudModel at an external providerNext
ConstrainedBetween the requirement plus 20% and twice itNext
UnknownMemory not measurableThe last one kept
InsufficientAvailable memory < requirement + 20%Eliminated

The 20% margin is the point to remember: a model asking for 4 GB doesn't fit in 4 GB of available memory, it needs 4.8. And when a model can run on the processor or on the graphics card, the better of the two verdicts is kept.

This same check is reapplied just before starting a local model, outside any automatic selection: the calculation is refused with “Insufficient resources for this model”.

The lock: the selection ticket

When the agent obtains a list of candidates, it also receives a ticket — a single-use identifier attesting that this choice really was made on that data.

Warning An automatic selection expires. It is valid for thirty minutes, and for that data. Modifying the file or waiting too long invalidates the choice, which has to be made again — “Auto selection expired or invalid”. That is what prevents a model chosen for one dataset from being applied to another without anyone noticing.

The choice reasons are a closed set. Only eight values are accepted, without duplicates: best validation result, beats the baselines, accuracy requested, speed requested, local execution required, cloud allowed, requested by the user, suited to the hardware. An invented reason causes the request to be refused.

Remote models in Auto mode

The “Allow cloud models” switch is off by default. As long as it is, every remote model is set aside from the selection, and a request that targeted a remote model anyway is refused: “Cloud models are not allowed in Auto mode”. It is a default decision in favour of local: nothing goes out to an external service until you have explicitly opened it up.

Two nuances not to leave out. The switch only concerns Auto mode: in Manual mode, a remote model chosen by hand is used without it. And a remote model receives the Cloud resource verdict, which places it above “Constrained” but below “Comfortable” — when a local model fits comfortably on the machine, it goes ahead of the remote model.

What is kept with the result

Every analysis records how its model was chosen: the source of the choice — Manual, Auto, or explicit user choice — the ranking basis, the resource verdict, the reasons kept, and the past-window measurement when it exists.

Why it matters: three months later, a saved forecast still says why that particular model was chosen. Without that record, a choice reads back as an arbitrary preference.
