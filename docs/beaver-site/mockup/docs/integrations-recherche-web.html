Web search

Beaver can search the internet with no account configured at all: it bundles its own metasearch engine, which runs on your machine. This page describes the four available sources, the order they are tried in, the prerequisite that blocks people most often, and what the engines queried actually see of you.

Four sources, a fixed order

Beaver tries the sources in this order and stops at the first one that returns results.

The order search sources are tried in
OrderSourceKey required
1Brave SearchYes
2ExaYes
3FirecrawlYes
4Built-in local engineNo
Note The order is not configurable. Configuring a Brave key means favoring it over everything else, including the local engine. A source that fails or returns nothing hands over to the next one; if all of them fail, the error reported aggregates the causes — and it is scrubbed before display, so no key can appear in it.

The built-in local engine

This is the least known part, and the most interesting. Beaver bundles a real SearXNG instance — a free metasearch engine — which it launches as a separate program on your machine. It is neither a remote service nor a middleman: it is software running locally.

Its configuration is tightened up. It listens only on your machine, on a port chosen at random at each start: no other device on the network can reach it. No metrics are collected, SearXNG's statistics collection being disabled. No session database: nothing is remembered between two searches. No image proxy or cache, no public interface, and it only answers in raw data format, not web pages. Its internal session key is generated randomly at each start with a cryptographic generator.

On the operating side: the engine is warmed up when Beaver starts, in the background, so that the first search is not slowed down by its startup. Beaver waits up to 12 seconds for it to be ready, polling it regularly. After a failed start, it does not try again for 30 seconds — without that delay, every search would relaunch an expensive attempt doomed to fail. The process identifier is recorded, and an orphaned engine left by an abrupt shutdown is cleaned up at the next start, with a budget of 3 seconds. The engine's contents are validated before launch: four expected files must be present, otherwise Beaver refuses to start rather than run an incomplete program.

One point to know: the engine stays on for as long as Beaver is open. It is only stopped when the application closes, and there is no idle sleep, unlike the MCP connectors. So a resident Python process takes up memory for the whole session.

What the engines queried see

A metasearch engine has no index of its own: it queries other public search engines and aggregates their answers. So this has to be precise, without overpromising.

  • The engines queried see your IP address, exactly as if you were visiting their site. There is no anonymizing relay.
  • No account is tied to your searches. No API key, no identifier, no persistent cookie: nothing that links two searches together or attaches them to a person.
  • Aggregation happens on your machine. No third party sees the complete list of what you searched for.
  • Beaver records no search history, neither the queries nor the results.
Warning Without an account does not mean anonymous. Your searches do go out to public engines, but with no account, no profile and no history kept: that is the absence of identification, not anonymity. If you want more than that, you have to go through an anonymizing network at your system level — Beaver does not provide one.

The Python prerequisite

The local engine needs a Python interpreter present on the machine — and not just any one. It is not "a recent Python 3", it is a precise version. A manifest file shipped with the engine declares the implementation and the version required; Beaver tries several commands, queries each one, and rejects every one that does not answer exactly that version: the implementation must be CPython, and both version numbers must match the manifest. For Beaver 1.2.2, the bundled manifest asks for CPython 3.14 — that value follows the engine shipped, so it can change from one Beaver version to the next.

The order of the commands tried
PlatformOrder
macOS, Linuxpython<major>.<minor>, then python3, then python
Windowspy -<major>.<minor> first, then the same three
Warning Having Python installed is not enough. A command whose version differs from the manifest is rejected, so a user who has "Python 3" can still be denied the local engine. If it finds none that fits, the engine does not start and key-free search is unavailable: you then have to install the exact version, or configure a key.

Once the right version is found, Beaver does the rest on its own: it creates an isolated Python environment inside its own data, installs the necessary dependencies there — from packages shipped with the application when they are present, so with no network access —, and computes a fingerprint of the source so as to reinstall only if it has changed.

On all three systems, key-free web search can therefore be unavailable until the exact version is installed. See Requirements and Windows installation.

The three key-based services

The search services that require a key
ServiceNatureWhere to create the key
Brave SearchSearch engine with an index of its ownapi-dashboard.search.brave.com/app/keys
ExaSearch oriented towards meaning rather than keywordsdashboard.exa.ai/api-keys
FirecrawlPage content extractionwww.firecrawl.dev/app/api-keys

What they bring compared with the local engine: faster, more relevant results, and operation that depends neither on Python nor on starting a separate program. What they cost: a sign-up, per-use billing, and the service sees your queries tied to your account.

The configuration flow is the same as for model providers: Settings › Integrations › Providers, pick the service, follow the link, paste the key, test. Each service has its own connection test. Search keys are protected exactly like model keys — encrypted vault, master key in the system password manager, no read command, memory erased after use.
