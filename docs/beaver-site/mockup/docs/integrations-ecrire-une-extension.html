Writing an extension

A Beaver extension is a JavaScript or TypeScript module that Beaver loads into a Node.js process of its own. It can add tools to the agent, react to events and place elements in the interface. No server to write, no port to open, no pairing token: Beaver runs your entry point and hands it the beaver object directly.

What you accept before writing a line

Warning Your extension is not in a sandbox. Its code runs with your account's rights: it can read your files, open the network and start processes. Beaver isolates each extension in its own process and empties its environment — that protects the application's stability, not the machine against approved code. The same goes for your users: they will only install your extension after explicitly approving it, and they are right to read your code first.

Three facts that change how you write. Every enabled third-party extension gets its own Node.js process, with an identity assigned by Beaver: an extension that crashes does not stop the others. That process's environment is emptied before launch — only PATH, TMPDIR, TMP, TEMP and, on Windows, SystemRoot survive: no HOME, no USER, none of your keys. And an approved extension can ask for the vault's secrets — provider key, MCP OAuth token, MCP environment value, channel token — bearing in mind that approval covers all of its code and all of its dependencies, with no per-key permission.

The entry point is in JavaScript or TypeScript, not Python, Rust, Go, Java or C#. An extension can, on the other hand, launch a program written in another language, since it has full access to Node.js.

The minimal project

Two shapes exist, and the choice has consequences. A standalone file — you add my-extension.ts directly — gets an implicit manifest: the identifier becomes local.<file-name>.<8 hexadecimal characters>, the version is 0.0.0, and above all apiLevel is advanced, not stable. A standalone file therefore gets the most permissive API level and an identity that changes on every add: fine for a trial, bad for everything else. A folder with a manifest is the only recommended shape.

$ ls hello-beaver
beaver-extension.json   index.ts   package.json   package-lock.json

Beaver looks for the manifest under three names, in this order: beaver-extension.json, then beaver.json, then package.json. The first one found wins, the others are not read. The entry point must carry a recognized extension — js, mjs, cjs, jsx, ts, mts, cts, tsx, mtsx, ctsx — and its path is canonicalized then checked as staying under the extension's root: a .. or a symbolic link that leaves the folder is refused.

You put the folder wherever you like on your disk: Beaver records the canonical path and reads the source in place, without copying it. On its own side it only writes its registry, ~/.local/share/cl-go-dash/extensions.json, and the managed copies of Git and npm installations in extension-installs/. Two points on tooling: never bundle @beaver/sdk in the distributed package, the host resolves that import to its own copy — keep it as a development dependency, for autocompletion; and no build step is required, since .js, .cjs and .mjs files go through Node's native import, and all the others through Jiti.

From loading to the first tool

Beaver loads an extension in three stages, which you will find as such in the diagnostics. import: the host imports the entry module. activate: it looks for the activation function and calls it with the beaver object — two shapes are accepted, a module whose default export is a function, or a module that exposes an activate method; otherwise, error activate_missing. register: it checks that tool names are unique, encodes the snapshot of contributions, verifies it fits inside the protocol message, and only then publishes the tools. An extension that fails at the register stage therefore leaves no tool behind.

On the lifecycle side: defineExtension does nothing at runtime, it returns its argument as is — its only role is to have TypeScript check the shape of your object. deactivate() is called when the host is reset; an exception thrown inside it is swallowed and cleanup of the other extensions carries on. That is where you stop your timers, close your files and remove your listeners. The unsubscribe functions returned by beaver.on and by interface registrations are idempotent.

A tool is registered with beaver.registerTool, and five fields matter. name: Beaver automatically prefixes the name with the extension's identifier, unless it already starts with that prefix — a tool declared hello in com.example.hello is therefore called com.example.hello.hello as far as the model is concerned. The full public name must fit in 96 characters: count the prefix, it is what brings you closer to the limit. description: mandatory, non-empty, 2,000 Unicode scalars maximum; empty, it makes registration fail, and therefore the whole activation. parameters: a JSON object, never an array. effect: see the next section. execute: mandatory, and must be a function.

The parameter schema is validated strictly. Its root must carry "type": "object", otherwise "A tool schema must describe an object." Only 38 keywords are accepted at all levels — $ref and $defs are not among them, so a schema that references a definition is refused. The maximum depth is 16 and the total is 256 nodes.

Your execute function receives the model's arguments and, in second position, a frozen context containing a single field: workingDirectory. There is no session identifier, no language, no model — do not look for them. You can return a string, or an object { content, isError?, displaySummary?, truncated? }. A string content is truncated at 1,048,576 units and displaySummary at 1,024 characters; truncation is silent, it raises the truncated flag without failing. The call is rejected after 55 seconds with tool_timeout — careful, the race rejects the promise but does not interrupt your code: your work carries on in the background with nobody reading the result.

The effect class

It is the declaration with the most consequences, and it is a single word in an object. A missing or misspelled value is not refused: "readonly" instead of "read-only" becomes unknown, the most restrictive class — the tool works, but it asks for confirmation on every call and becomes unusable in Plan mode, with no message explaining why.

Full access mode bypasses the permission gate for every row: your effect class therefore only protects users of the stricter modes — all the more reason to declare it accurately. On the subagent side, an "explorer" profile only receives extension tools declared read-only, while the "coder" profile receives them all.

Warning The effect class is a promise, and Beaver believes it. It does not check what your tool actually does: it applies the policy matching the declared class. Declaring read-only on a tool that writes to disk removes the approval request and allows the tool in Plan mode, a mode where the user expects precisely that nothing will be changed.
Security secret: what you take away does not come back. Once a vault value has been handed to your JavaScript code, Beaver can no longer guarantee it is erased from memory. Disabling or removing the extension does not take back a copy already obtained: the only answer to a leak is to revoke the secret at its provider. Never write it into a tool result, an error message or a diagnostic file.

Events and interface

Only one public event exists today: session.turn.started. Its payload contains exactly two fields, sessionId and mode. beaver.on returns an unsubscribe function to call in deactivate(). The bounds: 64 handlers per extension, 64 handlers in flight at once, and a budget of 5 seconds per handler — once it expires, Beaver stops waiting but does not interrupt your code, which keeps running unsupervised. An exception in one handler does not block delivery to the other extensions.

To place a view, you first have to declare a ui block in the manifest — without it, every interface registration is refused. In standard mode, you describe data and Beaver draws: four contribution types (tab, settingsTab, action, theme), five placement operations (before, after, replace, move, remove), eleven view primitives, twenty named icons, forty-seven redefinable theme tokens and seven languages plus default. No CSS, no JSX.

Eight public placements exist: app.navigation.primary for an application tab; settings.navigation.preferences, settings.navigation.agent, settings.navigation.models, settings.navigation.integrations and settings.navigation.application for a settings tab; app.toolbar.primary for a toolbar action; and agent.composer.leading for an action in the input field, the only one restricted to the Agent conversation and excluded from third-party chat.

Two behavioral differences not to miss. registerTool throws when refused; interface registrations, on the other hand, do not throw: they return an empty function and add a diagnostic. Your extension loads, its tools work, and the interface is simply absent — you have to go and read the diagnostic to find out. And two occupants are protected against remove and replace: beaver.settings in the main navigation and beaver.extensions in the Integrations settings. That is what guarantees a user can always come back and disable your extension.

The API levels

Mind the vocabulary: the manifest carries two different fields, with two sets of values. apiLevel accepts stable or advanced; ui.mode accepts standard or advanced. There is no API level named standard — that is an interface mode. In practice, three combinations: apiLevel: "stable" without a ui block, which gives you tools, events, skills and resources, and remains the right default choice; apiLevel: "stable" with ui.mode: "standard", which adds tabs, settings, actions and themes described as data; and apiLevel: "advanced" with ui.mode: "advanced", a JavaScript module loaded into the same WebView as Beaver.

Warning The advanced interface shares Beaver's page, with the same rights as it. There is no sandbox, and a synchronous loop in that module blocks the whole application: the only way out is then to restart, possibly with --safe-mode. That is why Beaver asks for an extra confirmation at activation. Only go there if standard mode is not enough.

The advanced level is required in two cases only: manipulating the DOM or mounting an interface the standard primitives do not allow, and replacing a native tool. What it does not give: beaver.unstable.call(...) can only call methods declared advanced in the contract, and the current contract publishes none — the bridge's twelve methods are all stable. So any call fails today with core_method_unavailable. It is not a back door into the backend.

Distributing from a Git repository

Beaver accepts two address shapes: an https or ssh scheme URL — the git+ prefix is tolerated and stripped —, and the SCP form user@host:path. Refused are any other scheme, so plain http://, a URL without a host, a password in the URL, a query string, a username over HTTPS, and an empty path.

The revision goes after a #: branch, tag or commit. The split happens on the last #, a second # makes the address be refused, and the reference is capped at 200 characters. A short commit form requires at least 7 hexadecimal characters; a full form, 40 or 64. What Beaver does with your repository: a shallow clone — unless the reference is a full commit —, then deletion of the managed copy's .git folder, measurement of the space taken up, and installation of production dependencies only. The operation's overall timeout is 300 seconds. Practical consequence: precompile anything that requires an npm install script, because npm lifecycle scripts are disabled.

Debugging: what you see when it crashes

Warning You cannot print anything. In the host process, console.log and all its variants are replaced by empty functions, and process.stdout.write is neutralized — standard output is the protocol channel between Beaver and the host. The process's error output is discarded at creation. An extension writes nowhere, leaves no trace. That is the first reflex a developer loses when arriving on Beaver.

What you get instead is a structured diagnostic with four fields: stage (import, activate or register), code, file — the name only of the entry file, 128 characters maximum, never the path — and line/column if the stack carries them. Your error message is never passed on: it only serves to pick the code.

What an extension cannot do

  • Write its entry point in a language other than JavaScript or TypeScript — it can launch a third-party program, but it has to supply it.
  • Print anything, or read the account's environment: console and standard output neutralized, environment emptied.
  • Listen to anything other than session.turn.started, or call a core method outside the contract.
  • Remove or replace beaver.settings and beaver.extensions, or touch Beaver's internal components in standard mode.
  • Work in Chatbot mode: extension tools are only available in Agent mode.
  • Make itself known to every model: Groq models through OpenRouter do not receive extension tools, and groq/compound receives no tool at all.

And one limit that is not one, not to be believed: nothing stops an extension from reading your files, opening the network or starting processes. Full access to Node.js is accepted as such.
