Écrire une extension

Une extension Beaver est un module JavaScript ou TypeScript que Beaver charge dans un processus Node.js qui lui appartient. Elle peut ajouter des outils à l'agent, réagir à des événements et poser des éléments dans l'interface. Pas de serveur à écrire, pas de port à ouvrir, pas de jeton d'appairage : Beaver lance ton point d'entrée et lui passe directement l'objet beaver.

Ce que tu acceptes avant d'écrire une ligne

Attention Ton extension n'est pas dans un bac à sable. Son code s'exécute avec les droits de ton compte : il peut lire tes fichiers, ouvrir le réseau et lancer des processus. Beaver isole chaque extension dans son propre processus et vide son environnement — cela protège la stabilité de l'application, pas la machine contre du code approuvé. Cela vaut aussi pour tes utilisateurs : ils n'installeront ton extension qu'après l'avoir approuvée explicitement, et ils ont raison de lire ton code avant.

Trois faits qui changent la façon d'écrire. Chaque extension tierce activée a son propre processus Node.js, avec une identité attribuée par Beaver : une extension qui plante n'arrête pas les autres. L'environnement de ce processus est vidé avant le lancement — seuls PATH, TMPDIR, TMP, TEMP et, sous Windows, SystemRoot subsistent : ni HOME, ni USER, ni tes clés. Et une extension approuvée peut demander les secrets du coffre — clé de fournisseur, jeton OAuth MCP, valeur d'environnement MCP, jeton de canal — sachant que l'approbation porte sur tout son code et toutes ses dépendances, sans permission par clé.

Le point d'entrée est en JavaScript ou TypeScript, pas en Python, Rust, Go, Java ni C#. Une extension peut en revanche lancer un programme écrit dans un autre langage, puisqu'elle a l'accès complet à Node.js.

Le projet minimal

Deux formes existent, et le choix a des conséquences. Un fichier isolé — tu ajoutes directement mon-extension.ts — reçoit un manifeste implicite : l'identifiant devient local.<nom-du-fichier>.<8 caractères hexadécimaux>, la version vaut 0.0.0, et surtout apiLevel vaut advanced, pas stable. Un fichier isolé reçoit donc le niveau d'API le plus permissif et une identité qui change à chaque ajout : bon pour un essai, mauvais pour tout le reste. Un dossier avec manifeste est la seule forme recommandée.

$ ls hello-beaver
beaver-extension.json   index.ts   package.json   package-lock.json

Beaver cherche le manifeste sous trois noms, dans cet ordre : beaver-extension.json, puis beaver.json, puis package.json. Le premier trouvé gagne, les suivants ne sont pas lus. Le point d'entrée doit porter une extension reconnue — js, mjs, cjs, jsx, ts, mts, cts, tsx, mtsx, ctsx — et son chemin est canonicalisé puis vérifié comme restant sous la racine de l'extension : un .. ou un lien symbolique qui sort du dossier est refusé.

Tu poses le dossier où tu veux sur ton disque : Beaver enregistre le chemin canonique et lit la source sur place, sans la copier. Il n'écrit chez lui que son registre, ~/.local/share/cl-go-dash/extensions.json, et les copies gérées des installations Git et npm dans extension-installs/. Deux points sur l'outillage : n'embarque jamais @beaver/sdk dans le paquet distribué, l'hôte résout cet import vers sa propre copie — garde-le en dépendance de développement, pour l'autocomplétion ; et aucune compilation n'est obligatoire, les fichiers .js, .cjs et .mjs passant par l'import natif de Node, tous les autres par Jiti.

Du chargement au premier outil

Beaver charge une extension en trois étapes, que tu retrouveras telles quelles dans les diagnostics. import : l'hôte importe le module d'entrée. activate : il cherche la fonction d'activation et l'appelle avec l'objet beaver — deux formes sont acceptées, un module dont l'export par défaut est une fonction, ou un module qui expose une méthode activate ; sinon, erreur activate_missing. register : il vérifie l'unicité des noms d'outils, encode l'instantané des contributions, contrôle qu'il tient dans le message du protocole, et seulement alors publie les outils. Une extension qui échoue en étape register ne laisse donc aucun outil derrière elle.

Côté cycle de vie : defineExtension ne fait rien à l'exécution, elle retourne son argument tel quel — son seul rôle est de faire vérifier la forme de ton objet par TypeScript. deactivate() est appelée quand l'hôte est remis à zéro ; une exception levée dedans est avalée et le nettoyage des autres extensions continue. C'est là que tu arrêtes tes minuteries, fermes tes fichiers et retires tes écouteurs. Les fonctions de désabonnement rendues par beaver.on et par les enregistrements d'interface sont idempotentes.

Un outil s'enregistre avec beaver.registerTool, et cinq champs comptent. name : Beaver préfixe automatiquement le nom par l'identifiant de l'extension, sauf s'il commence déjà par ce préfixe — un outil déclaré hello dans com.example.hello s'appelle donc com.example.hello.hello pour le modèle. Le nom public complet doit tenir dans 96 caractères : compte le préfixe, c'est lui qui te rapproche de la limite. description : obligatoire, non vide, 2 000 scalaires Unicode maximum ; vide, elle fait échouer l'enregistrement, donc toute l'activation. parameters : un objet JSON, jamais un tableau. effect : voir la section suivante. execute : obligatoire, et doit être une fonction.

Le schéma de paramètres est validé strictement. Sa racine doit porter "type": "object", sinon « Le schéma d'un outil doit décrire un objet. » Seuls 38 mots-clés sont acceptés à tous les niveaux — $ref et $defs n'en font pas partie, donc un schéma qui référence une définition est refusé. La profondeur maximale est de 16 et le total de 256 nœuds.

Ta fonction execute reçoit les arguments du modèle et, en deuxième position, un contexte gelé qui ne contient qu'un champ : workingDirectory. Il n'y a ni identifiant de session, ni langue, ni modèle — ne les cherche pas. Tu peux retourner une chaîne, ou un objet { content, isError?, displaySummary?, truncated? }. Un content en chaîne est tronqué à 1 048 576 unités et displaySummary à 1 024 caractères ; la troncature est silencieuse, elle lève le drapeau truncated sans échouer. L'appel est rejeté au bout de 55 secondes avec tool_timeout — attention, la course rejette la promesse mais n'interrompt pas ton code : ton travail continue en arrière-plan sans que personne n'en lise le résultat.

La classe d'effet

C'est la déclaration qui a le plus de conséquences, et c'est un simple mot dans un objet. Une valeur absente ou mal orthographiée n'est pas refusée : "readonly" au lieu de "read-only" devient unknown, la classe la plus restrictive — l'outil fonctionne, mais il demande confirmation à chaque appel et devient inutilisable en mode Plan, sans qu'aucun message ne l'explique.

Le mode Accès complet contourne la garde de permission pour toutes les lignes : ta classe d'effet ne protège donc que les utilisateurs des modes plus stricts — raison de plus pour la déclarer juste. Côté sous-agents, un profil « explorateur » ne reçoit que les outils d'extension déclarés read-only, tandis que le profil « codeur » les reçoit tous.

Attention La classe d'effet est une promesse, et Beaver la croit. Il ne vérifie pas ce que ton outil fait réellement : il applique la politique correspondant à la classe déclarée. Déclarer read-only un outil qui écrit sur le disque supprime la demande d'approbation et autorise l'outil en mode Plan, un mode où l'utilisateur s'attend précisément à ce que rien ne soit modifié.
Sécurité secret : ce que tu emportes ne revient pas. Une fois une valeur du coffre remise à ton code JavaScript, Beaver ne peut plus garantir son effacement de la mémoire. Désactiver ou supprimer l'extension ne retire pas une copie déjà obtenue : la seule réponse à une fuite est de révoquer le secret chez son fournisseur. Ne l'écris jamais dans un résultat d'outil, un message d'erreur ou un fichier de diagnostic.

Événements et interface

Un seul événement public existe aujourd'hui : session.turn.started. Sa charge utile contient exactement deux champs, sessionId et mode. beaver.on rend une fonction de désabonnement à appeler dans deactivate(). Les bornes : 64 gestionnaires par extension, 64 gestionnaires en vol simultanés, et un budget de 5 secondes par gestionnaire — à l'expiration, Beaver cesse d'attendre mais n'interrompt pas ton code, qui continue de tourner sans surveillance. Une exception dans un gestionnaire ne bloque pas la livraison aux autres extensions.

Pour poser une vue, il faut d'abord déclarer un bloc ui dans le manifeste — sans lui, chaque enregistrement d'interface est refusé. En mode standard, tu décris des données et Beaver dessine : quatre types de contribution (tab, settingsTab, action, theme), cinq opérations de placement (before, after, replace, move, remove), onze primitives de vue, vingt icônes nommées, quarante-sept jetons de thème redéfinissables et sept langues plus default. Ni CSS, ni JSX.

Huit emplacements publics existent : app.navigation.primary pour un onglet d'application ; settings.navigation.preferences, settings.navigation.agent, settings.navigation.models, settings.navigation.integrations et settings.navigation.application pour un onglet de réglages ; app.toolbar.primary pour une action de barre d'outils ; et agent.composer.leading pour une action dans le champ de saisie, le seul limité à la conversation Agent et exclu du chat tiers.

Deux différences de comportement à ne pas rater. registerTool lève en cas de refus ; les enregistrements d'interface, eux, ne lèvent pas : ils rendent une fonction vide et ajoutent un diagnostic. Ton extension se charge, ses outils marchent, et l'interface est simplement absente — il faut aller lire le diagnostic pour le savoir. Et deux occupants sont protégés contre remove et replace : beaver.settings dans la navigation principale et beaver.extensions dans les réglages Intégrations. C'est ce qui garantit qu'un utilisateur peut toujours revenir désactiver ton extension.

Les niveaux d'API

Attention au vocabulaire : le manifeste porte deux champs différents, avec deux jeux de valeurs. apiLevel accepte stable ou advanced ; ui.mode accepte standard ou advanced. Il n'existe pas de niveau d'API nommé standard — c'est un mode d'interface. En pratique, trois combinaisons : apiLevel: "stable" sans bloc ui, qui donne des outils, des événements, des skills et des ressources, et reste le bon choix par défaut ; apiLevel: "stable" avec ui.mode: "standard", qui ajoute onglets, réglages, actions et thèmes décrits en données ; et apiLevel: "advanced" avec ui.mode: "advanced", un module JavaScript chargé dans la même WebView que Beaver.

Attention L'interface avancée partage la page de Beaver, avec les mêmes droits qu'elle. Il n'y a pas de bac à sable, et une boucle synchrone dans ce module bloque toute l'application : la seule sortie est alors de redémarrer, éventuellement avec --safe-mode. Beaver demande pour cela une confirmation supplémentaire à l'activation. N'y va que si le mode standard ne suffit pas.

Le niveau avancé s'impose dans deux cas seulement : manipuler le DOM ou monter une interface que les primitives standard ne permettent pas, et remplacer un outil natif. Ce qu'il ne donne pas : beaver.unstable.call(...) ne peut appeler que des méthodes déclarées avancées dans le contrat, et le contrat actuel n'en publie aucune — les douze méthodes du pont sont toutes stables. Tout appel échoue donc aujourd'hui avec core_method_unavailable. Ce n'est pas une porte dérobée vers le backend.

Distribuer depuis un dépôt Git

Beaver accepte deux formes d'adresse : une URL de schéma https ou ssh — le préfixe git+ est toléré et retiré —, et la forme SCP utilisateur@hôte:chemin. Sont refusés tout autre schéma, donc http:// en clair, une URL sans hôte, un mot de passe dans l'URL, une chaîne de requête, un nom d'utilisateur en HTTPS et un chemin vide.

La révision se met après un # : branche, tag ou commit. Le découpage se fait sur le dernier #, un second # refuse l'adresse, et la référence est bornée à 200 caractères. Une forme abrégée de commit demande au moins 7 caractères hexadécimaux ; une forme complète, 40 ou 64. Ce que Beaver fait de ton dépôt : un clone superficiel — sauf si la référence est un commit complet —, puis la suppression du dossier .git de la copie gérée, la mesure du volume occupé, et l'installation des seules dépendances de production. Le délai global de l'opération est de 300 secondes. Conséquence pratique : précompile tout ce qui exige un script d'installation npm, car les scripts de cycle de vie npm sont désactivés.

Déboguer : ce que tu vois quand ça plante

Attention Tu ne peux rien afficher. Dans le processus hôte, console.log et toutes ses variantes sont remplacées par des fonctions vides, et process.stdout.write est neutralisé — la sortie standard est le canal du protocole entre Beaver et l'hôte. La sortie d'erreur du processus, elle, est jetée à la création. Une extension n'écrit nulle part, aucune trace. C'est le premier réflexe qu'un développeur perd en arrivant sur Beaver.

Ce que tu obtiens à la place est un diagnostic structuré à quatre champs : stage (import, activate ou register), code, file — le nom seul du fichier d'entrée, 128 caractères maximum, jamais le chemin — et line/column si la pile les porte. Ton message d'erreur n'est jamais transmis : il sert seulement à choisir le code.

Ce qu'une extension ne peut pas faire

  • Écrire son point d'entrée dans un autre langage que JavaScript ou TypeScript — elle peut lancer un programme tiers, mais elle doit le fournir.
  • Afficher quoi que ce soit, ni lire l'environnement du compte : console et sortie standard neutralisées, environnement vidé.
  • Écouter autre chose que session.turn.started, ou appeler une méthode du cœur hors contrat.
  • Retirer ou remplacer beaver.settings et beaver.extensions, ni toucher aux composants internes de Beaver en mode standard.
  • Fonctionner en mode Chatbot : les outils d'extension ne sont disponibles qu'en mode Agent.
  • Se faire connaître de tous les modèles : les modèles Groq via OpenRouter ne reçoivent pas les outils d'extension, et groq/compound ne reçoit aucun outil.

Et une limite qui n'en est pas une, à ne pas laisser croire : rien n'empêche une extension de lire tes fichiers, d'ouvrir le réseau ou de lancer des processus. L'accès complet à Node.js est assumé.
