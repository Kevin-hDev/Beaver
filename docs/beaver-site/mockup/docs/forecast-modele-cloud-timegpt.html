The model that runs elsewhere

TimeGPT-2, from Nixtla, is the only remote forecast provider in Beaver's catalog. Nothing is downloaded, nothing is installed: your data goes out to the service, which returns the forecast. This page says what that implies, field by field.

Note This page gives no prices and no usage limits. That information belongs to Nixtla and changes without Beaver knowing anything about it. The sign-up address offered by the catalog is https://dashboard.nixtla.io.

What it is in Beaver

In the interface, these models carry the note “Cloud (key required)”, and the absence of a key shows as “API key not configured”. The provider is called Nixtla (TimeGPT-2) and its displayed description is “Cloud TimeGPT family, API access.”

The catalog contains several variants of this family. What sets them apart isn't described by Beaver: their declared capabilities are nearly identical, and the site doesn't decide in Nixtla's place — its documentation is the authority on that point. None of these variants publishes a parameter count, a file size or a memory requirement: nothing runs on your machine.

What it brings compared to local models

The horizon. The family accepts 5,000 steps — which is also Beaver's absolute bound. Local models cap out between 1,000 and 4,096 depending on the family.

Context variables, with the future. It reads explanatory columns over the past and over the period to be forecast. Among the local models, only Chronos-2 and TimesFM 2.5 can do that.

Non-numeric context variables. Textual categories — a promotion name, a type of day — are accepted: Beaver spots them and flags them as such to the service. A column has to be entirely numeric or entirely textual, past and future combined; a mix is refused with “Invalid covariates”. True and false values are converted to 1 and 0, and a category is at most 256 characters.

Joint multivariate — taking the links between series into account — is only declared by the family's most recent variant, and only under a condition: there must be more than one series and all the series must carry exactly the same dates, history and future included.

Warning Joint multivariate requires perfectly aligned series. If the alignment is missing, the request goes out anyway, in independent-series mode, with no warning on screen. Badly aligned series therefore lose the benefit without anything saying so.

Configuring the API key

The key is entered in the API keys screen, under the Nixtla (TimeGPT-2) provider. It is filed in the encrypted vault like all the others — the full mechanism is described in The vault and API keys.

Three facts specific to Forecast:

  • Until the key is saved, remote models stay visible but not selectable. That's deliberate: they appear in the catalog with the note “API key not configured” rather than disappearing without explanation.
  • The key is read at each forecast, never stored in the analysis. A forecast launched with no key fails with “Nixtla API key not configured”.
  • The key is never written to the traces. On failure, Beaver only records the response's status code.

What exactly leaves your machine

This is the heart of the page, and it can be described field by field.

What does not go out, and is worth stating:

  • No dates. The request contains only values and series sizes; the forecast dates are recomputed on your machine from the frequency and the end of the history.
  • No column names. Columns are transmitted as lists of numbers, in order.
  • No series identifiers. Series are transmitted stuck together, separated by the array of sizes.
  • No other column from the file. The ones you didn't choose as target, date or context are not read.
  • No note, no scenario, no analysis name. Those items live only on your disk.
Key point What goes to Nixtla is your values — not their labels. That is already a lot: a revenue series stays a revenue series. But the context that makes it identifiable — names, dates, other columns — does not leave the machine.

How the call is made, and what becomes of it if it fails

The address of the service is hardcoded in the application: https://api.nixtla.io. It isn't configurable. Authentication goes through a header set at the last moment from a protected copy of the key, erased from memory after use. Redirects are never followed to another server, and a dedicated test checks that neither the key nor the data reaches a redirect's destination.

The timeouts, retries and bounds of the call
ItemValue
Maximum time for one request60 seconds
Maximum client time120 seconds
Retries2, after 2 s then 4 s
What triggers a retryService overloaded or temporarily unavailable

An authentication or request error is not retried: it fails immediately. The message shown is generic in every case — “Prediction service error”.

The response is checked before being accepted: the number of values returned must match exactly the number of series multiplied by the horizon, and every interval bound must be present and finite. An incomplete response is rejected rather than displayed partially.

Note An authentication error is not retried. Only overloads and passing outages of the service trigger two retries, at two then four seconds.

The settings specific to the remote model

This is the only family whose settings concern the model's fine-tuning rather than the context length.

What this model doesn't have, unlike the local models: no adjustable context length, no extra quantiles, no floor at zero. Those settings aren't offered because the service doesn't accept them.

The confidence interval is continuous: any whole level from 50% to 99% is accepted. That's an advantage over TimesFM, Toto, FlowState, TabPFN-TS, TiRex and Kairos, which only offer 60% or 80%.

The remote model and automatic selection

Beaver offers two model-choosing modes, Manual and Auto, described in Model selection. One setting goes with them: whether or not to allow the cloud in Auto mode.

  • Auto mode refuses the cloud by default. The switch stays off until you turn it on, and the default mode itself is Manual.
  • The same setting bounds evaluation. During a backtest, a remote model that isn't the analysis's own is refused if the cloud isn't allowed.
  • Choosing the remote model by hand is always possible, whatever that setting: it only concerns automatic selection.

One thing to weigh before launching an evaluation: evaluating a remote model sends your data as many times as there are windows — three by default, in addition to the original forecast.
