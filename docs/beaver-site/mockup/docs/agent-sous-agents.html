The subagents

The main agent can hand part of the work to a child session, which has its own context and works on its own side. Two benefits: your context stays light, because the tedious exploration happens in the child and only the result comes back; and the work is isolated, because the child modifies files in a separate space, not directly in your folder.

Security Subagents do not ask for confirmation. They run in an internal mode reserved for delegated sessions, which bypasses the permission guard — even if your conversation is set to Ask permission. Control does not disappear, it moves: upstream, when deciding what to delegate, and downstream, by inspecting their changes before applying them.

Following and correcting a running subagent

  • The state of each subagent is visible live.
  • An instruction can be sent to it while it works, to correct it, redirect it or give it a detail.
  • Instructions are queued: eight at most waiting, 50,000 characters each at most.
  • A subagent can be interrupted at any time.

A conversation tab can call for attention when a subagent is waiting for an answer.

Inspecting and applying changes

Each batch of changes goes through four states.

The lifecycle of a batch of changes
StateMeaning
PendingThe subagent has finished, nothing is applied
ConflictThe changes conflict with the current state
AppliedIntegrated into your folder
DiscardedThrown away

Before applying, you see the list of files touched, with the nature of each modification.

Conflict If your folder changed while the subagent was working, its changes move to conflict. Beaver refuses to apply them blindly rather than overwrite your work.

What a subagent cannot do

Delegate in turn. Cascading is explicitly forbidden: the tree is flat, one level deep — your conversation and its children, never grandchildren. This is a design choice: cascading delegation makes monitoring impossible and token consumption unpredictable.

The other restrictions:

  • Be cloned — cloning is refused on a subagent conversation.
  • Write to memory — a subagent can read it, not modify it; it can only propose a note to the parent.
  • Leave its working folder — every path passed to a tool is checked as being inside the subagent's working folder, and any upward traversal (..) is refused, including the working folder given for a shell command.
  • Receive your standing instructions — neither AGENTS.md nor the personality files are injected into a subagent session. If your conventions matter for the delegated task, restate them in the delegation instruction.
  • Have every tool — each subagent receives a restricted tool profile according to its type, and a tool outside the profile is refused.
  • Be archived in any state — archiving refuses certain cases.

Two types of subagent, and only two: explorer and coder. Any other value is refused at delegation time. The coder type additionally requires being started from a valid folder.
