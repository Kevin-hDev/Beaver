Running commands.

bash runs a shell command on your machine, with your user rights: anything you can type in a terminal, the agent can run. It is Beaver's most powerful tool, and it belongs to the Terminal group, locked — it cannot be turned off.

Not to be confused with the interface's built-in terminal, which is your own terminal. The two share neither limits nor processes.

What the tool does

  • Commands start in the conversation's working directory.
  • The agent can target another folder for a specific call, provided it gives an absolute path — and that choice does not persist: the next call starts from the working directory again. Likewise, a cd inside a command does not survive that command.
  • The targeted directory must stay within the allowed folders, otherwise the command is refused before it is even launched.

Which shell is used

On macOS and Linux, Beaver takes the first available shell in this order: the SHELL variable, then /bin/zsh (macOS only), then /bin/bash, then /bin/sh. The candidate must be an absolute path, must exist, and must be one of the recognised shells: zsh, bash, sh, dash, ksh. An exotic shell is ignored and Beaver moves down to the next one. If none fits, the tool returns "User shell unavailable".

On Windows, it is always PowerShell, taken from its system location (System32\WindowsPowerShell\v1.0\powershell.exe), launched with no banner, no profile and in non-interactive mode. The path is never guessed from the PATH.

Windows Commands are PowerShell, not bash. ls, cat or grep mean something else there, or do not exist. The agent knows this; if you read the command, know it too.

Your environment is loaded

This is what sets Beaver apart from a plain sh -c.

  • On the first command call of a conversation, Beaver captures a snapshot of your shell environment: aliases, functions, exported variables, shell options. It is taken by launching the shell in login mode and reading .zshrc or .bashrc depending on the shell.
  • It is then replayed at the start of every command in the conversation. Concrete result: version managers (nvm, pyenv, rbenv, asdf, mise, volta, bun) and the tools installed in your home folder work, whereas they would be nowhere to be found without it.
  • The snapshot is cached per conversation, for up to 64 conversations, and is taken only once.
  • It is capped at 128 KB and abandoned if it takes more than 5 seconds. On failure, commands still run, but without your customised environment — this is the most frequent cause of a "command not found" when it works fine in your terminal.
  • The captured content is handled in protected memory and wiped after use: it may contain tokens exported in a configuration file.

Long-running commands

Beaver does not block on a command that drags on.

  • After a waiting delay — 10 seconds by default, adjustable between 250 ms and 30 seconds — if the command is still running, the tool hands back control immediately with whatever has been produced so far and a session id. The agent carries on reasoning, then comes back to the session with bash_control.
  • There is no maximum duration imposed. A command can run indefinitely as long as no one stops it, unless the agent explicitly sets a delay for that call.
  • Processes launched in the background with & stay attached to the session until they finish.
  • 64 shell sessions can coexist. Beyond that, Beaver reclaims the slots of finished sessions; if all are active, the new command is refused with "Too many active shell processes".
  • A finished session returns its final exit code then disappears from the registry.

While a command is running, its output is shown live in the conversation.

Careful No command has a maximum duration by default. That is intended — a build or a development server should not be cut off halfway — but a process can outlive the question that started it by a long way.

Driving a running session

The four actions of bash_control
ActionWhat happens
PollReturns the output produced since the last visit, and says whether the process is still running
Write inputSends text to the process's input — answering a prompt, entering a password, confirming a choice
Close inputTells the process there will be nothing more to read
StopTerminates the process and all its children
  • Stopping is exclusive: the stop request cannot be combined with sending text or closing the input, the call would be rejected.
  • Sending an interrupt character (the equivalent of Ctrl-C) in the text amounts to requesting a stop.
  • An input is capped at 64 KB and its write is abandoned after 5 seconds if the process reads nothing.
  • A session is only accessible to the conversation that created it. Another conversation gets "Shell session not found", with no further detail.

What is blocked outright

Some commands are refused before any launch, whatever the permission mode, including in Full access. The list is short and targets irreversible system-wide destruction, not ordinary file deletion. The recognised categories:

  • deletion with privilege escalation, and wide-open permissions;
  • writing directly to a disk, formatting a volume;
  • shutting down and rebooting the machine;
  • process bomb, disguised mass deletion, indirect code execution.

Recognition ignores case and repeated spaces, and also applies to the text sent to a running session: you do not bypass the filter by typing the command in a shell that is already open. When a command is blocked, the agent receives a message that names the detected pattern. There is no confirmation screen: it is a refusal, not a permission request.

Note This filter is a guardrail against accidents, not a security barrier. It recognises known phrasings; it does not understand intent. Real protection comes from the permission mode and the disk access scope.

The shell sandbox

Beaver can run commands inside an operating-system sandbox, which genuinely limits what the process can read and write — not at Beaver's level, but at the kernel's.

The native mechanism used per platform
PlatformMechanism
macOSSeatbelt (sandbox-exec), with a policy generated for each command
LinuxLandlock (ABI v3) and namespaces
WindowsDedicated profile and access control lists

This sandbox only kicks in if disk access is restricted. As long as the allowed folders include the root of the disk — which is the default setting — the command is launched directly, with no isolation: there would be nothing to restrict.

When the sandbox is active, writing is limited to the allowed folders plus a temporary folder specific to the command, while reading stays open on the system folders needed to run programs and on the locations of tool managers. If the isolation mechanism is unavailable on the machine, the command fails with "Shell isolation unavailable" — it does not silently fall back to non-isolated mode. A warning may accompany the result when an internal limit was reached while building the policy.

The sandbox's temporary folders live in the application's data and are cleaned up at the end of each command, as well as on the next start-up for any an interruption may have left behind.

A running command does not escape a settings change: if you restrict disk access while a command is running, all active shell sessions are stopped and the requests in flight cancelled. Widening access stops nothing.

Security Restricting the allowed folders does not merely filter paths on Beaver's side: it genuinely locks every shell command inside an operating-system cage. It is the only setting in Beaver whose effect is guaranteed by the kernel and not by the application's code.

What the agent sees of the output

Three ceilings follow one another, from the closest to the process to the closest to the model: 1 MB kept per session, keeping the beginning and the end and dropping the middle with a note of the number of omitted bytes; about 28 KB returned on each visit, split between standard output and error output; and finally at most 2,000 lines or 50 KB for a command, then the general ceiling of 30,000 characters for bash results.

When an output is truncated, the full result is written to disk and its path is given to the agent. Other visible behaviours: a command that succeeds without displaying anything returns "Command finished in N ms (code 0)" rather than an empty result; a command still running shows its session id, its process id and its elapsed time; a stop, a cancellation or a timeout are reported explicitly, with an exit code of -1. Output buffers are wiped from memory after use: a command may display a key.

Modified files are tracked

While a command is running, Beaver watches the working directory and returns the list of files created, modified or deleted. The point of comparison is the repository's Git state when there is one, otherwise a snapshot of the folder. Up to 500 paths are tracked; beyond that, the list is flagged as incomplete rather than presented as exhaustive. When tracking could not start or missed events, the result says so — it never asserts "no changes" by default. These changes feed the diff display in the conversation.

Stopping a command

  • From the agent: bash_control with the stop request.
  • From the interface: stopping the answer in progress cancels the commands launched for that answer.
  • When Beaver closes: all shell sessions are cancelled, with 300 ms of grace, then forcibly terminated.

The stop targets the whole process tree, not just the launched command: a script that started three children leaves no orphans. On macOS and Linux, a clean stop request is sent to the process group, then a forced termination 50 ms later. On Windows, the tree is terminated in one go.
