When a conversation overflows

A long conversation eventually stops fitting in the model's window. Beaver then has it summarized, keeps the latest exchanges and the state of the work in progress, and replaces the history with that summary. This page states precisely what is kept, what is deleted, and what you can configure.

Compression in four sentences When a conversation reaches 90% of the model's window, Beaver has it summarized into nine mandatory sections, keeps the latest exchanges and the state of the work in progress, then replaces the history with that resumption point. The conversation carries on where it was, with nothing for you to do. If anything fails, your conversation stays intact. Everything is configurable in Settings › Advanced › Compression, and you can trigger the operation at any time by sending /compress.

The context window is finite

A language model does not read a conversation as it goes: it rereads the whole conversation for every answer. That reread has a maximum size, the context window, counted in tokens. A conversation that grows longer therefore ends up not fitting inside it.

This window is not the same everywhere, and Beaver determines it differently depending on the type of model.

  • Remote model — the length declared by the provider's catalog.
  • Local model — the first value available in this order: the window of the model already loaded, then the one written in its definition file, then the smaller of the model's native window and the tier derived from your hardware.

In other words: on a local model, the window actually used is often smaller than the one the model advertises, because your machine decides. See Hardware and VRAM and Local engine.

What compression does

Beaver asks a model to summarize the conversation in a mandatory format, files that summary along with a few recent items into a resumption point, then replaces the history with that resumption point. The conversation carries on where it was, in the same thread, with far fewer tokens.

Two properties to know up front.

  • The saved conversation is genuinely replaced. This is not a collapsed display: your conversation file no longer contains the old messages after the operation.
  • The replacement is all or nothing. Beaver builds the complete resumption point, validates it, checks that it fits the intended target, and only replaces the conversation at the end, in a single write. If anything fails along the way, the conversation stays exactly as it was.

When it triggers

Two triggers, one engine behind them.

Automatic. After every answer and every series of tools, Beaver checks whether the conversation has reached the threshold of the active profile. The condition is simple: estimated tokens ≥ window × threshold. The threshold of the profile shipped with Beaver is 90%. It can be set from 1% to 90%, and the engine caps it back to 90% at run time whatever happens.

A third check happens during the generation of an answer: Beaver watches the total every 32 tokens produced and interrupts the answer in progress as soon as the threshold is crossed, instead of waiting for the end. That is why an answer can stop dead and be followed by a compression.

On request. You send the message /compress. See Compression on request further down.

What you see on screen

During. A discreet banner replaces the usual work indicator: two horizontal bars pulsing on either side of the text “Context compression”. It shows neither a percentage nor a duration, and is not clickable. The animation disappears if your system asks for reduced motion.

The send button becomes a stop button during the operation, as it does for a normal answer. The input field itself stays editable.

After. At the exact point of the cut, the thread shows an archive icon followed by the text “Context compressed”. This marker cannot be expanded: the summary produced cannot be viewed anywhere in the application, even though it does exist in the conversation file.

The context ring, next to the input field, shows the conversation's active compression profile under the label “Compression”, or “Compression disabled” when it cannot apply. In that second case, a help button opens an explanation. See Conversations.

On failure, five distinct messages depending on the cause — the table is at the end of the page.

What is kept, what is deleted

Warning Compression genuinely deletes the old messages. This is not a display fold: your conversation file no longer contains them after the operation, and there is no way to get them back. What remains is the summary, the latest exchanges and the state of the work. If an old exchange matters to you, copy it elsewhere before the conversation grows long.

Anything not in the table below disappears from the conversation and survives only in the form of the summary.

What is carried over as is, message by message
ItemHow it is chosen
Recent messagesA quota per role — half rounded up for you, half for the assistant — then the remaining slots are filled from newest to oldest
Tool chainsA call and its results are taken whole or not at all; an over-long result is replaced by a bounded excerpt pointing to the full result kept on disk
The current turnAlways kept in full, outside the quota
ImagesThe images of the retained messages, within the profile's limit and the provider's

Alongside these messages, Beaver rebuilds four blocks and files them into the resumption point, in this order and as long as room remains:

  1. the state of the work — Git state, tasks in progress, unresolved failures, subagent reports;
  2. the recent files, reread from disk — that is, their current content;
  3. the text attachments, at most 8;
  4. the critical references, at most 32.
Note Files are reread, not copied over. The resumption point contains the current content of recently consulted files, not the content the agent had seen. This is deliberate: it lets the agent resume on the real state of your project. But if a file has changed in the meantime, it is indeed the new version that enters the resumption point.

The /compress message itself is excluded everywhere: it enters neither the kept messages nor the history sent to the model that writes the summary.

What compression keeps and what it loses

The summary and its nine sections

Beaver sends the conversation to a model with a fixed contract that nothing can alter. That contract imposes exactly nine sections, in this order. The headings are produced in English, exactly as shown below.

  1. Primary Request and Intent — the initial request and the intent
  2. Key Technical Concepts — the technical notions involved
  3. Files and Code Sections — the files and code sections
  4. Errors and Fixes — the errors encountered and their fixes
  5. Problem Solving — the resolution
  6. User Intent and Corrections — your intentions and your corrections
  7. Pending Tasks — what is left to do
  8. Current Work — the work in progress
  9. Next Step — the next action

The summary is checked before being accepted, and a single defect gets it rejected: a tool call, a truncated response, a missing opening or closing tag, text after the closing tag, empty content, one of the nine sections missing or in the wrong order, or exceeding the profile's token ceiling.

Security Your conversation is treated as data, never as instructions. The model that writes the summary receives a contract that no conversation content can alter, and the history is explicitly presented to it as untrusted data. A profile's custom prompt is introduced as an additional objective, which cannot override the contract. The model is forbidden from revealing secrets and from mentioning your permission settings — and automatic filtering removes sensitive data from the summary, the sections and the messages sent in any case. See The vault and API keys.

What the conversation becomes afterwards

The resumption point takes the form of two technical messages carrying the same turn identifier: one message containing the resumption point document — format number, identifier, summary and sections filed by name — and a boundary message carrying a fixed text. In the interface, the first becomes the “Context compressed” marker and the second is hidden entirely.

The intended target. Beaver does not aim to fill a percentage of the window: it targets 20% of what is compressible, that is, everything except the system instructions and the tool definitions, plus those latter as they are. That result is further capped by the size of the window.

Resumption point ceiling by model window
Model windowResumption point ceiling
Under 64K10,000 tokens
From 64K to under 128K20,000 tokens
128K and above28,000 tokens

Two guards on the way out: if the resumption point built exceeds the target, compression fails instead of publishing an oversized result; and if the compression was automatic and the result stays above the threshold, it fails as well — Beaver refuses to publish a compression that would have fixed nothing.

The protections: loops, failures, writing

The anti-loop guard. Every automatic attempt is identified by a set of markers: last turn, last message, message count, last resumption point, provider, model, window, profile and its revision. Three rules follow.

  • An attempt identical to the previous one is not replayed.
  • A successful compression cannot run again within the same main turn.
  • Any change of environment resets the counter — switching model or profile unblocks a stuck conversation.

After three consecutive failures, automatic compression pauses for that conversation. The message shown says so and gives the way out: “Automatic compression is paused for this session after repeated failures. You can retry with /compress.”

Writing is transactional. Before replacing anything, Beaver checks that the conversation on disk is still identical, byte for byte, to the one it photographed at the start. If a message arrived in the meantime, the compression is abandoned rather than applied to a stale state.

Finally, the summary request has a 600-second wait ceiling, with the same value as an idle timeout: beyond that, it is abandoned and the conversation stays intact.

The three window sizes, and small models

A profile does not carry one set of settings but three, one per window size. The boundaries are fixed.

The three window ranges and their label in the application
RangeModel windowLabel shown
Smallunder 64,000 tokens“under 64K”
Mediumfrom 64,000 to under 128,000“64K – under 128K”
Large128,000 and above“128K and above”

Under 64,000 tokens, compression is disabled by default. This is not an oversight, and the application gives the reason:

“Compression is disabled because this context window is under 64K. These small windows may not leave enough room to generate and then reinject a summary, instructions, tools, and recent exchanges. You can allow it in the advanced compression profile.”

So the permission does exist, and the advanced editor pairs it with its own warning: “For models under 64K, an oversized configuration can fill the context window. The session may run into problems and compression may fail if it reinjects too much context.”

Warning Under 64K, nothing happens and nothing says so. On a model whose effective window is under 64,000 tokens, compression is disabled by default and the automatic trigger gives up without a message. The conversation keeps growing until it fills the window. The only place this shows is the context ring, which then displays “Compression disabled”.

Compression profiles

A profile gathers everything configurable: the threshold, the permission under 64K, the two prompts, and the three sets of settings per window range. Beaver ships a single one, named “Beaver”. Here are its values.

Maximum summary size2,000 tokens4,0006,000

Threshold: 90%. Compression under 64K: disabled.

What you can do. Create up to 20 profiles, rename them, edit them, delete them, restore the Beaver values, and restore only the prompts without touching the rest. The “Beaver” profile can be neither renamed nor deleted; it can only be reset to its original values. Deleting a profile can be undone for 30 seconds, through a button in a notification.

Two levels of choice. The global profile is chosen in Settings › Advanced › Compression. A conversation can use a different one, chosen from the “+” menu of the input field, entry “Compression”. The per-conversation choice wins, as long as the global selection has not changed: if you change the global profile, conversations fall back to it and you have to choose again.

The budget projection. The bottom of the editor estimates, before any use, what the profile would send: the system and tools share, the share reinjected by the profile, the estimated target and the expected reduction as a percentage. The calculation is run on a demonstration conversation of 96,000 tokens, of which 12,000 are the system head, and not on your real conversation; the result is rounded in steps of 8,000 tokens. It is a tool for comparing profiles, not a prediction.

Compression on request: /compress

The path, step by step:

  1. typing / in the input field opens the list of commands;
  2. compress appears there as a built-in command;
  3. selecting it only writes the text /compress into the field;
  4. you then have to send it like a normal message.

There is no dedicated button or keyboard shortcut. The command is recognized only if the message contains nothing else: surrounding spaces are tolerated, an added word is not. On sending, Beaver does not answer — it compresses and stops there.

Note /compress ignores your trigger settings. It looks at neither the threshold nor the “Automatic compression” switch: it compresses right away. And unlike the automatic trigger, it tells you why when it cannot. It is the right reflex in three cases: before changing subject in a long conversation, when automatic compression has paused itself, and when you want to compress without waiting for the threshold.

Where all of this is stored

The profiles, the global profile and the automatic compression switch live in a single file in Beaver's data folder, compression-profiles.json. The resumption points and the compression counter live in the conversation file itself.

$ ~/.local/share/cl-go-dash/compression-profiles.json

This file carries a version number, is bounded to 1 MiB, is written atomically, and follows the project's tolerant-reading rule: a file written by a newer version of Beaver is refused, never rewritten; an unreadable file is replaced by the factory values, but the backup of the old format is kept permanently, next to it, under the name compression-profiles.v1.bak — because a factory repair does not prove that your profiles were recovered.

The compression settings used to live in config.json. They are carried over automatically on first access, then removed from that file once saved.

The last message is a catch-all: about ten distinct internal causes lead to the same text. Its final sentence — “Your conversation was not changed” — is accurate, and that is the information that matters.
