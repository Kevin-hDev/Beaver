How the agent works

When you send a message, Beaver does not answer in one shot: it loops until the work is done. This page describes that cycle, the five ways it ends, and why it sometimes stops on its own when nothing has failed.

The loop

On every turn:

  • Beaver sends the model the conversation, the instructions and the list of available tools.
  • The model replies: text, tool calls, or both.
  • Beaver runs the requested tools, asking for confirmation where needed.
  • The results are added to the conversation.
  • It starts over.

The loop stops when the model no longer asks for a tool: it is done, it answers. This cycle is what separates an agent from a chat — a chat stops at the second step.

The loop is the same in Chatbot mode. It is not reduced to a single turn: what is reduced is the tool catalog, cut down to web search and reading a page. A Chatbot turn can therefore chain a search, the reading of a page, then the answer. See Permission modes.

The stopping conditions

Five ways for a conversation turn to end.

The five possible endings of a turn
CauseWhat happens
The model is doneNo more tool calls: this is the normal exit

200 turns reachedHard limit; the model is told the end is near before the last turn
Loop detectedSix identical tool calls in a row
Blocking errorContext full, model unavailable, unrecoverable network failure

The 200-turn limit is generous: it is a safety net against an infinite loop, not a work ceiling. The model is warned before reaching it, which lets it wrap up cleanly rather than being cut off.

One case worth knowing: if subagents are still working, the loop may continue past the point where the model stops calling tools, until they hand back their result. See Subagents.

The anti-loop guard

Six consecutive identical tool calls stop the conversation. Same tool, same arguments, six times in a row: the model is going in circles and will not make progress on the seventh attempt. Beaver would rather hand control back to you than burn tokens.

Why it stops on its own If the conversation stops with a message when nothing has failed, this guard is the likely reason. Rephrase your request, or switch models.

Tools in parallel

When the model requests several read tools at once, Beaver runs them in parallel, in batches of ten. On an exploration that reads fifteen files, that means two waves instead of fifteen successive waits.

Tools that modify things do not take this path: they run one after another, to stay predictable.

Better still: read tools start before the model has finished writing. As soon as a read-only tool call appears in the response stream, Beaver launches it without waiting for the end of the message. The same ceiling of ten simultaneous calls applies, and a tool that requires confirmation never enters this mechanism.

Reasoning

Some models think before answering. Beaver displays that reasoning, separated from the answer. When a local model produces malformed reasoning, a recovery mechanism keeps internal tags from polluting the display.

Setting the effort level is described in Reasoning.

Interrupting, queuing

Interrupting is possible at any time. Cancellation is checked on every turn and before every tool: it takes effect quickly, without waiting for the current turn to finish.

Note You do not have to wait in front of the screen: a message sent while the agent is working is queued and handled once the turn ends.

When the connection drops

If the response stream is cut off midway, Beaver keeps what was received and carries on rather than losing the turn. Stream failures are recorded in the conversation — useful for spotting an unstable provider. They are not carried over into a clone.

Local models and video memory

A frequent question: does the local model stay loaded in the graphics card between two messages? Yes, for an adjustable amount of time — and it is not tied to the end of the loop. No unload is triggered when the agent finishes its work: Beaver attaches a keep-alive duration to every request, read from the advanced settings.

How long the model stays in video memory
Setting valueEffect
5 minutes (default value)The model is released after five minutes without a request
Another durationThe model is released after that duration without a request
AlwaysThe model is never unloaded

The trade-off is noticeable: a released model gives its video memory back to other applications, but the next message pays the reload time; a model kept in memory answers immediately and occupies the card permanently. This setting only concerns local models — cloud models do not go through this mechanism.
