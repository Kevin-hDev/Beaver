Updating Beaver

Beaver updates itself from the releases of its GitHub repository, after checking four elements of the downloaded file. This page says how it is triggered, what is checked, and what stays untouched.

How updates are detected

Beaver queries the latest published release of the official GitHub repository, at launch and then every hour, and compares your local version to the release tag. When an update exists, a notification appears, with a progress bar during the download.

This check works without authentication because the repository is public: that is a deliberate constraint of the project.

What is checked before installing

This is what explains why an update can be refused. The expected asset depends on the system: .dmg on macOS, .deb on Linux, -setup.exe on Windows. Beaver requires the release's update-manifest.json file to confirm four elements:

  • the same version as the one announced;
  • the same file name;
  • the same size;
  • the expected SHA-256 fingerprint.

If a single one of these does not match, the update is not offered. The download is capped in size, and the fingerprint is re-checked on receipt. The principle: when in doubt, Beaver refuses to update rather than install an unverified file.

The installation per system

One thing common to all three systems: Beaver copies a standalone helper program into a temporary file, closes itself, and lets that program do the work. The helper waits for the application to fully close before touching anything, and uses no intermediate shell.

An important point if you installed Beaver somewhere other than the suggested folder: the update replaces the installation actually running, not a default path. You do not end up with two copies.

If the installation fails

If the application does not restart after an update, manually reinstall the last version you knew to be working, from its GitHub release. Your data is not touched and is picked up by the reinstalled version.

Do not use the install script The first-installation script refuses to replace an existing installation. Go through the built-in update.

Ollama model updates

This is a mechanism separate from the application's, not to be confused with it. Beaver lists the installed models and queries the registry for each family; the comparison is on digests, not on a version number. Models with an update available are flagged, and the check is run again after every model download.

What is never touched

This is the question you ask yourself before clicking. An update touches neither your conversations, nor your memory, nor your API keys and your vault, nor your settings, nor your downloaded Ollama models. The data folder is independent of the installed application.

Your data is kept An update touches neither your conversations, nor your memory, nor your keys, nor your models. They live in a folder separate from the application.
