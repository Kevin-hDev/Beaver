Git branches.

The agent has two dedicated Git tools, and only two. They form the Git branches group, optional and off by default. Everything else — commits, merges, pushes — goes through shell commands you watch run.

Two tools only

The Git branches group
ToolRoleApproval
create_branchCreates a branch from the current state and switches to itYes
checkout_branchSwitches to an existing branchYes

Both ask for approval in Ask permission mode. They are the only two Git operations the agent performs through a dedicated tool.

Why so few

This is a deliberate design choice. Complex Git operations — merging, rebasing, amending a commit, pushing to a remote — do not go through dedicated tools. They go through the terminal, where the agent types the commands just as you would.

The upside: nothing to reimplement, nothing to maintain alongside Git, and you see exactly which command runs rather than an opaque tool doing "something" to your repository.

The two dedicated tools exist because they are the two most frequent operations, and because they benefit from careful error handling — notably the refusal to switch with unsaved changes.

Creating a branch

  • The branch starts from the repository's current state, and the agent switches to it immediately.
  • The repository targeted is the one in the conversation's working directory.
  • Creation fails if a branch of the same name already exists. Nothing is overwritten.

Switching branches

  • Switches to an existing branch.
  • Fails if unsaved changes remain. The message states how many files are affected, and asks that they be reviewed and preserved before carrying on.

This refusal is the most useful behaviour of the two tools: it prevents a branch switch decided by the agent from losing work in progress.

Key point Switching branches fails if unsaved work remains, and the message says how many files are affected.

Two cases are handled separately, and that is deliberate: when Beaver cannot confirm that a branch creation or switch went through, the message does not say "failed" but "could not be confirmed". The nuance matters, because the operation may well have succeeded. These cases are never replayed automatically.

Note "Could not be confirmed" is not "failed". When Beaver cannot verify the result of a Git operation, it says so this way rather than asserting a failure, and the agent checks the repository's state before starting over.

Everything else goes through the terminal

Anything that is not creating or switching a branch is written as shell commands:

  • listing branches, checking the status, reading a diff, browsing the history — read commands, run without approval because they are among the commands recognised as safe;
  • committing, merging, rebasing, pushing — commands that modify, and therefore subject to the permission mode like any other command.
Careful Turning off the Git branches group does not stop the agent touching Git: it will do so through the terminal, which is locked. This group only controls two shortcuts, not access to Git. To genuinely limit what it does to your repository, the lever is the permission mode.
