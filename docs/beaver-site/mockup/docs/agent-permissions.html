Permission modes

What the agent may do without asking you, what triggers a confirmation, and how you change that. This is the page to read in full if you care about knowing exactly where the line runs.

Warning On installation, Beaver is set to Full access: the agent runs its tools without ever asking. Switch to Ask permission if you would rather approve each sensitive action.

The three modes

The modes offered inside a conversation
ModeBehavior
Full accessThe agent runs its tools without ever asking
Ask permissionSensitive actions trigger a confirmation
ChatbotTwo tools only: web search and reading a page

Full access is also the fallback value. If the settings file is missing, unreadable or holds an unknown value, the mode used is Full access.

What Chatbot mode does exactly

Chatbot mode is not “no tools”. The agent keeps web_search and web_fetch: searching the web, and reading a page. In other words, it can neither read nor write on your machine, but it can still fetch information online.

The restriction rests on two simultaneous barriers. The catalog sent to the model is cut down to those two tools before it is sent, for remote providers and local models alike: the model does not know the others exist. And if a model invents a tool name anyway, the call is refused at execution time.

Chatbot is not “toolless” In Chatbot mode, the agent keeps web search and page reading. It also does not receive your standing instructions: AGENTS.md and the personality files are not injected. An instruction that seems ignored in this mode really is.

What triggers a request

In Ask permission mode, twelve tools always trigger a confirmation: write_file, edit_file, web_fetch, write_spreadsheet, write_document, create_branch, checkout_branch, apply_subagent_changes, manage_automation, forecast_data_audit, forecast_run, forecast_backtest.

Four tools trigger a confirmation conditionally.

The conditional tools
ToolCondition
bashThe command is not recognized as safe
bash_controlCharacters are sent to the process
transform_imageAt least one operation is requested
search_mcp_toolsThe mode is calling a tool — merely searching for tools asks nothing

Every other native tool goes through without confirmation, including in Ask permission mode: reading a file, listing a folder, searching by name or by content, searching the web. This is a design choice: asking for confirmation on every file read would make the mode unusable, and you would end up approving everything without reading.

Tools provided by an extension

They fall outside both lists above. Whether they need confirmation depends on the declared effect the extension gives that tool.

Confirmation by declared effect
Declared effectConfirmationCan be remembered for the session
Read onlyNoNo
External read (network)YesYes
Local write, external writeYesYes
Process execution, sensitive data, unclassified actionYesNo

Only read-only goes through without asking; everything else is confirmed.

Shell commands: the special rule

A bash command goes through without confirmation if it satisfies all three conditions at once: it touches no sensitive data, it contains no control operator, and it matches one of the patterns recognized as safe.

The operators that disqualify a command — their mere presence is enough, fifteen checks: ; && || | ` $( <( >( << > < & $', the line feed and the carriage return.

In other words: ls goes through, ls | grep foo does not. The reason is solid — an operator lets any command be chained behind an innocuous one.

The patterns recognized as safe cover about twenty families of commands, all of them reads or checks.

The command families that go through without confirmation
CategoryCommands
Reading filesls, cat, head, tail, wc, file, stat
Searchgrep, find, tree
Systempwd, echo, which, du, df
Git readsgit status, git log, git diff, git show, git remote, git tag, git branch on its own
Project checkscargo check, cargo test, cargo clippy, cargo build, npx tsc, npm run, npm test

Any other command triggers a confirmation. One case is worth flagging: git branch on its own is safe, git branch -d is not. It is the only pattern in the list that refuses every option; the others accept arguments after the command name.

Note In Ask permission mode, a read command recognized as safe — ls, cat, git status — runs without confirmation. As soon as a command contains a chain, a redirection or a sensitive path, confirmation is requested.

Sensitive data

A command that mentions a sensitive path is always subject to confirmation, even if it matches a safe pattern. A cat ~/.ssh/id_rsa does not go through.

Sixteen markers are watched: .env, .ssh/, /.ssh, id_rsa, id_ed25519, id_ecdsa, id_dsa, .npmrc, .pypirc, .netrc, .aws/credentials, .config/gcloud, .kube/config, credentials, login.keychain, keychain-db.

Four application files are also protected: config.json, secrets.enc, agent-settings.json, configured-providers.json.

One refinement avoids false alarms: the content of multiline text blocks is stripped before analysis. Writing a .gitignore that mentions .env triggers nothing; only a real path passed as an argument counts.

The three possible answers

Answering a confirmation request
AnswerEffect
Allow onceThe action runs, once
Always allowThe action runs, and the tool stops asking — under conditions
DenyThe action is not run

“Always allow” and its exceptions

Three tools are never remembered, whatever you answer: bash, bash_control and search_mcp_tools. Every call asks again. The reason is a good one: those three tools can do anything depending on their arguments, and allowing bash once for the session would amount to switching to Full access without realizing it.

For the other tools, the authorization is remembered within bounds.

Bounds on what is remembered
BoundValue
Validity period1 hour
Sessions remembered64 at most
Tools remembered per session16 at most

Expired authorizations are purged automatically.

Warning The “Always allow” option applies neither to shell commands nor to external tool calls. Those actions ask again every time, because the same command can do anything depending on its arguments.

What happens in case of doubt

The principle is denial by default. Three situations:

  • the conversation is cancelled while a request is pending: denied;
  • more than 64 requests are waiting at the same time: automatic denial;
  • an answer arrives for an unknown or stale request: it is ignored and logged.

Every decision is written to logs/permission-diagnostics.jsonl, rotating at 2 MB.

Subagents do not ask

Security Sessions delegated to subagents run without confirmation, even if your conversation is set to Ask permission. Control happens upstream, when deciding what to delegate, and downstream, by inspecting their changes before applying them. See Subagents.

Changing mode

  • The mode is changed from the conversation, at any time, through a dedicated selector.
  • The keys 1, 2 and 3 select a mode directly when the selector is open.
  • A default mode is set in the settings.
  • The mode is specific to each conversation.
