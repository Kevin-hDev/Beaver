Forecast, when the calculation fails

A forecasting model that won't install, rejected data, a calculation that stops dead. This page starts from the message displayed and works back to the real cause — which, on Forecast, takes a detour, because the panel has only three messages for some thirty different failures.

Note The message displayed almost never names the cause. The forecasting engine produces precise sentences — “Modèle non installé”, “Ressources insuffisantes pour ce modèle”, “Clé API Nixtla non configurée”, written in French whatever your language — but the Forecast panel replaces them all with a single one. When “The calculation failed” is not enough, ask the agent for the same forecast in a conversation: it receives the engine's exact sentence and shows it to you. That is the most useful piece of advice on this page.

Before looking: the two places where the message differs

The same failure produces two very different texts depending on how the forecast was launched. That is the first sorting to do, and it avoids half of the fruitless searching.

From the Forecast panel — importing a file, then the Launch forecast button — only three messages are possible.

The only three messages of the Forecast panel
What is shownWhen
“Import failed. Check the file format.”The file could not be read
“The calculation failed. Check the columns, model, and API key.”Any failure during the calculation
“Forecast storage is full. Delete older analyses, then try again.”The only special case recognized

The second sentence covers some thirty distinct causes. It names three leads — the columns, the model, the API key — but it does not say which one is at fault, and sometimes the cause is none of the three.

From a conversation with the agent (“forecast this file for me”), the engine's exact message is returned as is in the tool result, along with the suggested next step. That is the only place where the true sentence appears.

The Forecast workspace screens — Data, Scenarios, Comparisons, Notes, Evaluation — follow the same rule: they show a translated, generic message, never the engine's.

The forecasting model won't install

What you see, next to the install button, is unique: “Download failed”. The engine passes on only one failure code, whatever the real cause.

A second message exists, and it does not mean the same thing: “This model could not be added to the queue.” That one means the installation did not start — the queue is full, sixteen downloads waiting at most.

The real causes, in the order in which they occur
CauseSentence produced by the engine

Warning Local forecasting models require Python 3.12. Exactly 3.12: neither 3.11 nor 3.13. Beaver looks in turn for python3.12, python3 then python on the system path, and accepts only that version. It is the only external dependency of the local models, the app does not install it and has no fallback. Without it, the installation fails with the generic message “Download failed”, which does not say that Python is at fault. 
$ python3.12 --version

The corporate network case. The weights come only from huggingface.co and related domains, and the Python libraries only from pypi.org, with mandatory checksum verification and refusal of any package that would need compiling. An internal mirror, a proxy that rewrites responses or a block on these two domains makes the installation fail, and no setting allows it to be redirected.

Warning An interrupted installation starts over from zero. There is no resume: the temporary working folder is deleted on the first error, and every file being written is erased with it. Nothing already downloaded is kept. On a model of several gigabytes and an unstable connection, it is better to start the installation at a time when the machine will not be cut off.

The installation seems stuck

This is the most common symptom, and it is not a failure. The progress bar does not measure one operation but four, and the third is long and silent.

What the bar shows, and what is really happening
What the bar showsWhat is really happening
0 to 70 %Downloading the model weights
72 %Creating the Python environment
76 %Preparing the library installer
80 %Installing the Python libraries — the longest step
98 %Verifying the engine
99 %Putting the model definitively in place

The phase shown next to the percentage carries the labels Downloading, Preparing engine, Installing, Completed.

Note The bar stuck at 80 % is not a failure. That is the installation of the Python libraries. It can last several minutes without the percentage moving, then jump to 98 % and 99 %: it is not continuous progress, it is four steps.

At the very end, a real test of the model is run, with a maximum of fifteen minutes — a failure at that point cancels the whole installation.

Cancelling is possible at any time, using the Cancel button or the Esc key when the models screen is in the foreground. Cancelling deletes what was downloaded.

The model is installed, but Beaver shows “Preparation required”

Beaver distinguishes four states for a local model.

The four states of a forecasting model
What you readWhat it means
“Not installed”The weights are not there
“Preparation required”The files are there but do not have the expected size
“Update required”The receipt, the engine or the validity test is no longer up to date
“Installed”The five conditions are met

Reaching “Installed” requires five things at once: the model folder and its .complete marker, files of the expected size, an .artifacts-v1.json receipt matching the catalog of the installed version, a Python engine ready for the model's family, and an up-to-date test proof.

What to take away from this: after a Beaver update that changes the list of Python libraries, an already installed model flips to Update required, and the button shows Prepare instead of Install. The weights are not downloaded again: Beaver recognizes that they are valid and only redoes the engine and the validation.

One display quirk worth knowing: files that are present but the wrong size — typically after an interrupted copy — have no label of their own and also fall back on “Preparation required”. The Prepare button then does start a full download. The display is misleading, the action is the right one.

“Insufficient resources”: memory

Beaver measures the available memory before launching a local model and refuses rather than letting the machine collapse. There are two distinct refusals:

  • “Ressources insuffisantes pour ce modèle” — the memory was measured, and it does not cover the model's need plus 20 %.
  • “Ressources indisponibles pour ce modèle” — the memory could not be measured and the model asks for more than 2,048 MB. Below that threshold, Beaver lets it through.

The detail of the calculation — video memory versus main memory, the five verdicts — is in Model selection.

Warning Nothing checks the memory before downloading. This check only happens when a calculation is launched, never at installation. You can therefore install several gigabytes of model, then discover on the first calculation that the machine cannot run it. Check the memory required on the model's card before installing — see Hardware and VRAM.

One point that sometimes saves the situation: the memory measured is the one available at the time of the calculation. Closing a browser can be enough to let through a model refused five minutes earlier.

The most efficient sorting, in this order:

  • Is the chosen model marked “Installed”? If not, that is where it stops.
  • Does the Data section report a blocking error? If yes, that is it.
  • Is the model remote? Then check the key.
  • Otherwise, run the same request through the agent to read the exact sentence.

TimeGPT-2: key, quota, outage

With no key saved, the models screen shows “API key not configured” in place of the “Cloud (key required)” label, and the calculation is refused.

With a key, the call goes to Nixtla's forecasting service with a timeout of 60 seconds per attempt, three attempts at most, and pauses of 2 then 4 seconds. Retries are reserved for four situations: 429 (too many requests), 502, 503 and 504. A rejected key or an exhausted quota are not retried: the failure is immediate.

Every outcome produces the same sentence: “Erreur du service de prédiction”. Invalid key, quota exceeded, service down, malformed response: nothing tells them apart on screen. The only place carrying the information is Beaver's technical log, which writes the HTTP code returned, without the response body.

What you can do, for want of anything better: check the key's validity from the API keys screen — a test button exists and queries the provider, see The vault and API keys — then check the service status at Nixtla. If the key test passes and the calculation still fails, it is the quota or the service.

The detail of the model's variants, their settings and what leaves the machine is in TimeGPT (cloud).

The local engine won't start

Between the click on Launch forecast and the calculation, Beaver starts a small local Python service. All of its failures become “The calculation failed” on screen.

The five failures of the local forecasting service
CauseSentence produced by the engine
The previous service refuses to stop“Sidecar Forecast indisponible”
The service file is missing“Sidecar Python non installé”
The Python engine for this family is not ready“Moteur Forecast non préparé”
The process does not launch“Impossible de lancer le sidecar Forecast”
The service does not answer in time“Sidecar Forecast: timeout au démarrage”

The start timeout is thirty seconds. On a slow machine or for a large model, a first launch can therefore fail while nothing is broken — trying again is a useful action here, unlike most of the other failures on this page.

Note An installed model computes without the internet. The forecasting service is started in offline mode, listens only to your machine on a free port chosen at launch, and is protected by a token drawn at random on every start. It can download nothing during a calculation — which also explains why an incomplete installation fails instead of repairing itself. Only the installation needs the network.

“Forecast storage is full”

This is the only precise message the panel knows how to show: “Forecast storage is full. Delete older analyses, then try again.” The real mechanism is subtler than the sentence:

  • the limit is 500 analyses in total;
  • once that limit is reached, Beaver automatically deletes the oldest analysis of the same workspace and saves the new one;
  • the message only appears if the current workspace contains no analysis to delete — that is, when all 500 analyses belong to other projects or conversations.
Warning The message's advice does not apply where it is shown. Deleting older analyses is indeed the right action, but you must delete them in the other workspaces — not in the one where the message appears, since that one is precisely empty of any analysis.

A second, separate limit exists: an individual analysis cannot exceed 64 MB once saved, otherwise it is refused with “Analyse Forecast trop volumineuse”. It is met on forecasts with very many series.

What has no solution

Without softening it: in these cases, no way out is provided.

  • Telling a rejected TimeGPT key from an exceeded quota. The message is the same and nothing in the interface separates them.
  • Knowing which data anomaly is blocking, from the screen. The counter gives the number, never the name. The detour through the agent is the only route.
  • Knowing why an installation failed. A single failure code for some fifteen causes.
  • Resuming an interrupted installation. Everything is deleted and downloaded again.
  • Running a local model without Python 3.12. No fallback, no setting, no built-in backup engine.
  • Using an internal package mirror. The addresses of huggingface.co and pypi.org are not configurable.
  • Installing a model on a machine with no internet. The weights and the libraries are downloaded at installation; only running them afterwards works offline.
