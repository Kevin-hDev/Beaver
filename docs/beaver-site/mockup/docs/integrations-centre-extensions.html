The extension center

An extension adds capabilities to Beaver: tools for the agent, skills, resources, interface elements. This page covers the full cycle — finding, adding, approving, enabling, updating, removing — and says plainly what you take on by installing code written by someone else.

What an extension can do to your machine

An extension is code written by someone else, which Beaver runs on your computer with your account's rights. It can read and write your files, launch programs and use the network, exactly like software you would install yourself.

Warning An extension is not in a sandbox. Beaver isolates each extension in its own process: that stops one from bringing the others down, it does not stop it from doing whatever it likes with your machine. Beaver's technical documentation says so itself — "a custom extension is trusted local code, executed with the rights of the user account. This is not a sandbox" — and this page does not soften that.

Two direct consequences. An approved extension can ask for your API keys and tokens directly, through the development kit's interface: approval covers all of its code and all of its dependencies, and there is no per-key permission. And Beaver does not check what an extension does: it validates the manifest and the protocol, which is no substitute for auditing behavior. The manifest of a Node.js extension declares access: "full", and the code explains why in a comment: local Node.js code is not a security boundary.

What the isolation does bring is real: a separate process per third-party extension, so one crashing does not stop the others; an identity assigned by Beaver rather than declared by the extension, so none can impersonate another; a minimal process environment, so your environment variables are not passed on; a file fingerprint, which revokes approval as soon as a file changes; and a secret-access log, which records every handover without writing the secret.

Four official plugins ship with Beaver 1.2.2, all enabled and shown in the chat by default: Documents (beaver.office.documents) to create and edit editable DOCX files, PDF (beaver.office.pdf) to read, create, merge and verify PDFs, Spreadsheets (beaver.office.spreadsheets) for XLSX workbooks, and Presentations (beaver.office.presentations) to create PPTX files and fill in templates. In the application, the type is spelled out under the name: Official plugin or Local extension.

Where to find an extension

Note There is no built-in catalog and no marketplace. No extension is recommended to you, and none is checked on your behalf. You bring the code, you answer for it. Three questions are worth asking before installing: do you know who wrote this code, and can you check it? Can you read what it does before approving it? Does this extension have a legitimate reason to ask for your API keys?

The file picker accepts js, mjs, cjs, jsx, ts, mts, cts, tsx, mtsx, ctsx and json. On the Git side, unencrypted HTTP is refused, as is any address containing credentials. One detail that matters later on: an extension added from a local file or folder is not copied — Beaver loads the source where it sits on your machine. An extension that comes from Git or npm is copied into ~/.local/share/cl-go-dash/extension-installs/, and it is that copy Beaver runs.

Adding an extension

  • Open the screen. Settings › Extensions. Three tabs: Plugins, Extensions, Host — the host being the separate process that runs extension code.
  • Go to the Extensions tab. The Add button only appears there: official plugins are not added, they are shipped.
  • Click Add. The window shows a warning first, before any option: "The selected code will run with your user account's rights. Only install an extension you choose to trust."
  • Choose the source from Choose a file, Choose a folder, Install from Git, Install from npm.
  • Let the installation work. It runs in the background: you can close the window and carry on, and closing the tracker cancels nothing. The tracker appears on the Extensions page and in the notifications panel. The steps shown: Resolving source, Downloading, Installing dependencies, Verifying, Preparing interface, Finalizing, Cleaning up. Only one installation works at a time; the queued line says which one is blocking it.
  • Answer the volume request, if it appears. Beyond 1 GiB taken up by the installation, Beaver stops writing and offers Continue installation or Cancel. It keeps a reserve of 1 GiB of free space. No timeout counts as consent: an unanswered request stays pending indefinitely.
  • Open the entry that was created. The extension appears in the list — and it does nothing. Its status is Disabled, it is not approved. That is deliberate. The entry shows the status, the API level (Stable or Advanced), the runtime, the author, the installation source, the source, and the Open source button, which shows the code actually loaded.

Install, then trust

This is the most important point on this page. Installing grants no rights. The code formally refuses to enable an unapproved extension if confirmation does not accompany the request; on the interface side, flipping the switch of an unapproved extension enables nothing, it opens a confirmation window. It shows the title "Enable {name}?", the text "This extension will have full access to your account data, secrets, and features. Beaver has not audited it.", and two buttons: Cancel and Trust and enable.

Warning Approving means approving everything at once. Approval covers all of the extension's code and all of its dependencies. There is no per-key, per-file or per-folder permission. An approved extension can ask for your API keys and tokens directly, with no further question.

If the manifest declares an interface module in advanced mode, the window adds a paragraph — "Its advanced interface module runs directly inside Beaver and can change, access, or break the entire interface." — and a mandatory checkbox. The confirm button stays inactive until it is ticked. An advanced interface shares the same page as Beaver's, with the same rights: if you do not know why an extension needs that level, do not enable it.

At the moment you confirm, Beaver computes the fingerprint of the files, stores it and records the approval date, shown afterwards under Trusted since. It covers the JavaScript and TypeScript sources, the manifest and the interface artifact; symbolic links are refused, the comparison is done in constant time, and the limits are 2,000 files, 4 MiB per file, 32 MiB in total, depth 16.

Note The fingerprint does not cover node_modules or .git. A dependency modified locally therefore does not trigger a new approval request. As for the shortcut in the + menu of the input field, it leads to exactly the same confirmation window: it is not a back door.

Enabling, disabling, showing in the chat

Enabling makes the extension's tools available to the agent and starts its process. Disabling marks the extension as disabled in the registry — that change is written to disk before the process is stopped —, clears the permissions granted during conversations, then stops the process. Approval survives disabling: re-enabling afterwards asks nothing again, as long as the files have not changed.

Security Disabling does not recover what has already left. If an extension obtained one of your keys, disabling or removing it does not undo that: it may have kept a copy. Beaver reminds you — "As a precaution, change the access credentials used by this extension directly with their provider." The only effective action is to revoke the key at the service concerned.

Every extension carries a second switch, Show in chat, independent of activation. It changes nothing about the model's capabilities: it adds an activation shortcut to the + menu of the input field, which only exists in Agent mode. That menu shows eight lines before it becomes scrollable — that is a display height, not a cap on extensions. By default: on for the four official plugins, off for any extension you add.

Updating and reloading

Only extensions installed from Git or npm have an Update button. An extension that came from a local file or folder does not: you own the source. The button asks for a two-step confirmation, under a permanent warning: "Updating will disable the extension. Review the new version before trusting it again." Beaver then prepares a new copy next to the old one and only swaps after validation; the fingerprint changes, so approval is revoked, the extension moves to Error with the message "The extension files changed and must be reviewed again". An update that changes the extension's identity is refused. There is no automatic update.

For an extension linked to a file or a folder on your machine, Reload applies your changes. Two consequences catch people out: Reload restarts the whole host, so every extension stops and reloads together; and your changes alter the fingerprint, so modified local extensions are revoked, disabled, and ask for approval again.

Note Developing an extension takes you back through the trust step at every reload. That is not a defect: it is exactly the guarantee that protects the users who never modify their code.

Removing

The Remove button asks for a two-step confirmation. Beaver clears the conversation permissions, writes the deactivation to disk before stopping anything — so a process whose shutdown is not confirmed can never become active again at the next start —, stops the process and waits for confirmation of that shutdown, takes the extension out of the registry, deletes its interface artifact, then the managed copy if the installation came from Git or npm.

What removal does not do: it does not touch your file or folder if the extension was local; it does not recover any secret already handed over; it does not delete files the extension may have written elsewhere while it was running. Managed copies that become orphaned are cleaned up at the next start.

Warning Removal cannot be undone. Beaver does not offer to restore a removed extension. For a Git or npm installation, you will have to reinstall it from its source; for a local extension, your file or folder is untouched.

When an extension crashes

The troubleshooting order, from the least committing to the most radical: read the diagnostics in Settings › Extensions › Host; open the entry to see the status, the source and the last error; Open source to audit the code actually loaded; Reload after a local fix, or Update for a Git or npm installation; disable the extension; Restart host if the runtime itself is in error; Remove if you no longer trust it.

The Host tab shows the status (Stopped, Starting, Running, Error), the versions of Node.js, Jiti and the Beaver API, the number of active extensions, and the Latest loading errors with the identifier of the offending extension and the file concerned. Two buttons live there: Restart host and a Recovery mode that "disables Beaver plugins and local extensions so Beaver can return to a working state".

A crash does not drag the others down. Beaver automatically restarts a host at most 3 times over a 5-minute window, then stops trying. If Beaver stopped while an extension was loading, a recovery flow appears at the next start, with four outcomes: Open detail, Keep disabled, Retry loading, Restore previous registry. If an advanced interface stops Beaver from opening, quit the application completely then hold Shift during the restart — on Linux with Wayland, the key is asked for after the window appears. The executable also accepts a dedicated argument.

$ beaver --safe-mode

That launch shows no third-party interface and leaves the Extensions screen reachable so you can disable the offending module. If the registry itself is unreadable or comes from a newer version of Beaver, the application refuses the whole registry rather than replacing it with an empty list: your files are kept, any extension change is blocked, and conversations carry on with the internal tools only, plus a warning. Finally, an extension's raw output is never kept, because it can contain secrets: the diagnostics give the step, the category and the position, not the content.

What the Tools screen does not show

On an extension's entry, the Registered contributions section lists every declared tool with its technical name, its translated effect class — Read only, Local write, External read, External write, Process, Secret access, Unknown effect — and, where relevant, the note Replaces a built-in tool. A Skills and resources section lists the declared skills and resources.

Note The Settings › Tools screen does not tell the whole story: no extension tool appears there. Those tools are dynamic and are managed only from their extension's entry. And the three internal tools through which the agent discovers extensions — list_extensions, inspect_extensions, load_extension_resource — are always active and appear on no screen. That is not a security hole, they only list and read what you have approved, but it is better to know. See Tools overview.

One last setting worth knowing: Priority plugins. When the extension definitions exceed 10% of the model's context window, Beaver stops sending them all and switches to progressive discovery. You can designate up to 15 plugins to keep available as a priority.
