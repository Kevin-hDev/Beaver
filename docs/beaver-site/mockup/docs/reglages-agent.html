What the agent knows, says and is allowed to do

Four tabs decide the agent's behavior: what it remembers, the instructions that define it, the tools at its disposal, and the access it has to your machine. This page describes the screens: where the field is, what it holds, what it triggers.

The Advanced tab is the busiest in the whole application: it carries several blocks with no direct relation to each other. That's where the two settings people most often look for elsewhere live — folder access and the Ollama engine's behavior.

Memory tab

The tab opens on a framing sentence: “Manage what the agent can remember over time without loading every detail into each conversation.”

Memory mode — “Manual mode requires an explicit request. Automatic mode keeps only durable facts.” Three values:

The three memory modes
Label shownBehavior
DisabledDefault value. Nothing is remembered; files already written are kept
ManualThe agent only remembers on an explicit request
AutomaticThe agent remembers on its own what it judges durable

Context budget — “Maximum space reserved for the memory summary and memory reads.” Six values: 512, 1,000, 1,500, 2,000, 2,500 and 3,000 tokens. The default is 3,000, which is also the maximum the engine accepts. The selector is greyed out when the mode is Disabled. This budget is a ceiling, not a reservation: it's the maximum room memory can take in a conversation's context window.

Below the settings, a “Saved memories” section lists what the agent has remembered, with a search field and two filters.

The two filters of the memory list
FilterValues
TypeAll types, Preference, Feedback, Project, Reference
StatusAll statuses, Confirmed, Inferred, Needs review

Memories are grouped by scope: Global memory, then Active project followed by the project's name if there is one, then the other projects. The other projects' memories aren't loaded straight away: a “Show memories” button requests them on demand. Selecting a memory opens its content, with two actions — Close and Archive, archiving requiring a confirmation.

Two banners can appear at the top of the list. When the mode is off: “Memory is disabled. Existing files are kept.” And when files from an earlier organisation are found, a “Legacy content detected” banner states: “Old folders are preserved but never injected.”

The tab has its four states written: “Loading memory…”, “Could not load memory” with a Retry button, “No memory in this scope”, and the list itself.

Note Turning memory off erases nothing. The Disabled mode stops injecting and writing, but the memories already saved stay on disk. Turning them back on makes them available again. What memory retains and how is detailed in Persistent memory.

System prompt tab

The tab is called “System prompt” in the left-hand list, and its title once open is “System instructions”: both words designate the same thing.

This screen sets the global instructions, the ones that apply to every model. Ollama models can have their own instructions, set elsewhere — see Models.

Two selectors command what is displayed:

The two selectors that choose the text displayed
SelectorValues
Model modeChatbot, Agentic
Instruction formatCompact, Detailed

On opening, the screen presents the Agentic mode in the Detailed format. So there are four distinct texts to consult and customise, one per combination. Three sources are possible for the displayed text — Beaver, Ollama, Custom — and the actions offered are Edit, Use Beaver, Use Ollama, then Save or Cancel.

Two safeguards protect against losing work:

  • A warning before the first change, titled “Warning”: “This change replaces Beaver's system instructions for every AI, except Ollama models that have their own custom instructions.” A “Do not show this warning again” checkbox silences it.
  • A loss warning — “The custom prompt will be deleted” — with a “Copy prompt” button to save it before continuing. It appears when you go back to Beaver's or Ollama's instructions after writing your own.

Leaving the field empty is an explicit choice, and the field's text says so: “Leave empty to send no system instructions.” What these instructions contain is detailed in System prompts.

Tools tab

The tab opens on a sentence that lays out the whole principle: “These tools define what the agent can do for you. Essential tools are always on. Optional tools turn on or off based on your needs: the agent will only use what's enabled.”

Two sections, “Essential tools” and “Optional tools”. Tools aren't set one by one: they are grouped, and the switch acts on the whole group.

The five always-active groups. They carry the mention “Always on” in place of a switch, and the engine refuses any attempt to turn them off, including through a direct call — the message is then that the tool group is locked.

The five locked tool groups

FilesRead, create and edit your project's files: code, configs, notes, documents
File searchDig through your project to find a file or search for a specific word in the code
WebSearch for information online and open web pages
External connectorsUse the external connectors configured in the Connectors tab

The switchable groups, with their state at installation:

A group counts as enabled only if all its tools are. A half-enabled group doesn't happen through the interface; it could appear with a settings file edited by hand, and the switch would then show as off.

Warning Six tool groups are off at installation. Spreadsheets, Word documents, images, Git branches, task lists and Forecast aren't available until they are turned on here. An agent that “refuses” to open an Excel file most often doesn't have the tool — it isn't a matter of the model's capability.

Each tool is described in Tools overview. Tool groups aren't the permission modes, which are a separate mechanism: see Permission modes.

Advanced — import from other assistants

The tab's first block, “Import from other assistants”: “Manage rules, instructions, and skills read from your other tools.” A “Manage” button opens the dedicated screen.

This is the way back to it after the first launch — which the application announces during onboarding, incidentally: “You can change these choices later in Settings > Advanced.” The subject is covered in Importing from another agent.

Advanced — general behavior

A card with two settings.

Menu bar icon — “Keep Beaver in the system tray”. On by default.

Default model — “Model used by default for new conversations”. A searchable dropdown, grouped by provider, fed by the models actually available. Empty by default.

Advanced — context compression

Between the general behavior and the Ollama engine, a card titled “Compression” sets the way Beaver summarises conversations that grow too long: the global profile, its trigger threshold and the advanced profile editor. All of how it works — what triggers a compression, what is kept, what is removed, and every setting on this card — is described on the Context compression page.

Advanced — the Ollama engine

A block titled “Ollama”, distinct from the Ollama tab of the Models section. The split is this one: the Ollama tab manages the models; this block manages the engine that runs them.

Unload model — “Time before freeing model memory”. Seven values: Immediately, After 2 min, After 5 min, After 10 min, After 15 min, After 30 min, On app close. By default: After 5 min.

Hardware Acceleration — “Inference engine for local models”. Two values, CPU and GPU, with GPU by default. This setting doesn't appear on Mac, where the question doesn't arise.

Load multiple models — “Keep multiple models in VRAM simultaneously (requires more GPU memory)”. Off by default.

Show GPU status — “Display RAM/VRAM usage and CPU execution status in the chat”. Off by default.

A restart is needed for three of these four settings. Changing the unloading, the hardware acceleration or the multi-model option makes an extra line appear — “Restart required”, “Changes will be applied after restarting Ollama” — with a “Restart Ollama” button. Only “Show GPU status” applies immediately.

The restart gives three possible outcomes: “Ollama restarted” on success, “External Ollama reused” when Beaver found an engine already running that it doesn't own, or an error message.

Below these settings, a reference table — “Required VRAM per model”, “Estimated VRAM needed based on model size and quantization”. How to read it is explained in Hardware and VRAM, and the engine's life cycle in Local engine.

Advanced — File Access

This is the most important setting on the page. Title shown: “File Access”. Description: “Session working folders. Required tool components and network access remain available”.

The screen presents a list of folders, each with a cross to remove it, and two buttons: “+ Add folder” and “Reset”.

The default value is the root of the disk — / on macOS and Linux, C:\ on Windows. The interface doesn't show it as a path but under the label “Full disk”. It's a deliberate choice: the agent starts with full access to the disk, and it's up to you to restrict it if you wish. The reasoning is developed in Security model.

Three behaviors worth knowing:

  • The list can never be empty. The delete cross is disabled as soon as a single folder remains, and the engine restores the default if an empty list reaches it anyway.
  • The “Reset” button restores full disk access. It doesn't reduce rights: it puts them back to their original value, which is the widest one.
  • Restricting access interrupts work in progress. When the new list is narrower than the old one, the engine cancels all the agent's requests in flight and stops all the terminal processes launched. This is deliberate: without it, a command already under way would keep working in a folder that has just been removed. Widening access, by contrast, interrupts nothing.
Warning “Reset” widens access, it doesn't restrict it: this button restores the original value, that is, the whole disk. To restrict, remove the folders one by one and add only those the agent needs.

This setting has a single owner. It doesn't go through the same path as the other advanced settings: the two general save commands explicitly refuse to touch the folder list, and only the dedicated command can change it. Concrete consequence: no other screen, no automatic save, no extension going through the general settings can widen your access rights as a side effect.

A link from an error message can open this block directly: the area is then highlighted for 1.8 seconds and the screen scrolls to it. The folder a conversation works in is described in Working directory.

Advanced — session files

The last block, titled “Session files”, with two lines.

Deliverables location — “Beaver creates a separate folder there for each session's deliverables”. Two buttons: “Choose” opens a folder picker, “Default” — visible only if a folder has been chosen — goes back to the original value, shown as “Default Beaver folder”.

The path is validated before being accepted: it must be absolute, be under 4,096 characters, contain no control character and no ... A refused path produces the message that the output folder is invalid.

Beaver data — “Open the folder containing sessions, memory, and local settings”, with an “Open folder” button that opens the system's file explorer. It's the shortest way to reach ~/.local/share/cl-go-dash/ without typing it.
